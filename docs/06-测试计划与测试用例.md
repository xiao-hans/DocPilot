## 1. 测试目标

验证多租户隔离、文档处理正确性、任务恢复、结果可追溯、审阅流程、搜索和导出安全。测试优先覆盖跨租户越权、敏感文件处理、重复任务、部分失败和持久化恢复等高风险场景。

## 2. 测试范围

### 范围内

需求/设计静态评审、单元、API 集成、数据库迁移、队列/Worker、端到端浏览器、权限与租户隔离、安全、负载/容量、备份恢复、可用性/可访问性。

### 范围外（待具体版本）

未选定的云厂商认证、正式渗透测试认证、未接入的集成商验收和未知监管框架合规认证。

## 3. 测试策略

| 层级 | 重点 | 自动化目标 |
|---|---|---|
| 静态评审 | 需求可验证性、设计威胁面、迁移/回滚、文档追踪 | PR checklist / lint |
| 单元 | 权限策略、状态机、字段校验、幂等、文件名处理、导出转义 | CI 每次提交 |
| 集成 | API+DB、对象存储、队列、Worker、外部服务替身 | CI/预发布 |
| 系统/端到端 | 登录、模板、上传、处理、复核、检索、导出 | 每个发布候选 |
| 安全 | 跨租户对象引用、角色滥用、注入、文件炸弹、CSRF/SSRF、密钥与日志 | 自动化回归+定期人工评估 |
| 性能/恢复 | 上传吞吐、队列积压、搜索分页、Worker 扩展、备份恢复 | 预发布按基线目标执行 |
| 可用性 | 键盘导航、错误反馈、长任务状态、屏幕阅读器语义 | 关键流程抽查 |

## 4. 环境与测试数据

- CI 环境：临时数据库、队列、对象存储模拟器和 OCR/LLM stub；无真实客户数据和生产密钥。
- 预发布：与生产拓扑接近，使用合成/脱敏文档，启用安全日志和可观测性。
- 测试租户至少 A/B 两个、不同角色用户及平台管理员；使用重复 ID/路径参数进行越权验证。
- OCR/LLM 通过录制夹具或 stub 保证稳定；另设受控质量评估集跟踪提取准确率，避免把模型非确定性用例混入普通单测。

### 5.8 G1 在 PostgreSQL 上暴露的方言缺陷（2026-10-03）

G1 首次双跑时全量 248 项用例，发现并修复三类只有 PG 才会暴露的问题：

| 缺陷 | 表现 | 根因 | 处理 |
|---|---|---|---|
| 审计游标在 PG 上 422 | `GET /audit-events?before=<created_at>` 返回无 `events` 键 | `document_versions.created_at` 等列声明为 `DateTime(timezone=True)`，SQLite 返回 naive、PG 返回 tz-aware，`isoformat()` 带 `+00:00`；查询串里 `+` 按规范解成空格，FastAPI 解析失败。`tests/test_audit.py::test_audit_pagination_is_descending_and_stable` | `app/services/membership.py` 新增 `_iso_utc()`，UTC 时间戳统一输出 `...Z`，两方言格式一致且可直接回塞查询串 |
| 含 NUL 的结果值无法入库 | `psycopg.DataError: PostgreSQL text fields cannot contain NUL (0x00) bytes` | PostgreSQL 的 text/json 一律拒绝 `\x00`，SQLite 照收；脏文本来自 OCR/人工修订值 | 在两个入库边界剔除 NUL：`app/contexts/search/service.py` 的索引内容、`app/contexts/review/service.py` 的 `revise()` 字符串值；`tests/test_export_formats.py::test_csv_and_xlsx_share_control_chars_whitespace_and_overlong_cells` |
| 用例依赖数据库返回顺序 | `AssertionError: assert ['xlsx', 'csv'] == ['csv', 'xlsx']` | `tests/test_export_formats.py::test_export_is_audited_and_tenant_scoped` 查询审计事件时没有 `ORDER BY`，SQLite 恰好按插入顺序返回，PostgreSQL 不保证顺序。**这是测试缺陷，不是应用缺陷**——导出接口不承诺返回顺序 | 用例改为显式 `order_by(created_at, id)` 且断言不依赖排列（按排序后的集合比较） |

**同一根因的残留项（未在 G1 处理，须在后续阶段收口）**：时间戳序列化只在审计端点统一，其余端点仍按方言返回 naive 或 `+00:00`；NUL 剔除只覆盖复核修订与搜索索引两处入口，机器提取结果直接落 `extraction_results.values` 的路径未覆盖，遇到含 `\x00` 的解析文本仍会在 PG 上写入失败。

### 5.14 G5 第一部分：就绪判定纳入队列消费者（2026-10-03）

G2 留下的缺口：设置 `BROKER_URL` 后 API 不再进程内执行任务，但如果没有任何 Worker 在消费，任务会安静地停在 `queued`，而 `/readyz` 仍报 ready（`docs/17` G-DEC-09、风险 R-017）。现在 `/readyz` 的响应多了 `queue` 段并参与判定：

| 情况 | 判据 | 结果 |
|---|---|---|
| 未启用队列 | `BROKER_URL` 为空 → `{"enabled": false, "reason": "queue_disabled"}` | 队列不参与判定（进程内执行本就是基线） |
| 有积压、没有消费者 | `pending > 0 && consumers == 0` | 503，`queue.stuck=true`，并给出 `oldest_pending_seconds` |
| 没有消费者、也没有积压 | `pending == 0 && consumers == 0` | 200（缩容到零是正常状态，不该读成故障） |
| 问不到 broker | `consumers === null`（连接失败或队列不存在） | 503：配置声称走队列却连状态都取不到 |
| 探针自身抛异常 | 记为 `queue_probe:<类型>` 并判不就绪 | 503，`/readyz` 绝不因探针变成 500 |

消费者数取自 RabbitMQ 的 `queue.declare(passive=true)`：只查询、不创建，因此"配置里队列名写错"不会被探针自己掩盖成一个空队列。`pending` 只统计 `ready`/`published` 的派发意图——已 `claimed` 的行由租约超时回收负责，算进来会让"一个慢任务"看起来像队列故障。等待年龄显式按 UTC 归一（SQLite 返回 naive、PostgreSQL 返回 tz-aware）。

过程记录：`consumer_count()` 第一版按旧文档写成 `declare_ok[0].consumer_count`，在真实 broker 上永远返回 `None`——pika 1.3 的 `BlockingChannel` 返回 `Method` 包装（计数在 `.method` 上）且不可下标访问；`except Exception` 又把它伪装成"问不到"。修掉后异常面收窄到 `AMQPError`/`ChannelClosedByBroker`，编程错误不再被当成依赖故障。这是继 G2 回调签名、G3 `list_keys` 之后第三次同类问题。

三条会改变读法口径的发现：

- **`queue_backlog()` 的 `oldest_pending_seconds` 不是排队时间**。它按派发行**最后更新时间**算年龄，派发器投递成功会刷新这一列，所以它量的是"最久没有任何动作"——时间线里它先高后低正是这个原因。对 `/readyz` 的"卡住"判据这是正确语义，但拿它当排队指标会低估积压；真正的排队等待必须按 `job_dispatches.created_at → job_attempts.started_at` 算。
- **排队等待与调度延迟是两个数量级**：从"派发行创建"起算的等待 P50 是 5.6 秒（里面含 8.2 秒的任务创建循环），从"发布确认"起算的调度延迟 P50 只有 831 毫秒。引用时必须说清是哪一个。Worker 冷启动（进程 spawn → 8 个消费者到位）单独测了一项：5.2 秒。
- **夹具必须不可压缩，归因边界必须切开**：第一版大对象用重复文本填充，deflate 把 21 页压到 9.5 KB，于是 18 MB 目标要写四万多页，脚本被自己的夹具拖死（观测跑了 90 秒还没生成完）；改成"首页发票文本 + 随机噪声图像页"后 18.4 MB 约 1 秒生成，形状也更接近真实扫描件。同类坑有两个：RSS 必须在**仍持有对象时**采样（先 `len()` 再释放就永远测到回收后的水位，第一版因此报出"整对象读不涨内存"的假结论）；一个差值不能同时盖住"写 1000 份文档 + 记 1000 条结果"和"读导出行"，混在一起时同一个指标在两次运行里报出 7.5 MB 与 86.8 MB，看着像导出路径退化，其实只是归因没切开——现在写入侧与读取侧分列。

G6 之后的门禁证据：`scripts/migration_gate.py` 退出码 0、`alembic check` 无漂移；基础套件 PostgreSQL 303 项通过（135.44 秒）与 SQLite 303 项通过（115.05 秒），各 1 项跳过；真实 broker 套件 PostgreSQL 4 项（3.99 秒）；真实 S3 套件 PostgreSQL 8 项 + 1 项跳过（3.92 秒）。G6 只新增脚本与报告，未改动应用代码。观测脚本与 pytest 都会重置 `docpilot_test`，二者**不能并行**，本轮按「门禁 → 观测 → 观测复跑」的顺序执行。

未覆盖（报告里逐条列了）：真实提取器（OCR/LLM）的耗时与失败率、S3 后端下的同路径观测、多机部署与 broker 集群故障转移、Worker 子进程自身内存曲线、真实 1TB 语料。**性能阈值（P95 目标、吞吐上限、持续时间、文档构成、CPU/内存限额）仍未评审，因此本轮数字只是基线，不构成"支持 100 租户 / 1TB / 100 并发"的证据，也不是 SLA。**

### 5.17 G8 Compose 形态端到端与派发租约竞态（2026-10-03）

端到端环境从"一次性本地进程"换成 Compose 依赖栈：`E2E_COMPOSE=1 npx playwright test`，依赖来自 `docker-compose.yml`（PostgreSQL + RabbitMQ + SeaweedFS），一次性库与对象前缀由 `scripts/e2e_compose_env.py` 建立和回收，API / 派发器 / Worker 是三个独立进程。10/10 通过，1.4 分钟，`TEARDOWN RESULT: CLEAN`。

| 问题 | 表现 | 性质 | 处理 |
|---|---|---|---|
| Worker 抢在发布确认之前领租约，任务永久停在 `queued` | 复核用例 `waitForSuccess` 120 秒不通过，库里任务是 `queued`；现场日志 `docpilot.worker 未领到租约，跳过 dispatch_id=4d66c1bc…` 打在 22:27:03.514，而派发器写出同一行的轮次日志在 22:27:03.517——早 3 毫秒 | 真实缺陷，不是用例太脆。`Dispatcher.run_once` 的顺序是"先把消息投出去、拿到 confirm 才写 `published`"，而 `claim_lease` 只认 `published`，`handle()` 领不到租约就返回 True，传输层于是**确认掉这条消息**：消息没了，行还停在 `published`，要等 `DISPATCH_REPUBLISH_SECONDS`（300 秒）才可能重投。进程内基线看不到它（没有 Worker 与派发器赛跑），G2 的假传输用例也看不到它（投递和领取不同步发生） | `claim_lease` 的可领条件放宽为 `ready` 或 `published`：行早已提交且带齐 `(tenant, job, attempt_no)`，消息存在本身就是投递证据，条件更新仍是单一胜者，因此不引入重复执行。回归用例 `test_worker_beating_publish_confirmation_still_executes`（传输层在 `publish()` 内同步调用 `handle()`），负向验证：把谓词改回只认 `published` 时报 `assert 'queued' == 'succeeded'`。同时给 `handle()` 的跳过分支补 INFO——这是"消息被确认掉但任务没执行"唯一的现场证据，此前一无所有 |

### 5.18 阶段 G13：应用侧容器化后的 Compose 端到端（2026-10-04）

G8 把依赖换成真的，但应用与 Worker 仍是 Windows 侧的三个进程，因此"干净 Compose 环境"这条口径只满足了前半句。G13 补后半句：`Dockerfile` + `.dockerignore` + `docker-compose.yml` 的 `profile: app`（`migrate`/`api`/`dispatcher`/`worker`），端到端加 `E2E_APP_CONTAINERS=1` 形态——主机只剩 vite，其余都在容器里。

另两种形态本轮回归：默认一次性本地进程 **12/12**（1.1 分钟）、Compose 依赖栈 + 主机应用进程 **11 passed + 1 flaky**（重试即通过，套件用时 4.2 分钟；单跑那条用例 12.5 秒通过）。这条 flaky **未归因**：首轮失败、重试通过，单跑同一条 12.5 秒通过；我当时没有先留住 `test-results/…/error-context.md`，随后一次单跑把它覆盖了，所以现场证据已不在。不写成"冷启动导致的已知现象"，那超出证据支持的范围。

这一轮真正被证明的是三条判据，不是"用例过了"：

| 判据 | 为什么要它 | 怎么成立 |
|---|---|---|
| 迁移由容器负责 | 主机先迁移一次的话，"库是新的"永远成立，等于什么都没验 | `prepare --app-containers` 不跑主机 alembic；`app-up` 之后直接查 PostgreSQL 的 `alembic_version`，查不到就中止 |
| 容器连的是这套一次性环境 | 端口通了不代表连对库；镜像里有 SQLite 默认值兜底 | `app/main.py:29` 在非开发环境见 `sqlite` 连接串即抛错，容器起不来 → `app-up` 的形状核对（api running + healthy、migrate exited）失败并报 40 行日志 |
| 默认开发基线没被改动 | G1 以来 `docker compose up` 只起基础设施，备份演练与日常开发都依赖这条 | `tests/test_compose_shape.py` 断言三个依赖服务不带 `profiles`、四个应用服务只挂 `app`，且 `x-app-env` 不用 `${VAR:?}`（顶层扩展字段在解析整份文件时就求值，会把没启用 profile 的 `up` 一起拖垮） |

同一份用例文件里还有两条"守卫的守卫"：YAML 重复顶层键必须报错（本轮我自己写过第二个 `services:`，YAML 默认静默覆盖，只有 `docker compose config` 才报出来），以及 `Dockerfile` 的 HEALTHCHECK 路径必须在 OpenAPI 的 paths 里存在——指错端点的表现是容器永远 `unhealthy` 而不说原因，这类失败只会在端到端"莫名起不来"时才被发现。两条各配了负向用例：合成一段重复键的 YAML、合成一个指向 `/nopez` 的 HEALTHCHECK 文本。

同一轮还暴露了一处**门禁环境的隐性耦合**（不是 G13 引入的，但被这一轮的跑法抓出来）：`BROKER_URL` 只要存在于调用 shell 里——我先在同一条 shell 跑完 `-m broker`，接着跑 `-m s3`——上传端点就走队列而不是进程内执行，没有 Worker 消费时任务停在 `queued`，与队列无关的 `-m s3` 门禁里 `test_uploaded_job_reads_back_through_the_s3_adapter` 因此报失败：单跑通过、带那个变量就红，排查方向完全指错地方。`tests/conftest.py` 现在用 autouse 夹具把 `QUEUE_ENABLED` 默认钉成关闭（`-m broker` 标记的用例与 `queue_mode` 夹具自己再打开）。实测：同一个测试在同一份 `BROKER_URL` 环境下由 FAILED 转 PASSED；`-m s3` 8 项与 `-m broker` 4 项在该环境下通过。

未覆盖：镜像内容的构建期审计与供应链核验、多机部署、非 root 之外的安全加固（镜像内已是 uid 10001，但没做只读根文件系统与 capability 收敛）。

### 5.25 维护轮 M2：适配器可替换性契约（NFR-004，2026-10-10）

`NFR-004` 此前是追踪矩阵里唯一整格没有测试映射的需求行，映射栏只有"后续适配器契约测试"一句散文。本轮补 `tests/test_adapter_contracts.py` 8 条。

**为什么单独立一个文件而不是加进 `test_parsing.py` / `test_extraction.py`。** 那两个文件覆盖的是**构造函数**注入：`DocumentPipeline(dispatcher=..., extractor=...)`、`ParserDispatcher(FakeOCREngine())`。生产路径走的却是**工厂与单例**。此前没有任何用例证明"替换点在工厂层有效"——构造函数层的绿全部成立时，生产路径照样可能不可替换。契约测试要测的正是这一层。

| 判据 | 做法 | 反向（怎么证明它不是恒过） |
|---|---|---|
| 接缝在生产路径上生效 | 替换后在真实上传接口上跑完整链路，断言假解析器的文本进了 `document_texts`、哨兵值进了 `extraction_results` | 撤掉解析接缝 → 2 条红 |
| 读回经接口而非具体类 | 断言解析链路走 `get_object_storage()`（`local_path` 被调用），且没有多余 `open_read` | 存储只换写端 → 4 条红 |
| 写端与读端同一实例 | 断言语义相等的键集合 | 同上 |
| 两个后端都满足抽象方法集 | 比对 `__abstractmethods__` 与各实现的覆盖，再跑一遍契约行为（写→存在→大小→读回→删→不再存在） | `S3Storage` 移除一个抽象方法实现 → 红 |
| 工厂的拒绝分支 | 未知提取模式抛 `ValueError`，未知 `STORAGE_BACKEND` 抛 `RuntimeError` | 与上一条同一文件内，撤销即红 |

**实测到一处接缝差异，写进用例而不是只写在注释里。** 第一次跑这个文件时 2 条失败，签名是"假解析器一次都没被调用"。查下来是绑定时机不一致：

| 适配器 | 绑定时机 | 想替换时该动哪里 |
|---|---|---|
| 对象存储 | **每次调用**解析工厂 | 换 `build_object_storage()` / `get_object_storage()` |
| 解析器 | **构造时**绑定到 `DocumentPipeline.dispatcher` | 换工厂函数**无效** |
| 提取器 | **构造时**绑定到 `DocumentPipeline.extractor` | 同上 |

`get_job_manager()` 是进程级单例，它的 `DocumentPipeline` 在首次调用时就把当时的工厂结果存了下来。这不是缺陷——单例本来就是这个语义——但它意味着**想在生产形态下替换解析器或提取器，没有一个注入点**：只能改 `EXTRACTOR_MODE`（在 mock 与 llm 之间选）或替换类方法。已写成断言 `test_dispatcher_and_extractor_are_bound_at_construction_time`，哪天有人把流水线改成每次调用都解析工厂，这条会红并提示同步更新 `docs/07 NFR-004`。

**一处现状记录，不是验收。** `NFR-004` 把"搜索后端"也列为可替换项，但项目里没有搜索后端抽象：检索走 `search_entries()` 直接查 `search_entries` 表（`app/contexts/search/repository.py`），换后端要改仓储函数，没有接口可注入。用例 `test_search_backend_has_no_factory_and_that_is_recorded` 把这件事写成断言，避免"搜索后端可替换"被默认读成已满足；真要做替换点，应新增抽象并同步改这条用例与 `docs/07 NFR-004`。

> **维护轮 M16（2026-10-10）更新**：搜索后端抽象**已交付**（`app/contexts/search/backend.py`，设计见 `docs/22`）。上一条现状记录已改成 `test_search_backend_factory_exists_now`——它不再断言"没有工厂"，而是断言"工厂存在且在生产路径上生效"。完整契约在 `tests/test_search_backend.py`（11 条），见 §5.31。

判定方式与结果：`tests/test_adapter_contracts.py` **8 项全通过**（2.2 秒），三处反向验证各自成立（见上表）。本轮为纯新增，未改任何产品代码。

### 5.26 维护轮 M3：请求关联 ID 贯穿（NFR-005，2026-10-10）

`NFR-005` 要求"关键业务操作结构化记录关联 `request_id`、`tenant_id`、`job_id`；日志不得包含密钥或不必要的文档内容"。`tenant_id` 与 `job_id` 此前已到位（审计表按租户非空、任务链路自带 ID），缺的是 `request_id`：全仓 grep 无一处实现，`docs/11 §4.2` 当初拒绝给审计表加这一列的理由是"当前没有产生方，避免留下无消费者的空字段"。本轮把产生方与列一起交付，那个理由因此不再成立。

**一个 ID 要同时出现在三处才有用。** 只进响应头，用户拿着 ID 查不到日志；只进日志，用户根本不知道自己的 ID 是什么。三处分别是响应头、日志行、审计事件，每条判据对应其中一处。

| 判据 | 做法 | 反向（怎么证明它不是恒过） |
|---|---|---|
| 响应头带 ID | 每个请求回填 `X-Request-ID`，错误响应也带 | 中间件不回填 → 2 条红 |
| 入站 ID 沿用与校验 | 合规（可见 ASCII、8–64 字符）沿用；不合规替换 | 去掉校验改为回显原值 → 1 条红 |
| 每请求独立、不泄漏 | 两个请求 ID 不同；处理完后上下文清空 | 与第一条同一处，撤销即红 |
| 审计行与响应头同值 | 同一次请求的响应头 ID 与 `audit_events.request_id` 相等 | 审计不读上下文 → 2 条红 |
| 审计列表可读 | 该字段回给租户，否则关联只有 DBA 看得到 | 列表不回传 → 1 条红 |
| 无上下文不编造 | Worker、脚本路径写 `NULL`；显式传值优先 | 与上一条同文件内 |
| 日志真的渲染 | 用格式串手工格式化一条记录，断言文本里出现 ID | 只看"过滤器已挂"证明不了格式串里有 `%(request_id)s` |

**实现要点**（`app/request_context.py`）：

1. **中间件生成或沿用**：请求头带 `X-Request-ID` 时沿用（便于前端与网关串联），否则生成 32 位十六进制。
2. **格式校验**：只接受可见 ASCII、长度 8–64。不校验的话，控制字符会被写进日志行（伪造出新行）与响应头（响应拆分面）。不合规一律换成本进程生成的新 ID，**不报错**——关联 ID 不值得让一个正常请求失败。
3. **`contextvars` 而非参数传递**：审计写入点在服务层、日志散在各处，逐个加参数会改动几十个签名。上下文变量还带来一个必要的副作用：**后台线程天然拿不到请求上下文**，避免把一个请求的 ID 错误地贴到另一个请求的日志上。
4. **不给数据库默认值**：迁移 `e1f4c7a29d63` 加的列可空且无默认。历史行没有这个值，猜一个等于编造关联。
5. **日志配置集中一处**：派发器、Worker、Webhook 投递三个入口此前各写一份 `basicConfig(format=...)`，格式里没有关联 ID 也没有过滤器。现在统一走 `configure_logging()`；没有请求上下文时过滤器填 `-`，让"没有"在日志里是显式的。

**未做**：`request_id` 没有进任务与结果表，也没有做跨服务的传播（本项目是单进程 API + 三个后台进程，没有上游调用方）。`tenant_id`/`job_id` 的结构化字段化同样未做——它们目前只在审计的 `object_id` 与 metadata 里出现，没有独立列。这两条仍记在 `docs/07 NFR-005` 的"仍未做"里。

判定方式与结果：`tests/test_request_id.py` **26 项全通过**（2.1 秒），四处反向验证各自成立（见上表）。迁移门禁退出码 0，含新迁移的降级与升级往返。

两种形态都"全绿"时，光看结果分不出哪一面被验过，而"`E2E_WEBHOOK` 没传进 worker、静默走了关闭分支"正是这条用例最可能的假绿。两道防线：

1. 用例把实际走的分支写进 `testInfo.annotations`，报告里能看到 `enabled: 写路径` / `disabled: 关闭姿态`。
2. 用**审计表**做决定性对照（只追加，删除端点不会删审计）：`E2E_WEBHOOK=1` 那轮产生 `webhook.endpoint_created` / `_status_changed` / `_rotated` / `_deleted` 各 1 条、端点表删除后为 0 行；默认形态那轮 webhook 审计行为 **0**。两次运行的差别就是"写路径确实被执行过"的证据。

**界面覆盖的边界**（`frontend/src/components/WebhooksPanel.vue` + `api/webhooks.ts`，接后端八个端点）：

1. **能力关闭时说清原因**：`meta.enabled === false` 时不给建端点表单，而是显式说明关闭原因与配置项名字。后端也会返 409，但让用户点一次再看报错是把设计决定藏起来。
2. **签名密钥只显示一次**：创建与轮换之后把明文摊在界面上并说明"离开即取不回"，列表里只有末 6 位指纹。类型上把 `secret` 标成可选，正是为了逼调用方处理"这次没拿到"。
3. **投递明细只到失败类别**：`last_error`/`error_kind` 那一列展示的是类别，界面底部写明"接收方响应正文不入库"。
4. **角色可见性**：页签对 `reviewer` 隐藏（后端读面 `READ_ROLES` 也不含它）；写操作只对 owner/admin 显示。**藏入口不是权限控制**，真正的把关在后端 `require_roles`。

判定方式与结果：`npm run build`（含 `vue-tsc --noEmit`）通过；`npx playwright test` → **15/15 通过（47.1 秒）**。反向验证：把"能力关闭"那一段从组件里删掉后**该用例红、其余 14 条绿**，证明这条判据测的是那段说明而不是恒真。

**写路径已由 M15 补上**（见上面的表格与环境开关说明）：`E2E_WEBHOOK=1` 那一轮覆盖建端点、密钥只显示一次、暂停、轮换、删除五条，并用审计表做决定性对照。所以本节原先那句"写路径尚未"已不成立。

**仍未覆盖**：投递明细的状态筛选（需要真实产生投递行，端到端环境没有对端可投）、真实对端的送达证明、部署侧密钥流程（业主决定）。

### 5.31 维护轮 M16：检索后端可替换性（NFR-004，2026-10-10）

`NFR-004` 声明的四类适配器里，**只有搜索后端没有抽象**——M2 交付 `TC-FUNC-060` 时把这条现状写成了断言（`test_search_backend_has_no_factory_and_that_is_recorded`）。本轮把它补上。设计评审产出在 `docs/22`（DOC-DD-022），含取舍表、契约、依赖方向与风险。

| 用例 ID | 关联需求 | 判据 | 反向（怎么证明它不是恒过） |
|---|---|---|---|
| TC-FUNC-061 | NFR-004 | 默认后端是 `SqlSearchBackend`；未知 `SEARCH_BACKEND` 抛 `RuntimeError`（不静默退回默认实现） | 把未知值分支改成静默退回 → 2 条红 |
| TC-FUNC-062 | NFR-004 | **经工厂替换后 HTTP `/search` 走假实现**，且假实现拿到的是**已转义**的模式（`%` → `\%`） | service 改回直连 `repository.search_entries` → 2 条红 |
| TC-FUNC-063 | NFR-004 | **写入侧同样经契约**：上传→处理链路触发 `reindex`，入参含租户、文件名与字段值 dict | `reindex_version` 改回直连 `SqlSearchBackend()` → 1 条红 |
| TC-FUNC-064 | NFR-004 | 契约把 `reindex` 与 `query` 放在同一个 ABC 里，**缺任一侧都实例化不了** | 去掉 `query` 的 `@abstractmethod` → 1 条红 |
| TC-FUNC-065 | NFR-004 | 行为不变：默认后端写出的索引行仍是 filename/text/field 三类；重建索引仍幂等（行数不随重跑增长）；`now` 参数真的用在 `updated_at` 上 | 现有 `tests/test_search.py` 5 条是首要判据 |

**四条边界决策**（`docs/22 §2`、`§3`）：

1. **契约收"已转义的 pattern"，不收原始查询词**。转义属**查询语义**：换成词元匹配的后端时 `%` 不再是通配符，规则完全不同。放进契约会让每个后端各写一份转义，service 就失去了"查询词合法性"的唯一权威。反向验证里专门有一条断言 `\%` 出现在后端入参里。
2. **两侧应成对替换**，所以放进同一个 ABC。只换查询而保留写侧会让索引行与查询语义错位（换成词元匹配、索引仍整段存 → 永远零命中），而两侧各自的用例都可能是绿的。
3. **每次调用读配置**，不像流水线那样构造时绑定。`docs/06 §5.25` 记过那个陷阱，检索是短路径、没有性能理由提前绑定。
4. **不引外部依赖、不改查询语义、不加迁移**。真实分词与全文索引要容量数据支撑（`docs/15 §10`、`docs/08` R-010），属另一轮。

**一处被反向验证照出来的用例弱点**：第一版的 `test_both_sides_are_required_by_the_contract` 只断言了"只实现 `query` 会失败"，而那**只证明 `reindex` 是抽象的**——去掉 `query` 的 `@abstractmethod` 后它照样通过（negative-4 实测 `failures=0`）。补齐两侧断言后 negative-4 才正确变红。这条记在这里，因为"断言看起来在测双向、实际只测了一向"是很难从代码上看出来的失效方式。

判定方式与结果：`tests/test_search_backend.py` **11 项全通过**；现有 `tests/test_search.py` 5 项全通过（行为不变的首要判据）。四处反向验证各自成立（见上表）。四条门禁：迁移门禁退出码 0；基础套件在 PostgreSQL 与 SQLite 各 **416 项**、0 失败 0 错误 0 跳过；`-m s3` 8 项、`-m broker` 4 项。
