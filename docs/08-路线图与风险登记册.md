## 3. 风险登记

| ID | 风险 | 概率/影响 | 缓解与触发信号 |
|---|---|---|---|
| R-001 | 多租户隔离遗漏导致客户数据泄露 | 中/极高 | 集中租户上下文、DB 约束/RLS、跨租户负向测试；任何越权缺陷触发阻断发布 |
| R-002 | 文件恶意内容或解析资源耗尽 | 中/高 | 签名检测、隔离处理、CPU/内存/页数限制、扫描策略；异常峰值/Worker 崩溃触发告警 |
| R-003 | 外部 OCR/LLM 使用导致隐私或数据驻留不符 | 中/高 | 供应商审查、用户告知/配置、脱敏策略、禁止训练承诺确认；未审查前禁用生产敏感数据 |
| R-004 | 内存任务模式无法支持重启/并发 | 高/高 | 首期替换持久化任务与队列；服务重启导致任务丢失视为发布阻断 |
| R-005 | OCR/LLM 质量不稳定导致错误数据进入业务流程 | 高/高 | 字段置信度、原文定位、人工复核、评估集和错误更正追踪 |
| R-006 | 任务重复投递或失败重试产生重复导出/审批 | 中/高 | 幂等键、唯一约束、outbox/事件状态、重复投递测试 |
| R-007 | 文件删除未覆盖派生文本、索引或备份 | 中/高 | 定义生命周期清单、异步删除状态、定期清理核对及备份保留规则 |
| R-008 | 范围包含提取、搜索、自动化、集成导致首期过大 | 高/中 | 分阶段路线；V1 限定手动上传核心闭环和基础检索 |
| R-009 | Vue 构建与后端托管/反向代理发布配置不一致 | 低/中 | 后端现优先托管已构建的 `frontend/dist`；仍需将构建步骤纳入部署并完成发布流程验证 |
| R-010 | 缺少容量与SLA目标使选型/成本不可控 | 高/高 | G0 明确预期租户数、文件量、峰值并发、延时和恢复目标 |
| R-011 | 邀请令牌无投递渠道，管理员需人工转交，可能被转到错误的人或经第三方通道泄露 | 中/中 | 令牌短期有效且仅一次使用；接入官方投递渠道前，客户文档需说明人工转交责任；异常接受记录进审计事件 |
| R-012 | 成员与邀请管理只有后端能力，无前端界面，运营只能直接调 API | 高/低 | 阶段 B 收尾后优先排入界面；在界面就绪前不得宣称客户可自助管理成员。**当前状态**：复核台（队列/修订/确认/退回/原文预览）与文档库（检索/浏览/标签/保留状态）已在 `frontend/src/components/{ReviewPanel,LibraryPanel}.vue` 交付并经浏览器实操验证（登录 → 保存修订 v2 → 确认 → 检索命中 → 标签保存）；模板管理、成员与邀请、事件规则仍只有 API |
| R-014 | `domain_events.published_at` 被阶段 E 的自动化消费复用，语义从「已对外投递」变成「已被规则消费」 | 中/中 | 阶段 F 的 Webhook 必须另建投递状态列与独立游标，不得复用该列；上线前用运行日志核对历史事件可见性 |
| R-013 | `processing_jobs.snapshot` 与 `extraction_results` 双真相，读路径未完全切换 | 中/中 | 阶段 D 已让两者同事务写入；`/results`、`/export` 以规范化值为源。**G4（2026-10-03）已把最后两个快照消费者 `/result`、`/excel` 也切到规范化结果**（与 `/export` 共用同一读取函数，仅在任务没有任何规范化行时回落历史快照），`/excel` 同时不再复用 `excel_path` 缓存文件。列本身仍保留（`JobRepository.get()` 还需用快照重建 `Job` 的字段定义、进度与告警），退役要在"重建路径脱离快照 + 记录迁移前备份"之后单独一个变更完成 |
| R-015 | 开发环境缺少 Docker 且可用磁盘远小于 1TB 目标，无法直接运行 Compose 或存放真实规模数据 | 低/中 | **容器部分已消解（2026-10-03 G1）**：WSL Ubuntu-24.04 内 Docker Engine + Compose 可用，本机依赖栈与迁移/恢复脚本已跑通。剩余是数据规模：1TB 真实数据集仍超出本机磁盘，容量结论只能来自合成压测与外部基准，不得外推为生产容量。G6 已把「合成压测」做成可重复脚本（本轮留下 22.1 MB 对象与 30.3 MB 数据库），外部基准与真实 OCR 耗时仍缺 |
| R-016 | 同一份代码在 SQLite 与 PostgreSQL 上行为不一致，带病进入部署 | 中/高 | G1 已消灭两类已知差异（NUL 拒写、审计游标 `+00:00` 被查询串解成空格），并让全量用例在两种方言下通过；`TEST_DATABASE_URL` 为 PG 门禁入口；破坏性脚本统一走 `app/db.assert_disposable_database()` 命名守卫。残留项见 `docs/17 §6`：机器提取写 `extraction_results.values` 未剔除 NUL、其余端点时间戳格式仍随方言变化、运营视图 dict 键序依赖无 `ORDER BY` 的返回顺序（SQLite 按插入序、PG 不保证）。G4 切换规范化读路径前必须收口，并把 PG 全量测试作为合并门禁 |
| R-017 | 队列模式与进程内执行并存，部署配错会静默降回单进程 | 中/中 | `BROKER_URL` 为空即进程内执行（开发与用例基线），非空时 API 不再执行、必须由 `app.dispatcher` + `app.worker` 承载。`app/dispatcher.py` 与 `app/worker.py` 在未配置 broker 时直接退出并说明原因；部署清单需在就绪检查中确认"队列模式已启用且有 Worker 在消费"，否则任务会停在 queued 无人处理。该就绪判定已在 G5 第一部分落地：`/readyz` 的 `queue` 段用 `passive` 队列查询取真实消费者数，队列模式下"问不到 broker"或"有积压而消费者为 0"都返回 503，没积压时 0 消费者仍算就绪（探针不会创建队列，写错队列名不会被掩盖）。 |
| R-018 | 对象数据的可恢复备份缺少生产级保障，默认后端仍是本机目录 | 中/中 | **演练已交付并有证据（2026-10-03，G7）**：`scripts/object_store_backup_drill.py` 在源容器 `pause` 期间把 `object-store-data` 卷复制成冷副本，挂到独立端口的 SeaweedFS 实例后按 S3 语义核对键集合、对象大小与 SHA-256 内容，并用三类破坏注入（少对象、等长改写 1 字节、截断 1 字节）分别证明键集合、尺寸、摘要三道检查各自有效（TC-REC-013，`DRILL RESULT: PASS`）。 11 次运行里 10 次 `PASS`、1 次在「重建副本复跑」阶段失败（那次的输出被过滤掉，没留下失败签名，根因未知）。 所以残余风险从「没做过演练」变成「冷副本不保证每次可恢复」，收口方式是备份后强制恢复核对（`docs/19 §3.3`）。仍待处理：默认后端仍是 `local`，切换顺序见 G-DEC-10（先回填并确认退出码 0，再改 `STORAGE_BACKEND=s3`）；本机单节点演练**不等于**跨机灾备、增量备份或生产恢复时间，备份周期与 RPO/RTO 属 G-DEC-05 的业务决策 |

## 4. 待确认决策

1. 目标市场/地域与数据驻留要求、适用隐私法规和合同义务。
2. 首期登录体验：邮箱密码、邀请制、SSO；是否提供租户自助注册。
3. 首期格式、文件大小/页数、语言、批次；长期规模目标暂记为 100 个租户、约 1TB 文件、最多 100 个并发处理任务，待定义测量口径与验收阈值。
4. 身份、数据库、队列、对象存储、密钥和监控的部署/供应商约束。
5. 文档保留、软删除、彻底删除、备份清理和客户导出政策；当前设计不得默认清除真实数据。
6. 计费/配额是否需要首期实现；租户套餐边界。
7. 文档检索是精确字段/全文检索，还是还需要语义搜索/问答。
8. 工作流首期是否只做通知，或必须含审批与外部动作。
9. 处理结果需不需要页码/坐标级来源定位和置信度门槛。
10. 目标 SLA、RPO/RTO、并发持续时间、响应时间和可接受模型成本；本地阶段先测量，不设置生产承诺。
