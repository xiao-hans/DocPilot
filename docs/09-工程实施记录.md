  - **P1 状态机漏弯**：`rejected` 可直接再确认，且退回不清 `confirmed_by/at`，读模型出现"已退回却带确认人"。现 `rejected → confirmed` 禁止（必须先修订），退回同时清空确认信息。

  - **P1 治理字段越权**：`retention_status` 与业务标签同权限放开。现仅 `admin`/`owner` 可改保留状态，`member` 仍可改标签，`reviewer` 对文档库写接口整体 403。

## 5. 本地开发操作

安装 `requirements.txt` 中的依赖后，开发环境启动时会自动应用待执行的 Alembic 迁移。初始化平台管理员前，在 `.env` 设置高熵 `BOOTSTRAP_TOKEN`，并启动 API；随后通过前端“首次部署？初始化平台”操作，或向 `POST /api/v1/auth/bootstrap` 发送 `X-Bootstrap-Token` 请求头以及 `email`、至少 12 位 `password`、`tenant_name` 字段。该入口成功一次后即不可再次使用。

生产环境必须设置 `APP_ENV=production`，配置 PostgreSQL `DATABASE_URL`，先运行 `alembic upgrade head`，再启动服务；此时旧的无认证 `/api/jobs` 接口返回 404，未构建 Vue 前端则返回 503。会话 Cookie 默认为 Secure，HTTPS 是生产部署前提。

本机 PostgreSQL 依赖栈（阶段 G1，2026-10-03 起可用）：`docker compose up -d` 启动 `postgres:17-alpine`，端口只绑 `127.0.0.1:5432`，数据在命名卷 `docpilot-dev_postgres-data`。凭据取自未提交的 `.env`（见 `.env.example`），首次初始化数据卷时 `deploy/postgres/init-databases.sh` 会额外创建 `docpilot_test`。`docker` CLI 只存在于本机 WSL 的 Ubuntu-24.04 内，Windows 侧没有，因此 Compose 与两个脚本都要在 WSL 里执行：`cd /mnt/d/workspace/DocPilot && bash scripts/backup_restore_drill.sh docpilot_test`。迁移门禁可在 Windows 侧直接跑（只需网络连通）：`.venv/Scripts/python.exe scripts/migration_gate.py`。容器可能被 WSL 空闲回收（实测一次门禁因此连接超时），跑门禁或演练前先 `docker compose ps` 确认 `healthy`。

队列形态（阶段 G2）需要三个进程：API、`python -m app.dispatcher`（投递 + 超时回收 + 投递回收）、`python -m app.worker`（领租约执行）。`BROKER_URL` 为空时后两者会直接退出并说明原因，任务由 API 进程内执行；一旦设置，API 就不再自己跑任务，必须保证有 Worker 在消费，否则任务停在 `queued`（风险 R-017）。测试选择也据此分开：基础套件用 `pytest -m "not broker"`，真实 broker 用例用 `pytest -m broker` 并设置 `BROKER_URL`；把整套用例跑在队列模式下会因"没有 Worker"大面积失败，不是产品缺陷。

本机依赖与容器的两个事实：`pika` 未同步到 `pypi.tuna.tsinghua.edu.cn` 镜像（该机器 pip 默认源），需 `pip install "pika>=1.3,<2.0" -i https://pypi.org/simple`；WSL 会在空闲后被回收，容器随之停止、端口在重启窗口内拒绝连接（实测导致一次门禁连接超时），长任务期间保留一个 `wsl -d Ubuntu-24.04 -- tail -f /dev/null` 会话，或先 `docker compose ps` 确认 `healthy`。

测试执行：`python -m pytest`（259 个用例，含租户隔离、认证与授权边界、处理可靠性、复核与文档库）。测试进程会把上传/输出目录重定向到临时目录，不会读写本地开发数据。默认使用一次性 SQLite 文件；`.env` 中设置 `TEST_DATABASE_URL` 时整轮改用 PostgreSQL，并在会话开始前重置该库的 `public` schema——脚本拒绝指向名称不含 `test` 的库，以免误清开发数据。

## 10. 阶段 G2 交付记录（2026-10-03）

队列与派发层偏离原设计：改用 **RabbitMQ + pika 自建薄层**，理由、备选方案与影响见 `docs/adr/0004`（Celery 的 prefork 池不支持 Windows，而本项目的验证入口在 Windows 侧 `.venv`；§4 要求的租约/尝试/回收本身是数据库权威的独立状态机，与 Celery 自带状态机竞争）。

数据模型：新增 `job_dispatches`（一次执行尝试一行，承载发布状态与执行租约），迁移 `f2a6c81b4d73`。业务状态权威仍是 `processing_jobs` 与 `job_attempts`；消息只携带 `dispatch_id/job_id/tenant_id/attempt_no/queue` 五个字段，不含文件正文、令牌或绝对路径。

组件：

- `app/contexts/processing/dispatch.py`：派发记录状态机，每一步都是条件更新（`ready → published → claimed → settled`）。
- `app/contexts/processing/dispatcher.py` + `app/dispatcher.py`：领取 `ready` 记录、发布持久消息、拿到 publisher confirm 才推进；每轮先跑超时回收与投递回收。
- `app/contexts/processing/broker.py`：pika 连接与通道、confirm、prefetch、手动 ack、跨线程安全的 `stop()`。
- `app/worker.py`：独立进程入口，领取租约 → 后台线程续租 → 复用现有处理链路 → 结果与租约同事务收口 → 手动 ack。

关键语义：租约令牌随机且续租必须匹配令牌；被接管的旧 Worker 带过期租约收口时条件更新不命中，`finish_attempt()` 整体回滚并返回 `False`，因此不会覆盖新尝试；未拿到确认的发布留在 `ready`；任务停留在 `queued` 且派发行长时间无人认领时回炉重投，已 `settled` 的槽位会被重新打开而不是静默卡死。

配置：`BROKER_URL`（空 = 进程内执行，保持既有开发与用例基线）、`QUEUE_NAME`、`WORKER_PREFETCH`、`JOB_LEASE_SECONDS`、`DISPATCH_BATCH_SIZE`、`DISPATCH_POLL_SECONDS`、`DISPATCH_REPUBLISH_SECONDS`。测试因此分两轮：基础套件 `pytest -m "not broker"`（不设 `BROKER_URL`），真实 broker 套件 `pytest -m broker`。

- 真实 broker 套件 `pytest -m broker`：PostgreSQL 3 项通过（5.34 秒）、SQLite 3 项通过（5.52 秒）。
- `scripts/migration_gate.py`：退出码 0，含 `job_dispatches` 的空库升级、往返与 `alembic check` 无漂移。

## 11. 阶段 G3 交付记录（2026-10-03）

范围：把上传对象的写入与解析读取统一到一个 `ObjectStorage` 契约之后，本机 S3 模拟器可以替代本机目录，且失败时不留下无人认领的对象。默认后端仍是 `local`，因此本轮没有改变任何既有开发基线行为。

契约（`app/services/object_storage.py`）：`put` / `open_read` / `read_bytes` / `stat` / `delete` / `delete_prefix` / `list_keys` / `local_path`，两种实现 `LocalStorage` 与 `S3Storage`（boto3）。`stat` 只返回存在性与字节数；`local_path` 是给解析器（PyMuPDF、RapidOCR 只接受文件路径）的唯一出口，对象存储实现落临时文件、退出即删，该路径禁止进数据库、日志或响应。非"对象不存在"的后端故障统一包成 `StorageError(RuntimeError)`，接口层的补偿分支不必依赖 botocore 的异常层次。

接线：

- 上传按 `{tenant_id}/{job_id}/{uuid}.ext` 生成对象键，客户端文件名不参与寻址（原始文件名单存在 `document_versions.original_filename`），任务快照不再携带本机绝对路径。
- 任一步失败都按**任务前缀**整体回收对象（`delete_prefix`），删除对象后逐级收回空目录；清理失败只记日志，不覆盖本次请求的真实原因，残留对象交给孤儿审计报出。
- 解析端从 `Path(finfo.path)` 改为 `with storage.local_path(finfo.storage_key)`；遗留的无租户 `/api/jobs` 仍按 `path` 读取，其退役属 G4。
- 后端与存储根目录改为运行时读 `app.config`：写入端与解析端必须看到同一个根，否则测试隔离了上传目录后 Worker 会去读一个不存在的位置（`tests/conftest.py` 的 `sandbox` 因此改 patch `app.config.UPLOAD_DIR`）。

依赖栈：`docker-compose.yml` 新增 `object-store`（`chrislusf/seaweedfs:4.22`，`server -s3 -dir=/data -ip=127.0.0.1 -ip.bind=0.0.0.0`，命名卷 `object-store-data`，健康检查，端口只发布到 `127.0.0.1:8333`）。4.22 的几处启动约束（没有 `-smdir`、不要传 `-logdir`、`-ip` 必须是可回连地址）与"走本机端点要让 `NO_PROXY` 覆盖 `127.0.0.1`"记入 `docs/17 §3`。

运维脚本（都不删真实数据）：

- `scripts/storage_orphan_audit.py`：比对"存储里的对象"与"`document_versions.storage_key`"，报出孤儿对象与断链记录，退出码 0/1。报告行只含 `tenant_id`/`job_id`/`version_id` 与对象键摘要（SHA-256 前 12 位），不含对象键与文件正文（`docs/17 §7`）。**只报告不删除**——彻底删除政策 G-DEC-03 未批准。
- `scripts/storage_backfill_to_object_store.py`（G-DEC-07 决定的工具）：以 `document_versions.checksum` 为权威值逐条复制、上传后读回比对摘要、目标已存在且校验通过即跳过、只写不删源文件与记录，因此可中断重跑；`STORAGE_BACKEND=local` 时直接拒绝运行（源与目标同处一地）。切换顺序记入 G-DEC-10。

配置：`STORAGE_BACKEND`（默认 `local`）、`S3_ENDPOINT_URL`、`S3_BUCKET`、`S3_REGION`、`S3_ACCESS_KEY`、`S3_SECRET_KEY`、`S3_KEY_PREFIX`（默认 `docpilot`）。测试因此分三层：基础套件 `pytest -m "not broker and not s3"`、真实 S3 套件 `pytest -m s3`、真实 broker 套件 `pytest -m broker`。

新增用例：`tests/test_object_storage.py`（本地实现的完整契约、越界键拒绝、空目录回收、清理失败向上暴露、S3 错误映射离线用例、孤儿审计三条路径）与 `tests/test_object_storage_s3.py`（真实端点上的同一套契约、临时文件回收、任务经 S3 端到端成功、回填端到端含"目标被篡改后不得算作已迁移"的负向）。

  1. 切换前审计 → 对象数=0、记录数=1，报出 1 条断链记录，退出码 **1**；
  2. 回填 → 总数=1 新复制=1 失败=0，退出码 0；
  3. 再审计 → 对象数=1、记录数=1，输出"一致"，退出码 0；
  4. 重跑回填 → 新复制=0、已在校验通过=1，退出码 0（幂等）。
  审计退出码必须由不带管道的命令观测：`... | tail -3` 会把退出码变成 `tail` 的 0，第一轮记录里就出现过这种误读。

## 12. 阶段 G4 交付记录（2026-10-03）

范围只做两件事：把最后两个读快照的结果端点切到规范化表，以及收口 G1 留下的三条方言残留项（NUL、时间戳形状、无 `ORDER BY` 的聚合装配）。没有新增功能面，也没有移除 `processing_jobs.snapshot` 列。

读路径：`/result` 与 `/excel` 过去直接返回 `job.result`（来自快照），因此人工修订之后它们仍给出机器值——这正是 R-013 说的双真相。现在两个端点与 `/export` 共用 `_current_result()`：以 `extraction_results` 的当前值（含修订）为源，只有当任务没有任何规范化行时才回落快照（阶段 D 之前的历史任务，`test_legacy_job_snapshot_remains_readable_without_document_rows` 钉住这条兼容路径）。`/excel` 顺带不再复用 `excel_path` 缓存的旧文件：缓存会让修订之后的下载继续输出旧内容，与本次要消灭的不一致同源；文件名不变，下载链接不受影响。

方言残留：

- NUL 清洗从两处散落的 `replace("\x00","")` 收敛到 `app/services/text_safety.py`（`without_nul` + `clean_payload`），并补上两处真正会收到脏数据的入口：解析原文（`document_texts.text`，清洗早于 `char_count` 计算，保证记录字符数与实际存储一致）与机器提取值/告警（`extraction_results`）。
- 响应时间戳全部经新增的 `app/services/timestamps.iso_utc()` 输出 `...Z`：SQLite 返回 naive、PostgreSQL 返回 tz-aware，过去同一端点两种形状，且 `+00:00` 回塞查询串会被解成空格。改成 `Z` 对前端无影响（两处展示都按 `slice(0,10)`/`slice(0,16)` 取前缀）。覆盖 audit、members/invitations、jobs、results/revisions、documents、templates、processing attempts、automation rules/runs/notifications。
- 运营聚合 `_grouped`/`_by_tenant` 显式 `order_by(value.is_(None), value)`：先把 `IS NULL` 排在一侧，避免 SQLite（ASC 时 NULL 在前）与 PG（ASC 时 NULL 在后）的默认差异，再比值。

防护写成结构约束而不只是行为断言：`tests/test_dialect_residue.py` 里一条用例对 `app/` 做 AST 扫描，出现手写 `.isoformat()` 即失败（只豁免 `timestamps.py` 自身与把 `date` 格式化成 `YYYY-MM-DD` 的提取层）；另一条断言聚合 SQL 真的带 `ORDER BY`。每条新防护都做过反向验证——撤掉对应修复后确认它会失败。**一处例外如实记下**：`test_operations_aggregates_keep_a_stable_key_order` 在撤掉 `ORDER BY` 后仍然通过，因为 PG 在该数据集上走了索引扫描恰好返回有序行；它的价值是钉住响应形状，判别力来自那条 SQL 结构断言。

快照列未删除：`JobRepository.get()` 仍从快照重建 `Job` 的字段定义、进度、告警、`excel_path` 与遗留 `path`。删列需要先让这条重建路径脱离快照，并按"记录迁移前备份 → 单独一个变更删列"推进（`docs/17 §6`）。遗留的无租户 `/api/jobs` 仍以本机绝对路径读文件，与快照列一起退役。
