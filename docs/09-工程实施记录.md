- 评审（陌生读者子代理 + 安全子代理 + 自查）发现并修复：
  - **P0 乐观并发只在前台**：修订与状态变更先读后写，两个复核员同时保存会互相覆盖，且审计写两遍。现统一为数据库层条件更新（`WHERE id AND tenant_id AND revision_no=expected AND state ∈ 前态集合` 判 rowcount），修订链追加由 `UNIQUE(result_id, revision_no)` 兜底，`IntegrityError` 一律回滚转 409。并发用例证明恰好一个 200、一个 409。
  - **P0 快照与规范化结果分两次提交**：崩溃会留下"快照有这一行、`extraction_results` 没有"的混合读视图，导出因此半新半旧。管线改为只暂存，由 `JobRepository.save(after=…)` 与快照同事务落库；写入失败时回暂存、下一次快照写入重试。注入一次提交失败的用例断言两侧行集一致。
  - **P0 标签索引漂移**：`DocumentLabel.tenant_id` 上的 `index=True` 与迁移里显式命名的两个索引不一致，`alembic check` 报"要删索引"。改为模型显式声明同名 `Index`，迁移往返与 `alembic check` 复归干净。
  - **P0 复合外键自相矛盾**：`fk_result_template_version` 用 `SET NULL` 去置空一个 NOT NULL 的 `tenant_id`，且租户侧 `CASCADE` 与"被引用版本 RESTRICT"冲突。现版本引用改 `RESTRICT`、`extraction_results.tenant_id` 不带级联。
  - **P1 状态机漏弯**：`rejected` 可直接再确认，且退回不清 `confirmed_by/at`，读模型出现"已退回却带确认人"。现 `rejected → confirmed` 禁止（必须先修订），退回同时清空确认信息。
  - **P1 修订静默改值**：`{name: str(values.get(name, ""))}` 会把缺失字段清成空串、把数字强转成字符串、把嵌套结构字符串化。现未知键 422、缺字段 422（提示缺哪几个）、非标量 422，标量按原类型保存。
  - **P1 两种导出不同源**：XLSX 与 CSV 各自实现转义，XLSX 遇 XML 非法控制字符直接报错而 CSV 原样写出；且 XLSX 的 XML 解析会把 CRLF 折成 LF，两侧同一单元格内容并不相同。现两格式共用 `cell_value/cell_text`（换行统一到 LF、非法控制字符替换为空格、`=+-@` 前缀单引号、32767 上限截断），数字在 XLSX 保持数字、CSV 写其文本形式，用例逐字符比对。

## 5. 本地开发操作

安装 `requirements.txt` 中的依赖后，开发环境启动时会自动应用待执行的 Alembic 迁移。初始化平台管理员前，在 `.env` 设置高熵 `BOOTSTRAP_TOKEN`，并启动 API；随后通过前端“首次部署？初始化平台”操作，或向 `POST /api/v1/auth/bootstrap` 发送 `X-Bootstrap-Token` 请求头以及 `email`、至少 12 位 `password`、`tenant_name` 字段。该入口成功一次后即不可再次使用。

生产环境必须设置 `APP_ENV=production`，配置 PostgreSQL `DATABASE_URL`，先运行 `alembic upgrade head`，再启动服务；此时旧的无认证 `/api/jobs` 接口返回 404，未构建 Vue 前端则返回 503。会话 Cookie 默认为 Secure，HTTPS 是生产部署前提。

本机 PostgreSQL 依赖栈（阶段 G1，2026-10-03 起可用）：`docker compose up -d` 启动 `postgres:17-alpine`，端口只绑 `127.0.0.1:5432`，数据在命名卷 `docpilot-dev_postgres-data`。凭据取自未提交的 `.env`（见 `.env.example`），首次初始化数据卷时 `deploy/postgres/init-databases.sh` 会额外创建 `docpilot_test`。`docker` CLI 只存在于本机 WSL 的 Ubuntu-24.04 内，Windows 侧没有，因此 Compose 与两个脚本都要在 WSL 里执行：`cd /mnt/d/workspace/DocPilot && bash scripts/backup_restore_drill.sh docpilot_test`。迁移门禁可在 Windows 侧直接跑（只需网络连通）：`.venv/Scripts/python.exe scripts/migration_gate.py`。容器可能被 WSL 空闲回收（实测一次门禁因此连接超时），跑门禁或演练前先 `docker compose ps` 确认 `healthy`。

队列形态（阶段 G2）需要三个进程：API、`python -m app.dispatcher`（投递 + 超时回收 + 投递回收）、`python -m app.worker`（领租约执行）。`BROKER_URL` 为空时后两者会直接退出并说明原因，任务由 API 进程内执行；一旦设置，API 就不再自己跑任务，必须保证有 Worker 在消费，否则任务停在 `queued`（风险 R-017）。测试选择也据此分开：基础套件用 `pytest -m "not broker"`，真实 broker 用例用 `pytest -m broker` 并设置 `BROKER_URL`；把整套用例跑在队列模式下会因"没有 Worker"大面积失败，不是产品缺陷。

本机依赖与容器的两个事实：`pika` 未同步到 `pypi.tuna.tsinghua.edu.cn` 镜像（该机器 pip 默认源），需 `pip install "pika>=1.3,<2.0" -i https://pypi.org/simple`；WSL 会在空闲后被回收，容器随之停止、端口在重启窗口内拒绝连接（实测导致一次门禁连接超时），长任务期间保留一个 `wsl -d Ubuntu-24.04 -- tail -f /dev/null` 会话，或先 `docker compose ps` 确认 `healthy`。

测试执行：`python -m pytest`（259 个用例，含租户隔离、认证与授权边界、处理可靠性、复核与文档库）。测试进程会把上传/输出目录重定向到临时目录，不会读写本地开发数据。默认使用一次性 SQLite 文件；`.env` 中设置 `TEST_DATABASE_URL` 时整轮改用 PostgreSQL，并在会话开始前重置该库的 `public` schema——脚本拒绝指向名称不含 `test` 的库，以免误清开发数据。

## 10. 阶段 G2 交付记录（2026-10-03）

队列与派发层偏离原设计：改用 **RabbitMQ + pika 自建薄层**，理由、备选方案与影响见 `docs/adr/0004`（Celery 的 prefork 池不支持 Windows，而本项目的验证入口在 Windows 侧 `.venv`；§4 要求的租约/尝试/回收本身是数据库权威的独立状态机，与 Celery 自带状态机竞争）。

数据模型：新增 `job_dispatches`（一次执行尝试一行，承载发布状态与执行租约），迁移 `f2a6c81b4d73`。业务状态权威仍是 `processing_jobs` 与 `job_attempts`；消息只携带 `dispatch_id/job_id/tenant_id/attempt_no/queue` 五个字段，不含文件正文、令牌或绝对路径。

组件：

- `app/contexts/processing/dispatch.py`：派发记录状态机，每一步都是条件更新（`ready → published → claimed → settled`）。
- `app/contexts/processing/dispatcher.py` + `app/dispatcher.py`：领取 `ready` 记录、发布持久消息、拿到 publisher confirm 才推进；每轮先跑超时回收与投递回收。
- `app/contexts/processing/broker.py`：pika 连接与通道、confirm、prefetch、手动 ack、跨线程安全的 `stop()`。
- `app/worker.py`：独立进程入口，领取租约 → 后台线程续租 → 复用现有处理链路 → 结果与租约同事务收口 → 手动 ack。

关键语义：租约令牌随机且续租必须匹配令牌；被接管的旧 Worker 带过期租约收口时条件更新不命中，`finish_attempt()` 整体回滚并返回 `False`，因此不会覆盖新尝试；未拿到确认的发布留在 `ready`；任务停留在 `queued` 且派发行长时间无人认领时回炉重投，已 `settled` 的槽位会被重新打开而不是静默卡死。

配置：`BROKER_URL`（空 = 进程内执行，保持既有开发与用例基线）、`QUEUE_NAME`、`WORKER_PREFETCH`、`JOB_LEASE_SECONDS`、`DISPATCH_BATCH_SIZE`、`DISPATCH_POLL_SECONDS`、`DISPATCH_REPUBLISH_SECONDS`。测试因此分两轮：基础套件 `pytest -m "not broker"`（不设 `BROKER_URL`），真实 broker 套件 `pytest -m broker`。

- 真实 broker 套件 `pytest -m broker`：PostgreSQL 3 项通过（5.34 秒）、SQLite 3 项通过（5.52 秒）。
- `scripts/migration_gate.py`：退出码 0，含 `job_dispatches` 的空库升级、往返与 `alembic check` 无漂移。
- `scripts/backup_restore_drill.sh docpilot_test`：退出码 0。

## 11. 阶段 G3 交付记录（2026-10-03）

范围：把上传对象的写入与解析读取统一到一个 `ObjectStorage` 契约之后，本机 S3 模拟器可以替代本机目录，且失败时不留下无人认领的对象。默认后端仍是 `local`，因此本轮没有改变任何既有开发基线行为。

契约（`app/services/object_storage.py`）：`put` / `open_read` / `read_bytes` / `stat` / `delete` / `delete_prefix` / `list_keys` / `local_path`，两种实现 `LocalStorage` 与 `S3Storage`（boto3）。`stat` 只返回存在性与字节数；`local_path` 是给解析器（PyMuPDF、RapidOCR 只接受文件路径）的唯一出口，对象存储实现落临时文件、退出即删，该路径禁止进数据库、日志或响应。非"对象不存在"的后端故障统一包成 `StorageError(RuntimeError)`，接口层的补偿分支不必依赖 botocore 的异常层次。

接线：

- 上传按 `{tenant_id}/{job_id}/{uuid}.ext` 生成对象键，客户端文件名不参与寻址（原始文件名单存在 `document_versions.original_filename`），任务快照不再携带本机绝对路径。
- 任一步失败都按**任务前缀**整体回收对象（`delete_prefix`），删除对象后逐级收回空目录；清理失败只记日志，不覆盖本次请求的真实原因，残留对象交给孤儿审计报出。
- 解析端从 `Path(finfo.path)` 改为 `with storage.local_path(finfo.storage_key)`；遗留的无租户 `/api/jobs` 仍按 `path` 读取，其退役属 G4。
- 后端与存储根目录改为运行时读 `app.config`：写入端与解析端必须看到同一个根，否则测试隔离了上传目录后 Worker 会去读一个不存在的位置（`tests/conftest.py` 的 `sandbox` 因此改 patch `app.config.UPLOAD_DIR`）。

依赖栈：`docker-compose.yml` 新增 `object-store`（`chrislusf/seaweedfs:4.22`，`server -s3 -dir=/data -ip=127.0.0.1 -ip.bind=0.0.0.0`，命名卷 `object-store-data`，健康检查，端口只发布到 `127.0.0.1:8333`）。4.22 的几处启动约束（没有 `-smdir`、不要传 `-logdir`、`-ip` 必须是可回连地址）与"走本机端点要让 `NO_PROXY` 覆盖 `127.0.0.1`"记入 `docs/17 §3`。

运维脚本（都不删真实数据）：

- `scripts/storage_orphan_audit.py`：比对"存储里的对象"与"`document_versions.storage_key`"，报出孤儿对象与断链记录，退出码 0/1。报告行只含 `tenant_id`/`job_id`/`version_id` 与对象键摘要（SHA-256 前 12 位），不含对象键与文件正文（`docs/17 §7`）。**只报告不删除**——彻底删除政策 G-DEC-03 未批准。
- `scripts/storage_backfill_to_object_store.py`（G-DEC-07 决定的工具）：以 `document_versions.checksum` 为权威值逐条复制、上传后读回比对摘要、目标已存在且校验通过即跳过、只写不删源文件与记录，因此可中断重跑；`STORAGE_BACKEND=local` 时直接拒绝运行（源与目标同处一地）。切换顺序记入 G-DEC-10。

配置：`STORAGE_BACKEND`（默认 `local`）、`S3_ENDPOINT_URL`、`S3_BUCKET`、`S3_REGION`、`S3_ACCESS_KEY`、`S3_SECRET_KEY`、`S3_KEY_PREFIX`（默认 `docpilot`）。测试因此分三层：基础套件 `pytest -m "not broker and not s3"`、真实 S3 套件 `pytest -m s3`、真实 broker 套件 `pytest -m broker`。

新增用例：`tests/test_object_storage.py`（本地实现的完整契约、越界键拒绝、空目录回收、清理失败向上暴露、S3 错误映射离线用例、孤儿审计三条路径）与 `tests/test_object_storage_s3.py`（真实端点上的同一套契约、临时文件回收、任务经 S3 端到端成功、回填端到端含"目标被篡改后不得算作已迁移"的负向）。

## 15. 阶段 G6 交付记录：合成数据容量观测（2026-10-03）

目标不是"跑出一个吞吐数字"，而是把 `docs/17 §9` 的三条 TC-PERF 变成**可重复执行**的观测，并且让报告里的每个数字都能被下一个人复算。交付物是 `scripts/capacity_observation.py`（约 700 行，三段观测 + Markdown 报告生成）与它产出的 `docs/18-合成数据容量观测报告.md`。

三段观测都走真实链路，不抄近路：合成数据用与上传接口相同的顺序落库（对象写入 → `Job` → `Document`/`DocumentVersion` → 任务与派发意图同事务），并发调度用真实派发器与 8 个 `python -m app.worker` 子进程，导出走 `/export` 的同一个视图构造（快照重建 `Job` 后用 `extraction_results` 替换 `result`）。数据库受命名守卫保护：PG 必须是 `docpilot_test`；SQLite 的"库名"在 URL 里是完整路径、守卫正则不适用，脚本改用最强的构造性检查——文件必须位于本次运行新建的 `data/capacity/<run>/` 内且此前不存在。

本轮数字（详见 `docs/18`）：100 租户 / 1000 文档 / 1000 条规范化结果，1800 次读查询 0 失败、跨租户泄漏 0，读路径 P95 3.9–12.8 ms；100 个任务在消费者到位后 3.3 秒排空（1825.7 任务每分钟），调度延迟（发布确认→开始执行）P50 831 毫秒，终态与规范化结果 100% 同源；18.4 MB 大对象的分块流式读 RSS 变化 0.0 MB、整对象读 RSS +18.4 MB；深翻页 1011 份文档 15.3–18.7 ms；1000 行导出 XLSX 0.34 秒；磁盘留下观测目录 22.1 MB + 数据库 30.3 MB。

四条只有真跑才会撞上的教训：

- **夹具必须不可压缩**。第一版大对象用重复文本填充，deflate 把 21 页压到 9.5 KB，于是 18 MB 目标要写四万多页，观测脚本被自己的夹具拖死（90 秒还没生成完）。改成"首页发票文本 + 随机噪声图像页"后 18.4 MB 约 1 秒生成，形状也更接近真实扫描件。压测夹具的"体积"要按落盘后的字节算，不是按写进去的字符数算。
- **采样时机决定结论真假**。`read_bytes` 的内存测量第一版写作 `whole = len(storage.read_bytes(key))`，缓冲区在采样前就被释放，于是报出"整对象读 12.7 MB 只涨 0.0 MB"的假结论——而且看起来像是好消息。改成先持有对象、采样、再取长度之后，实测 +18.4 MB，与"整对象读必然线性增长"的代码事实一致。
- **一个指标名不能盖两件事**。从"派发行创建"起算的等待里混着任务创建循环（本轮 8.2 秒），从"发布确认"起算的才是调度延迟，两者差一个数量级；`queue_backlog()` 的 `oldest_pending_seconds` 更特殊，它按最后更新时间算年龄、投递成功就会刷新，量的是"最久没动作"而不是"最久排队"（对 `/readyz` 的卡住判据是对的，当排队指标会低估积压）。报告现在把三个口径分列。
- **顺序本身就是测量条件**。先造任务再起 Worker，队列等待会被 Worker 进程导入应用的冷启动吃掉；脚本改成先等消费者到位再造任务，冷启动单独测一项（5.2 秒）。

未做与不做：CPU 占用不报（观测进程、8 个 Worker 与数据库同机混跑，采样无法归因，硬凑一个数字比不报更容易误导）；真实 1TB 语料、真实 OCR/LLM 耗时、S3 后端下的同路径观测、多机与 broker 集群故障转移都未覆盖，报告里逐条列成"不得当作已验证"。**性能阈值仍未评审，因此 G6 只交付基线，不交付"支持 100 租户 / 1TB / 100 并发"这类结论，也不构成 SLA。**

评审后的三处修补（同一提交内 amend，全部带负向验证）：

- **[P1] 观测脚本的库名守卫太宽**。`app/db.assert_disposable_database()` 只要求名字形如 `*_test` / `test_*`，`staging_test` 这类库也能通过，而本脚本会 `DROP SCHEMA public CASCADE`。现在额外要求目标库名精确等于 `--expect-database`（默认 `docpilot_test`）。负向验证：`--expect-database other_test` 直接被拒，且拒绝前后 `docpilot_test` 里的 100 个租户 / 201 个任务一条不少。
- **[P2] 异常路径会泄漏 Worker 子进程**。Worker 只在正常收尾时被终止；等待、建任务或读库中途抛错，子进程会继续消费观测队列并往观测库写结果。现在整段观测包在 `try/finally` 里，`teardown()` 统一停派发线程、终止并回收每个子进程、关闭日志句柄（不关会在 Windows 上锁住日志文件）。负向验证：用 `--tenants 0` 强制在 Worker 已启动后抛 `ZeroDivisionError`，脚本按预期失败退出，事后系统里 `app.worker` 进程数为 0。
- **[P3] 用例数量记录不一致**。`docs/04` 与 `docs/07` 把当前状态写成 G1 时代的 259 项，而 G5/G6 门禁是 303 项。现在两处都写成"当前 303 项，并注明 G1 时是 259"；`docs/08`/`docs/09` 里明确归属 G1 的历史记录保留原数字。
- 顺带修掉一个自己造的读数错误：宽任务的 RSS 差值原本同时盖住"写 1000 份文档 + 记 1000 条结果"和"读导出行"，两次运行报出 7.5 MB 与 86.8 MB，看着像导出路径退化；拆成写入侧与读取侧两个指标后，本轮是 +6.8 MB 与 −0.5 MB。报告与 `docs/06 §5.16` 都按新口径重跑重述。

执行纪律：观测脚本与 pytest 都会重置 `docpilot_test`，二者不能并行；本轮顺序是「门禁 → 观测 → 修脚本 → 观测复跑 → 门禁复跑」。基础套件必须在**不设 `BROKER_URL`** 的 shell 里跑（见 §13 与 `docs/06 §5.15`）。

## 16. 阶段 G7 交付记录：对象卷备份恢复演练（2026-10-03）

交付：`scripts/object_store_backup_drill.py`（fail-closed，只对 127.0.0.1 端点、源容器名与卷名必须精确等于预期值才继续，只删本次自己创建的东西）。

流程与实测（2026-10-03，本机 Compose 依赖栈；连续跑两轮，退出码均 0）：

0. 起手的残留回收也是被测的一部分：故意植入一个占住 `127.0.0.1:18333` 的 `docpilot-object-restore-deadbeef` 容器与配套 `/tmp/docpilot-object-drill-deadbeef` 目录，演练在第 0 步报告并回收这两项，随后整轮仍然通过。这两个前缀由本脚本独占，留着它们会占住恢复端口，让下一次演练直接起不来。
1. 往源桶写 4 个体积跨度足够的探测对象（16 B / 4 KB / 1 MB / 5 MB），加上 1 个既有应用对象一起核对——只有一个 3 KB 文件时，撕裂的副本也可能碰巧比对通过。
2. `docker pause docpilot-object-store`，用一次性 alpine 容器把 `docpilot-dev_object-store-data` 卷复制成冷副本（2.3 / 3.5 秒），随后 `unpause`。
3. 副本挂到新容器 `docpilot-object-restore-<run>`，端口从 18333 起逐个试（不复用别人的端口）；就绪 23.7 / 27.5 秒。就绪的口径是"能把探测对象读出来且 SHA-256 命中"，不是"桶能 head"：只 head 时卷还没向 master 注册完，第一个大对象直接 `IncompleteRead`；只要求非空时曾拿到 0 字节响应。
4. 正向核对 5 个对象：缺 0、多 0、尺寸不符 0、摘要不符 0，探测对象 SHA-256 全部命中。
5. 三类破坏注入各证明一道检查（全部只作用于本次探测前缀下的对象）：删除 `block.bin` → 键集合抓到；`text.bin` **等长**改写 1 字节 → 只有摘要能抓到；`large.bin` 截断 1 字节 → 尺寸检查抓到。
6. 注入后重建副本复跑正向一致，说明第 5 步的抓取来自注入，不是校验器本身失真。
7. 收尾核对：恢复容器、副本目录、探测对象三类都在删除后重新查询确认为 0，源桶回到演练前状态。输出 `DRILL RESULT: PASS`；任一项不成立打印 FAIL 并以退出码 1 结束，门禁可以直接消费退出码而不必读最后一行。

发现并修掉的缺陷（首轮并不通过：当时判定打印 CHECK，且退出码仍是 0）：

- **[P1] 校验器只在尺寸相等时比摘要**。原 `compare()` 写作 `dst[key] == src.get(key) and digest(...) != digest(...)`，于是"整对象被换成一小段内容"（首轮注入把 5 MB 换成 17 字节）同时躲过尺寸与摘要两道检查，`missing`/`extra` 也不报——被改写的恢复副本会被判成"与源一致"。现在尺寸与摘要是两个独立判定，负向注入也从两个增加到三个，专门补上"等长改写"这一类只有摘要能发现的情形。**这条缺陷是负向用例抓出来的，不是评审读出来的**：它说明此前的演练脚本即便跑绿也不能证明恢复内容可信。
- **[P2] 核对基数会把别的运行的探测对象当成应用对象**。原本按本次 `DRILL_PREFIX` 过滤既有键，一次被中断的运行在源桶留下 4 个 `_drill-0c7f093a/` 对象，被计入"既有应用对象 5 个"（真实值是 1）。现在按 `/_drill-` 段过滤任何一次演练的残留，并在收尾账目里单独报告；这 4 个残留对象已按精确键名删除并核对为空。

- **[P3] 收尾只发命令不核对，"已回收"是没有证据的声称**。`cleanup()` 里的 `docker rm -f … || true` 会把失败连同"容器不存在"一起吞掉，而第 9 步无论如何都打印"恢复容器与副本目录已回收"。这正是本机出现过真实残留的原因：一个 `docpilot-object-restore-*` 容器活着占住 18333，下一轮恢复实例起不来，而上一轮的账面却写着"已回收"。现在三类产物（恢复容器、副本目录、探测对象）在删除后都重新查询确认，任一项仍在就计入 notes，并通过 `passed` 直接把判定打成 FAIL。

测量输入（不是结论）：卷副本 2.3–3.5 秒、恢复实例就绪 23.7–27.5 秒、端到端可核对约 26.0–31.1 秒。这是将来定 RPO/RTO 的输入，本机单节点冷副本不构成生产恢复时间；且这里的"恢复"只包含"副本可用并核对通过"，不含备份设施本身的调度与保留。

同期门禁：基础套件 `pytest -m "not broker and not s3"` 退出码 0（本轮只新增独立脚本与文档，未改动应用代码）。

仍不属于本阶段：生产备份设施与周期、增量备份、跨机灾备、多副本一致性、保留与彻底删除策略（G-DEC-03）、RPO/RTO 取值（G-DEC-05）。默认 `STORAGE_BACKEND` 仍是 `local`，切换顺序照 G-DEC-10。

可靠性统计（把交付后的重复运行也算进来）：修完上述缺陷后连续跑 11 次，10 次 `DRILL RESULT: PASS`、1 次在"重建副本复跑正向"阶段失败。那次失败的输出被我的 grep 过滤掉了，没留下失败签名，所以根因未知——这本身是一条要记的教训：**演练脚本必须自己把失败落盘**（`data/drill-*.txt` 那种临时重定向不算交付物）。

这条统计直接限制本节能签什么：能签的是"我们有能力发现某次备份不可恢复"（第 8 步正是干这个的，也确实抓到过一次），**不能签**"对象数据已有可恢复备份"。要让后者成立，备份流程必须自带恢复后的全量摘要核对，或者改用逻辑级对象复制 / SeaweedFS 原生复制——方案与代价见 `docs/19 §3.3`。

## 17. 阶段 G8 交付记录：Compose 形态端到端与派发租约竞态（2026-10-03）

为什么要做：G-DEC-12 记下的是 G5 的诚实代价——端到端跑在一次性本地进程（独立 SQLite、`BROKER_URL=''`、`STORAGE_BACKEND=local`），所以"核心 UI 流程可在 Compose 形态下端到端通过"这条一直没被证明。更重要的是：**进程内基线里派发器和 Worker 不会赛跑**，队列形态特有的那一类故障永远碰不到。

交付：`scripts/e2e_compose_env.py`（prepare / teardown）+ `frontend/tests/{global-setup,global-teardown,helpers}.ts` 与 `playwright.config.ts` 的 Compose 形态分支。`E2E_COMPOSE=1 npx playwright test` 跑在同一套 10 条用例上：PostgreSQL 一次性库 `docpilot_e2e_test`（名字必须精确相等才允许删）、RabbitMQ 本次专用队列 `docpilot-e2e-<run>`、SeaweedFS 前缀 `e2e-<run>/`，API / 派发器 / Worker 三个独立进程。

结果：**10/10 通过，1.4 分钟，`TEARDOWN RESULT: CLEAN`**。起步门槛不是 `/healthz` 而是 `/readyz` 并报出"队列已启用且 consumers ≥ 1"——只看 200 不够，因为没积压时 0 个消费者也算就绪（G-DEC-09 的口径），那样用例会在一条没人消费的队列上等结果。

这一轮抓到的缺陷（也是本轮真正的价值）：

- **[P1] 派发租约竞态：抢在发布确认之前到达的消息会被确认掉，任务永久停在 `queued`**。`Dispatcher.run_once` 是"先 `transport.publish()`、拿到 confirm 才 `mark_published()`"，而 `claim_lease` 只认 `status == 'published'`，`handle()` 领不到租约就返回 True（= 告诉传输层可以 ack）。于是跑得快的 Worker 在毫秒级窗口里把消息取走、确认掉、什么也没执行；行还停在 `published`，要等 `DISPATCH_REPUBLISH_SECONDS`（300 秒）才可能重投。现场证据：`docpilot.worker 未领到租约，跳过 dispatch_id=4d66c1bc…` 打在 22:27:03.514，派发器写同一行的轮次日志在 22:27:03.517。修法是把可领条件放宽为 `ready` 或 `published`——行早已提交且带齐 `(tenant, job, attempt_no)`，消息存在本身就是投递证据，条件更新仍是单一胜者，因此不引入重复执行。回归用例 `tests/test_queue_dispatch.py::test_worker_beating_publish_confirmation_still_executes`（假传输在 `publish()` 内同步调用 `handle()`）：负向验证过——把谓词改回只认 `published`，报 `assert 'queued' == 'succeeded'`。
- **[P2] 这条分支在日志里不留痕迹**。`handle()` 的跳过分支原先静默返回，"没领到租约"和"不需要领"长得一模一样；本轮是靠新加的 INFO 才定位到的。现在跳过与执行完成各记一条。
- **[P3] 一次性环境的回收只声称不核对**。首版只管删库和对象，durable 队列在开发 broker 上逐次累积（本机现存的 `docpilot.capacity.*` / `docpilot.drill.*` / `docpilot.it.*` 是更早阶段留下的，不属于本次制造，已如实记为待清理项）。现在库、本次前缀对象、本次队列三类删完都回查，任一仍在即 `RESIDUE` + 退出码 1；本次遗留的两个队列已按精确名字删除（HTTP 204，回查为 0）。
- **[P4] 用例上限会冒充缺陷**。同一批用例在 60 秒上限下先后有 1 条、2 条失败，而单跑那条 13.6 秒就过——队列形态下整条套件共用一个队列，末位用例会被前面用例的排队拉长。`playwright.config.ts` 在 Compose 形态把上限抬到 150 秒（进程内基线仍 60 秒），`waitForSuccess` 的等待窗口由 setup 注入 120 秒；两处都写明理由，避免后来者把它读成"性能问题"。

顺带修掉一处已进主干的破坏：`2a100b4` 给 `scripts/capacity_observation.py` 改文案时在双引号字符串里用了半角引号，G6 观测脚本从那次提交起就 `SyntaxError` 无法导入。本轮把该处换成「」并 `py_compile` 通过。

门禁：基础套件 `pytest -m "not broker and not s3"` 在 SQLite（清空 `TEST_DATABASE_URL`）与 PostgreSQL（`.env` 的 `TEST_DATABASE_URL`）两种方言下各全量通过，304 项（G7 后 303 项 + 本轮回归用例 1 项）。

## 19. 阶段 G10 交付记录：失败明细下钻（FR-042，2026-10-03）

为什么挑这条：objective 第 2 条里剩下的四项（FR-040 投递、FR-041 Webhook、FR-042 配额/计费/下钻、FR-010/013 检测/清除）大多要先有被批准的业务口径。只有"失败明细下钻"是纯工程缺口——错误本来就存在库里，缺的只是把它按正确的边界呈现出来。

设计的拦路石是 `docs/16 §3` 那条不变式："失败摘要不返回错误文本"。直接加一个带原文的端点就是违反既定设计；把不变式改宽又不负责任（错误文本可能带文件名与正文片段）。所以拆成两个视图，各守各的边界：

- `GET /api/v1/tenants/{tenant_id}/usage/failures`：本租户的失败任务与失败规则运行，**允许**出现该租户自己的任务号与错误原文；由成员关系与角色矩阵把关，取 `attempt_no` 最大的那条尝试。
- `GET /api/v1/platform/usage/failures`：跨租户只给错误代号、任务数、受影响租户数与最后出现时间；原文、文件名、正文、邮箱、任务号一律不出。要看原文必须回到租户端点。

代号来自 `classify_failure`：按自家处理链路的措辞做启发式匹配（超时 / 队列不可用 / 提取引擎不可用 / 文档无法读取 / 未提取到结果），规则先命中先得；认不出的只给 `unclassified-<sha8>` 加文本长度，不回显原文。已在 `docs/16 §6.4` 写明它是"便于聚合的近似分类"，权威永远是租户明细里的原文——避免后来者把代号读成事实。

平台分布有扫描上限（默认 5000 行，按 `finished_at` 倒序）。撞顶时 `truncated=true` 并连同 `scan_cap` 一起返回：宁可报"看不全"，也不给一个看起来完整的分布。审计动作 `platform.usage_failures_viewed` 走既有白名单机制登记在 `app/services/audit.py`，未登记的动作为拒绝写入。

## 20. 阶段 G11 交付记录：演练读数改成"稳定"判定并自留转录（2026-10-03）

起因是 G7 交付后并行会话又跑了 8 次，得到 10 次 PASS / 1 次第 8 步不一致，而失败签名被一次 grep 过滤丢掉了，根因不明。本轮不假装已经解释那次失败，而是先把"能不能解释下一次"这件事解决掉。

三处改动：

- **核对从"一次读数"改成"稳定判定"**。恢复实例重启后各卷是逐个向 master 注册的，`wait_ready` 原先只确认一个 4 KB 探测对象可读，随后第 4/8 步就把全部键（含 5 MB）一次性比对完——"还没稳定"会被读成"备份不可恢复"。`settle_compare` 在窗口内重试并分别给结论：稳定下来算通过（记下核对次数与耗时），窗口耗尽仍不一致才算损坏，且保留最后一次签名。就绪判定同时改用最大的探测对象。
- **转录由脚本自己落盘**到 `data/drill/object-<UTC>-<run>-<PASS|FAIL|ERROR>.log`（只回收本脚本自己写的文件，保留最近 20 份），`main()` 的 `finally` 里写，异常路径也留。
- **异常把 traceback 写进转录**。这条是本轮当场学到：我连着跑 5 次，第 4 次在打印完第 7 步之后、第 8 步之前抛异常退出（exit=1），转录到第 7 步就断了——因为当时 traceback 只走 stderr，而我又用 grep 过滤了输出，**于是第二次把同一次失败签名弄丢了**。现在 `except BaseException` 会把 traceback 追加进转录再重抛。

同一批证据：5 次运行 4 次 PASS、1 次异常退出；崩溃那次的收尾仍然干净（`finally` 回收了自己的恢复容器与副本目录，事后核查 `no restore containers` / `no drill dirs`）。

结论要说准：**那次崩溃的根因仍未定位**，候选是 pause/cp 阶段或恢复实例端口分配在本机负载下失败（崩溃时间与并行跑的用例重叠）。现在的差别是——下一次再发生会留下可读的签名，而不是又一轮"某次跑挂了"。没有把崩溃改成静默重试：备份验证工具遇到基础设施打嗝应当失败并说清，而不是绿给我看。


## 21. 阶段 G11 追加：把演练的两种失败分开，并更正一条写过头的结论（2026-10-04）

§20 说的是"下一次再发生会留下可读签名"。这一轮就去查上一次那笔账，结果是**两件被混成一件事的失败被分开**，并且推翻了一条已经写进决策提案的前提。

## 24. 阶段 G14 交付记录：出站 Webhook 的机制与默认关闭（FR-041，2026-10-04）

目标 2 里 FR-041 写的是"出站 Webhook、签名和密钥轮换尚未实现"。开工前先撞上一条既有记录：`docs/16 §1` 明写这件事**刻意不做**，理由是"没有批准的外部出口与密钥管理流程，写完也是上线一个真实的外呼通道"。这条理由我不动它，改的是做法：机制交付，但**默认关闭**——没有 `WEBHOOK_MASTER_KEY` 就不让建端点（409），投递进程拒绝启动，出站目标默认只允许 https 且解析到回环/内网直接拒。于是"要不要真发出去"仍然是部署方的决定，我不替他做这个决定；业主确认密钥流程之前，任何联网部署都不该设这个主密钥。这一点在 `docs/07` FR-041 与 `docs/16 §1` 里都写成未收口项，而不是已交付。

三个形状上的决定值得留下理由。

签名密钥不落库：`HMAC(master, endpoint_id|secret_version)`。库里因此没有可拿去签名的秘密，轮换就是推进版本号；宽限窗口内额外发一个 `X-DocPilot-Signature-Previous`，接收方按 `X-DocPilot-Secret-Version` 选密钥。把窗口设成 0，那个头就消失——用例证明确实是窗口在决定它，而不是恒发。

扇出不借用 `domain_events.published_at`。那个字段现在的含义是"事件规则引擎已消费过"，Webhook 是第二个独立消费者，共用一个闸门会互相吞事件。所以用 `webhook_deliveries` 的 `(endpoint_id, event_id)` 唯一约束当幂等键，认领沿用 G2 的租约形状（条件更新单一胜者、过期回收）。这条写在 `service.py` 的模块 docstring 里，因为它正是"看起来能省一步"的那种地方。

字节只序列化一次：信封在扇出时就成形并落库，签名与发送共用同一串。否则重试时重新读事件、重新 dump，任何键序差异都会让对端验不过——这类 bug 只在生产出现，本机永远碰不到。

用例抓出两个真缺陷，都不是先想清楚再写的：`finish()` 在重试预算耗尽时报 `retry`（调用方会以为还会再投，我最初的 410 计数也因此读错）；`meta` 的 `enabled` 读的是导入期快照，配置后注入也看不到。两处都改了并留下前后对照。

门禁（全部串行，见 §23 那条并发教训）：基础套件 **317 项**在 SQLite（294.7 秒）与 PostgreSQL（305.2 秒）各全量通过、0 跳过、12 排除；`-m s3` 8 项、`-m broker` 4 项通过；G1 迁移门禁在 PG 上空库 `upgrade head` → `downgrade -1` → `upgrade head` 且 `alembic check` 无漂移（新增两张表）。compose 的 `profile: app` 加了第五个服务 `webhooks`，`docker compose up` 默认仍只有基础设施三项——这条由 `tests/test_compose_shape.py` 盯住。G13 的容器形态端到端在加服务后重跑：**12/12（2.0 分钟）**，`webhooks` 容器 running，`alembic_version = b7c1d4e9a052` 仍由 migrate 容器写入。

这一轮也踩了自己挖的坑：第一次跑容器形态带了 `--no-build`，复用的旧 tag 里没有 `python -m app.webhooks`，形状核对如实报红（api 那边一切正常，很容易让人怀疑是新服务写坏了）。判据没骗人，是参数在骗人，所以现在 `app-up` 在 `--no-build` 场景失败时会附一句"先重建再看"。

没做的：Webhook 管理界面与浏览器验收、真实对端的送达证明、mTLS/IP 白名单、批量重放、投递级审计（一次事件 × N 端点 × 重试会把审计面淹成噪声，明细走 `webhook_deliveries`）。通知渠道与审批流（FR-040）不在这次范围内：投递读的是领域事件，`NotificationRequest` 仍然只是登记。


## 25. 阶段 G15 交付记录：对象存储进入就绪判定（TC-OPS-002，2026-10-04）

`docs/04` 与 `docs/06 TC-OPS-001` 都留着同一句话：`/readyz` 判数据库、迁移与队列，但**不判对象存储**。也就是说 SeaweedFS 已经连不上时探针还能报 `ready`——上传与下载都会失败，而服务自己说没问题。这条不需要任何人拍板，就把存储段补上了。

口径沿用 G5 那次队列段的三分法，而不是「通/不通」：`STORAGE_BACKEND=local` 时文件就在本机目录，没有外部依赖可问，段里写 `checked: false` 且不参与判定；声明走 s3 就必须真能列出对象，列不出即 503 并带上错误类名；探针自己炸了也只记一段 `reachable: false`，绝不把端点变成 500（那会把「探针故障」读成「进程死了」）。

判据的取法值得一提：不做写入探针，也不 `head_bucket` 通个状态就算，而是 `list_keys("")` 取第一个键就停（`itertools.islice`，一次 ListObjectsV2）。空桶会得到 `reachable: true` + `listed_sample: false`——「列得动」与「里面有东西」是两件事，混成一件会让刚建好的空桶被读成故障。

实测分两层。假探针层覆盖四种口径（local 不判、s3 可达算 ready、问不到算 503、探针抛异常也是 503 而不是 500），`storage_health()` 自身另测 local／s3 活桶／坏桶三种形状；真栈层直接对开发机上的 SeaweedFS 跑一次：活端点 `reachable=true listed_sample=true`，把端点改成 `http://127.0.0.1:1` 就得到 `reachable=false error=EndpointConnectionError`。这一对是必要的——只有假探针的话，「错误类名从哪来」没人证明过。

顺带确认改动没弄坏邻居：`capacity_observation.py` 只在正文里引用 `/readyz` 的判据口径，不把它当门禁；端到端的 Compose 形态都以 `/readyz` 为起步门槛，容器形态在「存储段参与判定」之后 **12/12（2.2 分钟）** 通过，等于对真栈做了一次不误报验证。

门禁（串行）：基础套件 **319 项**在 SQLite（331.7 秒）与 PostgreSQL（312.6 秒）各全量通过、0 跳过、12 排除；`-m s3` 8 项、`-m broker` 4 项通过。

仍未进探针的：提取依赖（`EXTRACTOR_MODE=mock` 时没东西可判，接真实 OCR/LLM 才有意义）与 Webhook 投递积压。前者要等真实提取器落地，后者取决于 G14 那件事是否被批准保留——不给一个未定的东西预先做判据。


## 26. 阶段 G16 交付记录：内容签名核对（FR-010 读侧，2026-10-04）

FR-010 在矩阵上留的是"内容签名与恶意文件检测待补"。这两半不是一回事：恶意引擎选哪个、命中之后是隔离还是只标记，都是业主口径；**内容签名是纯工程**——上传时已经记了 `sha256` 与字节数，缺的从来不是"记下来"，而是"读回来再算一次"。

不补这一步会留下什么：`checksum` 只是数据库里的一行字符串。对象被覆写、备份回滚到旧副本、键被另一个任务重用，数据库这边全都看不出来——记录"完好"，字节已经不是当初那份。所以 `app/contexts/documents/integrity.py` + `POST /api/v1/tenants/{tenant_id}/documents/{document_id}/integrity/check` 做的是把存储里的真字节重新哈希、与登记值比对，分四类如实报告：`matched`／`mismatched`／`missing`／`unreadable`。

三类状态的分开是有意的，不是细分癖：
- 对象读不到（`FileNotFoundError`）报 `missing`，不能混进 `mismatched`——"内容被改了"与"对象不在了"对运维是两个完全不同的动作。
- 读得动但抛异常（端点抖动、权限）报 `unreadable` 并带上错误类名，与"桶里就没有这个键"分开。
- 判定只看摘要，不看长度。等长改写正是最常见的那类破坏，字节数拦不住它；反过来"摘要相同而长度不同"意味着哈希碰撞，不值得为它造一个永远不会走到的状态——所以 `size_matches` 只是随附信息，不是判据。

**严格只读**：不改文档、不删对象、不打处置标记。"发现不一致之后怎么办"属于保留与处置政策（FR-013），那要业主定，这里不替他做——与阶段 G3 的孤儿审计同一个口径：工具负责发现并如实报告。审计动作 `document.integrity_checked` 只记 `checked/clean/counts`，不落文件名与摘要正文。角色给到 owner/admin/member，`reviewer` 不开放（它会对外发一趟存储读，且要求 CSRF）。

用例六条，两条是必须的负向：把一个字节翻转成**等长**内容 → 必须 `mismatched` 且 `size_matches: true`（证明抓到它靠的是摘要）；删掉对象 → 必须 `missing` 而不是 `mismatched`。另有跨租户 404、reviewer 403、审计落一行、核对完对象字节原样未动。

门禁（串行）：基础套件 **325 项**在 SQLite（335.7 秒）与 PostgreSQL（315.4 秒）各全量通过、0 跳过、12 排除；`-m s3` 8 项、`-m broker` 4 项通过。文档同步：`docs/07` FR-010 改写为"读侧已交付、恶意检测待口径"，`docs/06` 新增 TC-DATA-006。

仍没做的：恶意文件检测（待引擎与处置口径）、租户级批量巡检端点与界面（单个文档的核对已经够排障用，批量要先把"扫多少、多久扫一次"的运维口径定了）。


## 27. 阶段 G17 交付记录：备份演练收成一个入口，边界跟着结论一起打印（2026-10-04）

目标 1 的原话是"数据库备份演练还不覆盖对象存储"。G7 已经补上对象卷演练，但两个脚本各放各的：跑完 `backup_restore_drill.sh` 打印的是"核对通过"，不看细节的人照样以为备份这件事整体过了。所以缺的不是第二个脚本，是**边界不跟着结论走**。

两处改动都小但在点上。数据库演练结尾现在固定打印自己覆盖了什么：`DRILL RESULT: DB PASS（范围=PostgreSQL 备份与恢复）` 后面紧跟"未覆盖对象卷"和另一个脚本的名字——把"通过"和"通过了什么"绑成同一次输出。另加 `scripts/run_backup_drills.sh` 一次跑完库 + 对象卷，**聚合两侧结论**：任一侧不成立就非零退出，不会一半绿着报通过。

聚合逻辑自己也能证伪：`DRILLS_SKIP=1` 只走查不跑真演练，此时结论只报 `PROBE` 不报 `PASS`（否则这个开关本身就成了假绿的来源）；`DRILLS_PROBE=db|object` 强制一侧失败。实测两条都对——跳过时两侧 rc=0 退出码 0 且明确写着是走查，强制对象侧失败时退出码 1。

真跑一次（非走查）：数据库侧备份/恢复/结构·行数·指纹三道核对通过；对象卷侧副本 1.2 秒、恢复就绪 20.8 秒、键集合与尺寸与摘要三类核对一致、回收无残留；聚合输出 `DRILLS RESULT: PASS 数据库=PASS 对象卷=PASS`，并保留同一句范围声明（本机、冷副本、同机恢复；不含异机灾备、增量、保留策略与 RPO/RTO）。

这一轮没碰的也写清楚：包一个脚本出来不会改变对象卷演练本身的能力边界——G7/G11 记的那一次未解释异常、以及从未做过的异机恢复都还在。R-018 的结论要从"我们有能力发现某次备份不可恢复"升级到"对象数据已有可恢复备份"，前提仍是"备份流程自带恢复后全量摘要核对"（或逻辑级复制 / 原生复制），那是 `docs/19` 待批的运维决策，不是多一个入口能顶掉的。


## 28. 阶段 G18 交付记录：配额强制，默认不限、管理员设值（FR-042，2026-10-04）

2026-10-04 的答复是"做：默认不限，由管理员设值"（记录在 `docs/19 §5`）。同一批答复还有三条：Webhook 保留但默认关闭、彻底删除先不做、§1–§3 的数值仍由业主定。所以这一轮做的就是配额，且**只做答复允许的那部分**。

形状上三条约束是有意选死的：

只有两个轴，且都对着用量视图已经在算的东西——文档数与存储字节。没有按人配额、没有速率、没有计费口径：那些要先有被批准的业务定义，我不替业主发明单位。

默认必须是"无行即不限"，不是"建行填个大数字"。前者让这次交付对现存任何部署都是零行为变化；后者等于我偷偷设了一个没人批准的额度。同理，`MAX_LIMIT` 是给上限本身设上限——没有它，一次手滑的 `10^18` 会在字节轴上溢出成负数，反而放开所有上传。

判定必须发生在**任何对象写入与任何行落库之前**。被拒的请求因此不需要 G3 那套按前缀补偿：没有半份文件进过存储，也没有孤儿任务。用例就是照这条断言的：拒绝后文档/版本/任务三个计数一字不变。

字节轴走 `BigInteger` 不是排面：SQLite 的 `Integer` 是 64 位、PostgreSQL 的 `INTEGER` 不是，1TB 级别的目标会在撞到上限之前先溢出。

## 29. 阶段 G19 交付记录：快照退役 R1+R2，把双真相变成当场可发现的 bug（2026-10-04）

业主那四条答复里没有一条提到快照，但目标句"明确 `processing_jobs.snapshot` 的最终迁移/删除方案"是工程侧能自己推进、且不依赖任何待定产品决策的那一条。`docs/20`（DOC-DD-009）已经把六个修订写死，R1/R2 是其中唯一"加了之后不改变任何现有读行为"的两步，所以这一轮只做这两步。

形状上三条约束是有意选死的：

**新列一律可空，迁移不给默认值。** 可空的含义是"还没回填"。用 `""`、`0`、`[]` 去填历史行，等于把 R3 的判断提前做掉——而 R3 本该在真实开发数据上逐行看快照再决定每个键怎么落。用例第一条就是断言迁移前已存在的行新列必须是 `NULL`。

**镜像来自同一份 `Job`，不来自列本身。** 写快照与写新列在同一个事务、同一处代码里派生（`JobRepository._save_job_record` 与 `_sync_normalized_facts`），所以两者不一致只可能是我写错了，不可能是"两个进程各写一半"。这条不是说说：用例先手工把 `progress` 改成 `"lying"` 并提交，再走一次正常保存，断言它被覆盖回与快照一致——只有"不读列本身"的实现办得到这件事。

**`warnings` 归尝试、`parse_error` 归版本行。** 快照里 `warnings[]` 与 `files[].error` 是唯二"按任务存下来的每文件/每次尝试事实"：任务级快照会被下一次尝试覆盖，这本身就是归属错误。R5 切读之后这些事实必须已经有家，否则切读等于丢告警。

一处写规则的选择值得记下来：**模板版本任务也写 `field_definitions` 副本**。`docs/20 §2` 的读规则是"`template_version_id` 非空就只信模板版本"，两处都有值因此多了一条可能漂移的边。我没有选择"模板任务留 NULL"，因为 NULL 会让 R4 对账区分不开"这是模板任务所以本来就不写"与"这次写失败"；改成照写之后，对账只需比较三者是否逐键相等，用例也照这条断言（`field_definitions == snapshot["fields"] == template_versions.fields`）。

一处实现细节被用例抓到，值得留在文档里：第一次写多尝试用例时，`attempt 1` 的 `warnings` 是 `None`——因为 `_sync_normalized_facts` 只在尝试行已存在时才写，而尝试行由派发/Worker 路径创建，测试里我先保存了任务再补尝试行。这个行为本身是对的（没有尝试就没有"哪一次尝试的告警"），但它说明**这条镜像是尽力而为的同步，不是"每个任务都保证有 warnings 行"**，R4 对账必须把这个形状算进去，否则会把"尝试行还没建"报成漂移。

门禁（串行，四道，数字取自 junit XML 而非终端回显）：PG 迁移门禁（空库 `upgrade head` → `downgrade -1` → `upgrade head`，`alembic check` 无漂移，新修订 `d5e2b74c0a19` 可逆）；基础套件 **339 项**在 PostgreSQL（324.7 秒）与 SQLite（330.9 秒）各全量通过、0 失败、0 跳过、12 排除；`-m s3` 8 项、`-m broker` 4 项通过。用例七条（`tests/test_snapshot_retirement_r1r2.py`，TC-DATA-007），关键负向三条：迁移前的历史行新列必须为 `NULL`、手工把 `progress` 改成假值会被下一次保存覆盖回一致、部分成功批次里失败文件的 `parse_error` 非空而成功文件的留在 `NULL`。容器形态端到端 12/12 见 `docs/06 §5.20`。

两处运行事实记下来，避免下一个人误判：`-m broker` 那 4 项在 `BROKER_URL` 未设置时是**跳过**而不是失败，而 `.env` 里只有 `RABBITMQ_USER`/`RABBITMQ_PASSWORD`、没有 `BROKER_URL`，所以这一道要显式拼 URL 才会真的执行——本轮第一次跑就是 4 skipped，第二次带 URL 才是 4 passed。另外后台命令的输出一律不要接管道：本轮两次把长命令接进 `tail`，一次结果被进程强退吞掉，一次 `tail -2` 只留下进度点、把 `N passed` 那行挤掉，最后改用 junit XML 落盘才拿到可核对的数字。

没有做的：R3 回填脚本、R4 对账脚本、R5 切读、R6 删列。快照列仍然是 `JobRepository.get()` 的读源，因此这一轮之后双真相仍是**两个家**——R2 的价值不在消灭快照，而在让"列与快照不一致"从"日后对账才发现"提前到"当场就能被用例抓到"。

## 30. 阶段 G20 交付记录：快照退役 R3+R4，让"删了不丢信息"变成可执行的判定（2026-10-04）

## 33. 阶段 G23 交付记录：把 R-018 那条"未归因失败"查到能归因（2026-10-04）

## 35. 阶段 G25 交付记录：逻辑级对象备份恢复，第一次拿到「可重复通过」的恢复证据（2026-10-04）

## 37. 阶段 G27 交付记录：把 R6 的门禁判据从内存搬到审计表（2026-10-04）

G21 我给 `docs/20 §6.1` 换了一个"可核对"的判据：观察期内 `incomplete_rebuild_count()` 增量为 0。写完两轮之后发现这个判据本身是坏的——**进程内计数活不过一次重启**，而删列恰恰是几周之后才会发生的事，那时候没人知道重启过多少次、计数被归了几次零。自己造的洞，自己补。

改法很小：读路径判定"规范化源不完整"时，除了抛 `IncompleteJobFacts` 和累加内存计数，再写一条审计事件 `job.rebuild_incomplete`，元数据只有 `missing`（缺哪几项：fields / progress / files）。于是 §6.1 变成"观察窗口内这条审计事件新增 0 条"，跨重启、跨进程都能查，`GET /api/v1/platform/usage` 直接给出 `job_rebuild_incomplete_total`。

三条边界写清楚：

**审计只带内部 ID 与缺项名。** 不带字段值、文件名、错误正文——那些是租户数据，平台侧审计不该把它们带出来。用例把这条钉住（`set(metadata) == {"missing"}`）。

**审计写失败不能掩盖真正的问题。** `_record_incomplete_rebuild` 里吞掉异常并就地记日志：主异常必须是 `IncompleteJobFacts`，否则一次审计表故障会把"这条任务读不出来"变成"整个读路径 500"，把一个数据问题升级成可用性问题。

**两个读数并列而不是替换。** `..._total`（持久）是门禁看的那条；进程内那条留着，因为它能回答"这个 worker 起来之后有没有过"，两者失效方式不同，只留一个反而会误导。

实现过程中自己踩了一处：把新方法插在 `_rebuild` 的 `raise` 后面，结果 `_rebuild` 剩下的函数体被吸进了新方法，`get()` 静默返回 `None`——六个用例一起红。这是"补丁按锚点插入，不检查插入后结构"的典型后果，也是为什么改完必须立刻跑用例而不是相信 diff 看着对。

新增用例 `test_incomplete_rebuild_leaves_a_durable_audit_event` 钉住三件事：事件存在且带正确 `action` / `tenant_id`、`sorted(metadata["missing"]) == ["fields", "files", "progress"]`、`set(metadata) == {"missing"}`，并断言 `GET /api/v1/platform/usage` 报出 `job_rebuild_incomplete_total >= 1`——只写表不读数等于没有门禁。

四道门禁串行全绿（结果落盘后读取，未接管道）：迁移门禁退出码 0；PG 侧 354 用例 0 失败 0 错误 0 跳过；SQLite 侧 354 用例同口径全绿；`-m s3` 8/8；`-m broker` 4/4。`tests/test_snapshot_retirement_r5.py` 7/7、`tests/test_operations.py` 全绿。

**broker 那一项差点被"跳过"糊过去**：复核链里我重写的那条命令没导出 `BROKER_URL`，四条真实队列用例整组 skip，退出码照样 0——是 junit 里的 `skipped=4` 露出来的，不是退出码。补上 `BROKER_URL` 重跑才是 4/4、`skipped=0`。跳过即通过的门禁不是门禁，这条用例套用的判据也一样：如果哪天只看 rc，R-016 那类方言残留会重新溜进来。

## 40. 维护轮 M2 交付记录：适配器可替换性契约（NFR-004，2026-10-10）

`NFR-004` 是追踪矩阵里最后一个整格没有测试映射的需求行，映射栏只有"后续适配器契约测试"一句散文。本轮补 `tests/test_adapter_contracts.py` 8 条，纯新增，未改任何产品代码。

**为什么单独立一个文件。** `test_parsing.py`（19 条）与 `test_extraction.py`（21 条）覆盖的是**构造函数**注入：`DocumentPipeline(dispatcher=..., extractor=...)`、`ParserDispatcher(FakeOCREngine())`。生产路径走的却是**工厂与单例**。此前没有任何用例证明"替换点在工厂层有效"——构造函数层的绿全部成立时，生产路径照样可能不可替换。契约测试要测的正是这一层，所以它属于新文件而不是加进那两个文件。

**第一次跑就红了 2 条，红得有价值。** 签名是"假解析器一次都没被调用"。查下来是四类适配器的绑定时机**不一致**：

| 适配器 | 绑定时机 | 想替换时该动哪里 |
|---|---|---|
| 对象存储 | **每次调用**解析工厂（`build_object_storage()` / `get_object_storage()`） | 换工厂函数 |
| 解析器 | **构造时**绑定到 `DocumentPipeline.dispatcher` | 换工厂函数**无效** |
| 提取器 | **构造时**绑定到 `DocumentPipeline.extractor` | 同上 |

`get_job_manager()` 是进程级单例，它的 `DocumentPipeline` 在首次调用时就把当时的工厂结果存了下来。这不是缺陷——单例本来就是这个语义——但它意味着**想在生产形态下替换解析器或提取器，没有一个注入点**：只能改 `EXTRACTOR_MODE`（在 mock 与 llm 之间选）或替换类方法。这件事此前只存在于 `pipeline.py` 的构造函数写法里，没有任何文档或断言记过。现在它是 `test_dispatcher_and_extractor_are_bound_at_construction_time`，并且写明了"哪天改成每次调用都解析工厂，这条会红，请同步更新 `docs/07 NFR-004`"。

我原本写的第一版用例就是在工厂层替换全部三类，跑出来 2 红 6 绿。修法有两条路：改产品代码给流水线加注入点，或者按现状在类方法层替换。**选了后者**——本轮的目标是补契约测试而不是改架构，给单例流水线加注入点是设计变更，应当单独一轮并走设计评审。所以用例记录的是现状，并在 docstring 里把差异写成表。

## 41. 维护轮 M3 交付记录：请求关联 ID 贯穿（NFR-005，2026-10-10）

`NFR-005` 要求"关键业务操作结构化记录关联 `request_id`、`tenant_id`、`job_id`；日志不得包含密钥或不必要的文档内容"。前两者已到位，缺的是 `request_id`：全仓 grep（`app/`、`tests/`、`scripts/`）无一处实现。`docs/11 §4.2` 当初拒绝给审计表加这一列的理由是"当前没有产生方，避免留下无消费者的空字段"——这个理由本身是对的，所以本轮把**产生方与列一起交付**，而不是先加列等以后接。

**一个 ID 要同时出现在三处才有用。** 只进响应头，用户拿着 ID 查不到日志；只进日志，用户根本不知道自己的 ID 是什么。三处是响应头、日志行、审计事件。这也是为什么 `docs/05 §9` 早就写了"错误响应使用稳定错误码、用户可理解描述和 request_id"，而它一直没有落地：只做其中一处的话，那句设计描述看起来像完成了，实际用不起来。

**实现分四块**（`app/request_context.py` 新增，其余为接线）：

1. **中间件**：请求头带 `X-Request-ID` 时沿用，否则生成 32 位十六进制；响应头一律回填。
2. **格式校验**：只接受可见 ASCII、长度 8–64。不校验的话，控制字符会被写进日志行（伪造出新行）与响应头（响应拆分面）。不合规一律换成本进程生成的新 ID，**不报错**——关联 ID 不值得让一个正常请求失败。这条取舍写进了模块 docstring。
3. **`contextvars` 而非参数传递**：审计写入点在服务层、日志散在各处，逐个加参数要改几十个签名。上下文变量还带来一个必要的副作用：后台线程天然拿不到请求上下文，避免把一个请求的 ID 贴到另一个请求的日志上。
4. **统一日志配置**：派发器、Worker、Webhook 投递三个入口此前各写一份 `basicConfig(format=...)`，格式里没有关联 ID 也没有过滤器——三份重复且都不合格。现在统一走 `configure_logging()`，过滤器只挂一次（有用例钉住"不叠加"）。

**列与迁移**：`audit_events.request_id`，`String(64)` 可空、**不给服务端默认值**，加索引供"拿用户报的 ID 查这次请求做了什么"。迁移 `e1f4c7a29d63`（`down_revision = d5e2b74c0a19`），`downgrade()` 删索引与列。可空是刻意的：历史审计行没有这个值，猜一个等于编造关联；Worker 与脚本路径今天也仍然是 `NULL`。

**四处反向验证**（每条判据都证明它不是恒过）：

| 注入的破坏 | 结果 |
|---|---|
| 中间件不回填响应头 | 2 条红 |
| 审计不从上下文取 ID | 2 条红 |
| 中间件不做格式校验（回显原值） | 1 条红（`bad\nvalue` 被原样回显） |
| 审计列表不回传该字段 | 1 条红 |

**两条自己抓到的测试缺陷**：第一版用 `{"name": ..., "fields": []}` 建模板，`fields` 有 `min_length=1`，接口返 422 而我在断言里读 `["events"]` 才炸；第二版手工用 `LOG_FORMAT % record.__dict__` 渲染日志，`asctime` 不在 `__dict__` 里，改成 `logging.Formatter(LOG_FORMAT).format(record)`。两条都是"用例写得比产品还脆"，记在这里因为它们的签名（422、KeyError）都不指向真正的错处。

## 48. 维护轮 M10 交付记录：快照的纯逻辑导出兜底（R6 门禁第 3 条，2026-10-10）

`docs/20 §6` 门禁第 3 条要求删列前"另存一份纯逻辑导出作为兜底，不能只依赖卷副本"——卷级冷副本 12 轮 3 次失败、根因未归因（R-018），所以这条兜底不是形式要求。本轮交付该工具：`scripts/snapshot_logical_export.py`。

**为什么不是 `pg_dump --column`**：`docs/20 §6` 的原话是"`pg_dump --column` 级别的转储"，但 `pg_dump` 没有"按列"这个粒度——要么整库、要么整表。所以做法是**逐行读 `snapshot` 列并序列化**，效果等价而更小（导出里只有主键、租户、状态与这一列，不含其他表内容），而且 SQLite 与 PostgreSQL 共用同一份代码，不必为删列准备两套工具。

**产出两份文件**：`snapshot.jsonl`（每行一条 JSON）与 `manifest.json`（行数、逐行 SHA-256、整文件 SHA-256、源库标识、时间、列名）。有清单才能事后证明"这份导出覆盖了当时库里的每一行"——只有一堆行文件的话，"少了一行"这件事永远看不出来。

**一处与入库边界相反的取舍，实测后改的**：第一版我给 `snapshot` 过了 `without_nul()`，因为入库边界正是这么做的（PostgreSQL 的 text/json 拒收 NUL）。跑出来直接 `AttributeError`——`without_nul` 只接受字符串，而快照是 dict。修之前先实测了 NUL 在 JSON 往返里的行为：`json.dumps` 把 NUL 转义成 `\u0000`（文件里没有裸 NUL），`json.loads` 能无损还原。所以**清洗只会丢数据而不会提高可读性**，与"兜底"的目的正好相反——一份被改过的兜底导出比没有更危险，因为它看起来是完整的。现在导出对 NUL 无损，并有一条实测记录钉住它。

**四处反向验证**：

| 注入的破坏 | 结果 |
|---|---|
| 改动一行内容（`status` 改成 `tampered`） | `VERIFY RESULT: FAIL`，整文件摘要不符 |
| 删掉最后一行 | `VERIFY RESULT: FAIL`，报"行数不符：清单 1，实际 0" |
| 输出目录指向仓库内（`outputs/bad-export`） | 拒绝执行并提示改到仓库之外 |
| 注入含 NUL 的快照再导出 | 读回是真实 NUL，文件里是 `\u0000`（无损） |

**实跑读数**：

```
开发库 SQLite        导出 1 行 → VERIFY PASS（整文件摘要 e8e6d23dee59…）
一次性 PG 库         导出 1 行 → VERIFY PASS（整文件摘要 2e2672a4e65a…）
```

**边界：工具就绪不等于动作已做。** 门禁第 3 条要求的是"删列前另存一份"，那一次导出**没有执行**——它属于删除前的动作，现在执行只会得到一份很快过期的文件。所以 `docs/20 §6.2` 里这条改写成"工具已交付，尚未执行"，仍不计为满足。**R6 仍不得执行。**

**下一轮候选**：① `NFR-004` 的搜索后端抽象与单例流水线注入点（同属设计变更，应先评审）；② Webhook 管理界面（按 G10→G12 的规矩先有验收再上线）；③ 把导出的"读回来"也做成可验证的——现在只验摘要一致，没有验证"这份导出能重建出可用的任务对象"。
