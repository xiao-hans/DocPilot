## 1. 目标与范围

补齐阶段 B（多租户基础）的授权与审计缺口，使租户边界从"数据归属正确"升级为"动作按角色默认拒绝"。本期覆盖三件事：服务端角色矩阵判定、一次性邀请令牌驱动的加入流程、只追加审计事件。

本期不实现：邮件投递、未注册用户的自助注册、所有者转让、成员重新激活、登录限流、SSO、复核动作（FR-023）、审计保留与删除策略、PostgreSQL Row-Level Security。（请求 `request_id` 关联原列在此，已于维护轮 M3（2026-10-10）交付，见 §10.5 与 `docs/06 §5.26`。）

兼容性口径（明确表述，避免误读为"零影响"）：既有端点的**请求体与成功响应形状不变**；`POST /jobs` 会新增 403 拒绝路径，客户端必须把它当作授权失败而非网络错误处理。§3 的"复核确认/编辑结果"行只是矩阵预留，本期没有对应端点，因此不进入本期用例。

## 2. 方案与取舍

| 决策 | 取舍与理由 |
|---|---|
| 角色存放在 `Membership.role`，不引入权限表 | 四角色矩阵无需通用 RBAC；权限表在无第二个消费方时是负担。将来动作维度膨胀时再抽 `RolePermission` |
| 每次请求都从库中读取成员关系与角色判定 | 每请求多一次查询，换取"移除成员即刻生效"，满足 FR-004 验收且不依赖会话撤销。会话只证明身份，不携带权限快照 |
| 邀请令牌只存 SHA-256 摘要 | 与既有 `AuthSession.token_hash` 同一做法（ADR-0002）：拖库不等于邀请可用 |
| 接受邀请要求已登录且邮箱匹配 | 本期不做注册流程（属 `docs/08` 待确认决策 #2）；宁可让被邀请人先注册，也不引入"无身份写入成员关系"的路径 |
| 惰性过期在**每一次读取该邀请的路径**上生效 | 列表、撤销、接受都先做 `expires_at <= now` 判定；命中即把状态写为 `expired` 再按 `expired` 语义响应。不引入定时任务，也不允许"事实过期却仍显示 pending/被撤销成功" |
| 接受邀请用条件更新保证一次性 | 以 `UPDATE ... WHERE id = ? AND status = 'pending'` 判定影响行数，命中 0 行即视为已被并发请求使用；避免"唯一索引只约束 pending"导致的并发双接受 |
| 邀请列表与撤销属管理面，限 `admin`/`owner` | 邀请邮箱 + 待加入状态是管理信息；成员目录（含邮箱）对所有 active 角色可见，这是租户协作的正常可见范围，与 §7 的未认证路径防探测不冲突 |
| 审计只追加、不提供修改/删除接口 | FR-006 要求可追溯。数据库层触发器/RLS 保护待 PostgreSQL 基线，本期先保证应用层无写回路径，并在 §7 明确该保护的层次 |
| 平台管理员不进入租户矩阵 | 避免 `is_platform_admin` 成为隐式跨租户超级权限（SRS §5 新约束）；平台运营视图待 FR-042 单独设计 |

## 3. 角色与权限矩阵

角色取值：`owner`（租户所有者）、`admin`（租户管理员）、`member`（成员）、`reviewer`（复核人员）。角色之间**不构成包含关系**，逐动作判定；矩阵未列出的动作一律默认拒绝（403）。

| 动作 | reviewer | member | admin | owner | 判定入口 |
|---|---|---|---|---|---|
| 查看成员列表 | 允许 | 允许 | 允许 | 允许 | `GET /members` |
| 查看任务与结果、下载 Excel | 允许 | 允许 | 允许 | 允许 | 既有 `/jobs` 路由 + 写审计 |
| 创建任务（上传文件） | **拒绝** | 允许 | 允许 | 允许 | `POST /jobs` |
| 查看审计事件 | **拒绝** | **拒绝** | 允许 | 允许 | `GET /audit-events` |
| 查看待接受邀请 | **拒绝** | **拒绝** | 允许 | 允许 | `GET /invitations` |
| 邀请成员 | **拒绝** | **拒绝** | 允许 | 允许 | `POST /invitations` |
| 撤销邀请 | **拒绝** | **拒绝** | 允许 | 允许 | `DELETE /invitations/{invitation_id}` |
| 移除成员 | **拒绝** | **拒绝** | 允许（仅限 `member`/`reviewer`） | 允许（不得移除自己，且移除后须仍有 active owner） | `DELETE /members/{user_id}` |
| 变更成员角色 | **拒绝** | **拒绝** | **拒绝** | 允许（不得变更自己或现存 `owner`） | `PATCH /members/{user_id}` |
| 接受邀请 | 不要求成员身份：任何已登录用户，须邮箱匹配且令牌有效 | 同左 | 同左 | 同左 | `POST /api/v1/invitations/accept` |
| 复核确认/编辑结果（矩阵预留） | 允许 | 拒绝 | 允许 | 允许 | 本期无端点；FR-023 实现时接入同一依赖 |

补充规则：

- `User.is_platform_admin` 不授予任何租户权限；平台管理员若无该租户 active 成员关系，访问其任意租户端点得 403（TC-SEC-007）。
- 一个租户必须至少保留一名 active `owner`。移除或降级最后一名 active `owner` 的请求返回 409。
- `owner` 只由 bootstrap 或创建租户产生；邀请角色仅允许 `reviewer`、`member`、`admin`，不允许邀请 `owner`（无转让流程时避免所有者扩散）。
- 角色变更与移除只影响后续授权，绝不改写历史数据归属：既有任务的 `tenant_id`/`owner_id`、文档与版本记录保持不变。

## 4. 数据模型

### 4.1 Invitation

| 字段 | 约束 / 用途 |
|---|---|
| `id` | 32 位随机十六进制，主键 |
| `tenant_id` | 必填，外键 `tenants.id`，`ondelete=CASCADE`，索引 |
| `email` | 必填，写入前 `strip().lower()` 规范化；最长 320 |
| `role` | 必填，取值 `reviewer`/`member`/`admin` |
| `token_hash` | 必填，邀请令牌原文的 SHA-256（64 位十六进制），唯一索引。令牌原文不入库 |
| `status` | 必填，`pending`/`accepted`/`revoked`/`expired`，初始 `pending`，索引 |
| `invited_by` | 可空，外键 `users.id`，`ondelete=SET NULL` |
| `created_at` | 必填，UTC |
| `expires_at` | 必填，UTC，`created_at + INVITE_TTL_DAYS` |
| `accepted_at` / `accepted_by` | 可空，接受时写入 |

- `INVITE_TTL_DAYS`：环境变量，非负整数，取值范围 1–30，缺省 7；非法值回落缺省（沿用 `app/platform/config.py` 既有 `_env_int` 的安全读取风格）。不支持按单条邀请指定有效期。
- 同一租户内同一邮箱同时至多一条 `pending` 邀请，由**部分唯一索引** `unique (tenant_id, email) where status = 'pending'` 保证；SQLite 与 PostgreSQL 均支持该形式。命中即返回 409。
- `accepted`/`revoked`/`expired` 历史记录可与新 `pending` 邀请共存（不受部分索引约束），保证重复邀请同一邮箱可审计。

### 4.2 AuditEvent

| 字段 | 约束 / 用途 |
|---|---|
| `id` | 32 位随机十六进制，主键 |
| `tenant_id` | 必填，外键 `tenants.id`，`ondelete=CASCADE`，索引 |
| `actor_user_id` | 可空，外键 `users.id`，`ondelete=SET NULL`，索引；用户删除后事件仍保留 |
| `action` | 必填，点分动作名（见 §4.3），索引 |
| `object_type` | 必填，`membership`/`invitation`/`job` |
| `object_id` | 可空，被操作对象的 ID，语义见 §4.3 |
| `metadata` | 必填 JSON，默认 `{}`，键名受 §7 白名单约束 |
| `created_at` | 必填，UTC，索引 |

不提供 `request_id` 列：当前没有产生方，避免留下无消费者的空字段；与结构化日志和关联 ID 机制一并设计（§10.5）。**维护轮 M3（2026-10-10）已按这条理由补上**：产生方随 `app/platform/request_context.py` 一起交付，列现在有真实写入者（HTTP 请求上下文），Worker 与脚本路径仍为 `NULL`（见 `docs/06 §5.26`）。

### 4.3 动作与对象语义

| `action` | `object_type` | `object_id` | `metadata` 允许键 |
|---|---|---|---|
| `member.invited` | `invitation` | 邀请 ID | `role`, `expires_at` |
| `member.invitation_revoked` | `invitation` | 邀请 ID | `role` |
| `member.invitation_accepted` | `invitation` | 邀请 ID | `role`, `user_id`（接受者） |
| `member.role_changed` | `membership` | 被变更用户的 user ID | `from`, `to` |
| `member.removed` | `membership` | 被移除用户的 user ID | `role`（其原角色） |
| `job.created` | `job` | 任务 ID | `file_count` |
| `job.excel_exported` | `job` | 任务 ID | — |

### 4.4 既有模型变更

`Membership` 不变，复用 `role` 与 `status`（`active`/`removed`）。`User.is_platform_admin` 保留原样，本期仅明确其不产生租户权限。

## 5. API 契约

前缀 `/api/v1/tenants/{tenant_id}`（下表内路径均相对该前缀），除接受邀请外均沿用 `get_tenant_context`：路径租户必须与 actor 的 active 成员关系匹配。

**所有状态改变端点（含 `POST /api/v1/invitations/accept`）都要求 `X-CSRF-Token`**；接受邀请的发起方是已登录用户的浏览器，同样存在 CSRF 面，因此不豁免。

| 端点 | 角色 | 请求 | 成功响应 | 失败（按 §5.1 顺序） |
|---|---|---|---|---|
| `GET /members` | 任意 active 角色 | — | `200 {members:[{user_id,email,role,status,joined_at}]}` | 401/403 |
| `PATCH /members/{user_id}` | `owner` | `{role}` | `200 {user_id, role}` | 422 角色非法；403 请求者非 owner；404 目标非本租户 active 成员；409 变更自己 / 目标是 `owner` / 降级后无剩余 owner |
| `DELETE /members/{user_id}` | `admin`/`owner` | — | `200 {user_id, removed: true}` | 403 请求者角色不足或 `admin` 针对 `admin`/`owner`；404 目标非本租户 active 成员；409 移除自己 / 移除后无剩余 active owner |
| `POST /invitations` | `admin`/`owner` | `{email, role}` | `201 {invitation_id, email, role, token, expires_at}`，`token` 仅此一次返回 | 422 邮箱格式非法或角色非法（含 `owner`）；409 已有同邮箱 pending 邀请 |
| `GET /invitations` | `admin`/`owner` | — | `200 {invitations:[{id,email,role,status,created_at,expires_at}]}`，不含令牌或摘要 | 401/403 |
| `DELETE /invitations/{invitation_id}` | `admin`/`owner` | — | `200 {invitation_id, revoked: true}` | 404 邀请不属于本租户；409 状态已非 pending（含已过期、已接受、已撤销） |
| `GET /audit-events` | `admin`/`owner` | `?limit=50&before=<ISO8601>`，`limit` 上限 100 | `200 {events:[{id,actor_user_id,action,object_type,object_id,metadata,created_at}]}`，按 `created_at` 倒序、同秒按 `id` 稳定次序 | 401/403 |
| `POST /api/v1/invitations/accept` | 任何已登录用户 | `{token}` | `200 {tenant_id, tenant_name, role}` | 401 未登录；403 登录邮箱与邀请邮箱不一致；410 令牌无效 / 已被使用 / 已撤销 / 已过期（同一文案，不区分原因）；409 已是该租户 active 成员 |

### 5.1 统一判定顺序

同一请求可能同时命中多条拒绝条件，服务端按此固定顺序判定，测试按此断言状态码：

1. 会话有效性（401）
2. 写操作的 CSRF（403）
3. 请求者与路径租户的成员关系与租户状态（403）
4. 请求者角色是否满足该动作（403）
5. 输入格式与取值校验（422，含请求体 schema 与服务层的非法角色/非法邮箱）
6. 目标资源在该租户内的存在性与可用性（404）
7. 业务保护规则（owner 唯一性、自移除、pending 唯一、邀请状态机、复活角色规则）（409）或过期/失效（410）

非法角色与非法邮箱不可能命中任何资源，因此先于存在性判定；邀请的 `expires_at` 判定属于第 7 步之前的状态归一化：状态改变路径（接受、撤销）先把命中过期的 pending 写为 `expired`，再按新状态语义响应；只读列表仅在展示层归一化，不写库。

### 5.2 兼容性核查

- 新增端点不改动 `/api/v1/auth/*`、`/api/v1/tenants`（列表与创建）、`/api/v1/tenants/{t}/jobs*` 的请求体与成功响应形状。
- `GET /api/v1/auth/me` 与 `GET /api/v1/tenants` 已返回 `role`，前端无需改造即可显示新角色。
- 存量角色取值假设必须**核实而非默认**：实施前在开发库与测试库执行 `SELECT role, status, count(*) FROM memberships GROUP BY role, status` 并把结果写入 `docs/09`；据此确认 `POST /jobs` 收紧到 `member+` 不会把既有可用调用方挡在门外。若发现除 `owner`/`member` 之外的取值，停止发布并回到本节修订矩阵。

## 6. 关键流程

### 6.1 创建邀请

1. 按 §5.1 顺序完成认证、CSRF、成员关系与角色判定（`admin`/`owner`）。
2. 规范化邮箱，校验角色属于 `{reviewer, member, admin}`。
3. 生成 `token = secrets.token_urlsafe(32)`（256 bit 熵），库内只写 `sha256(token)`。
4. 插入邀请；命中部分唯一索引则返回 409 且不写审计。
5. 同一事务写 `member.invited` 审计事件（按 §4.3 填 `object_type`/`object_id`/`metadata`）。
6. 响应一次性返回令牌原文；由管理员自行转交，本期不发邮件。

### 6.2 接受邀请

1. 认证 + CSRF 判定（该端点不要求路径租户成员身份）。
2. 以 `sha256(token)` 摘要查询邀请。未命中 → 410。
3. 状态归一化：若 `status='pending'` 且 `expires_at <= now`，写为 `expired` 后返回 410。
4. 非 `pending`（`accepted`/`revoked`/`expired`）→ 410，与无效令牌同一文案，避免状态探测。
5. 比较 `User.email` 与 `Invitation.email`（两侧均为规范化小写）。不一致 → 403，邀请状态保持不变。
6. 若该用户在此租户已有 `active` 成员关系 → 409，且不得改变邀请状态（避免用拒绝响应消耗一次性令牌）。若历史成员关系的 `status='removed'`，接受时复活为 `active`，但**沿用原角色**：邀请不得成为 admin 提升或降低既有成员权限的通道；若原角色是 `owner` 而邀请人当前不是该租户 `owner`，返回 409。
7. **条件更新保证一次性**：`UPDATE invitations SET status='accepted', accepted_at=?, accepted_by=? WHERE id=? AND status='pending'`；影响行数为 0 说明被并发请求抢先，直接 410 且不创建成员关系。
8. 同一事务内提交 `Membership(role=invitation.role, status='active')` 与 `member.invitation_accepted` 审计；`(tenant_id, user_id)` 既有唯一约束作为并发下的最终兜底。
9. 客户端重新拉取 `/api/v1/auth/me` 后即可看见新租户。

### 6.3 移除成员

1. 按 §5.1 判定后确认目标在本租户且 `status='active'`，否则 404。
2. 保护规则：不得移除自己；`admin` 只能移除 `member`/`reviewer`；目标是 `owner` 时移除者必须是 `owner`，且移除后必须仍有其他 active `owner`，否则 409。
3. 写 `status='removed'`（保留行以维持历史归属）；审计 `member.removed`，`object_type='membership'`、`object_id=` 被移除用户 ID、`metadata.role=` 其原角色。
4. 不撤销被移除者的登录会话：其后续对该租户任一端点的请求都会因成员关系判定失败得 403；对其他租户的访问不受影响。

### 6.4 变更角色

1. 仅 `owner`（第 4 步判定）。
2. 拒绝：目标不是本租户 active 成员（404）、请求者不是 owner（403）、角色取值非法（422）、变更自己的角色、或目标当前是 `owner`（409）。由于本期不允许邀请 `owner` 也不允许把成员升为 `owner`，"降级最后一名 owner" 已由"目标是 owner"一条覆盖，无需重复计数（所有者唯一性由 §6.3 的移除保护保证）。
3. 写新角色并记录 `member.role_changed`，`metadata={"from": ..., "to": ...}`。

### 6.5 撤销邀请

1. `admin`/`owner`；状态归一化后仅 `pending` 可撤销。
2. 条件更新 `WHERE id=? AND status='pending'`，0 行 → 409（并发或已使用）。
3. 置 `revoked` 并写 `member.invitation_revoked` 审计。

### 6.6 判定实现

`app/platform/http/dependencies.py` 增加 `require_roles(*roles)` 依赖工厂：在 `get_tenant_context` 之后读取 `context.membership.role`，不在允许集合内抛 403。路由在声明处列出所需角色，端点函数体内不出现散落的 `if role ==` 判断。

## 7. 安全与数据约束

- 令牌熵 256 bit，仅以摘要入库；默认 7 天有效；一次性使用。
- **未认证路径不得成为探测工具**：接受邀请对无效/已用/已撤销/已过期一律 410 同一文案；创建邀请不对"该邮箱是否已注册"给出任何区分。租户内成员与邀请列表对 `admin`/`owner`（邀请）和全部 active 角色（成员）返回明文邮箱，属产品要求的协作目录可见性，不属未认证泄露。
- 角色、成员状态、审计内容只出现在服务端判定中；客户端传入的角色字段一律忽略。
- 审计查询强制携带租户上下文，跨租户读取 403；不存在按 `tenant_id` 直读审计的公开路径。
- `metadata` 采用**键名白名单 + 未知键丢弃**：服务层只接受 §4.3 表中列出的键，其余丢弃并在开发日志记录被丢弃的键名（不记录值）。禁止文档正文、OCR 文本、服务器绝对路径、令牌、密码散列与密钥进入 `metadata`、错误信息与日志。
- 只追加保证在应用层：无 UPDATE/DELETE 入口，`AuditEvent` 不暴露任何写回接口。数据库层触发器与 RLS 属后续（§10.4）。
- 文件与存储路径边界沿用 `docs/10`：`resolve_storage_path()` 在写入时做键—落盘往返校验。
- **历史无租户演示入口不得触达租户数据**：`JobManager.get_job` 要求任务租户归属与请求上下文完全相等（含内存缓存命中），Worker 走独立的 `load_for_processing` 内部装载路径。本期评审发现旧的 `tenant_id=None` 回退会让匿名 `/api/jobs/{id}` 读到租户任务与其 Excel，已修复并由 `test_legacy_demo_api_cannot_reach_tenant_scoped_jobs` 固定。
- 接受邀请对"邮箱不匹配"返回 403、对"令牌无效/已用/已过期"返回 410：该判定要求已登录身份，且令牌为 256 bit 不可枚举，因此不构成对外探测 oracle；换来的是被邀请人走错账号时能看到可执行的提示。

## 8. 迁移与回滚

- 新增 `invitations` 与 `audit_events` 两张表、索引与部分唯一索引；单个 Alembic revision，`down_revision` 指向实施时的当前 head（撰写时为 `e3a9c2d4176f`，提交前须以 `alembic heads` 复核，避免多分支 head）。
- 不回填历史数据：本期之前的成员变更与导出动作没有审计记录，这是已知缺口，必须在 `docs/09` 与 `docs/06` 未覆盖项中声明。
- 现有表与 JSON 快照结构不变；无需停机。
- `downgrade` 逆序删除索引与两张表。回滚前提：先回退应用代码；回滚会丢弃全部邀请与审计历史（含未完成的邀请），不含其他表数据。该数据损失需在发布检查单中显式确认。
- 验证顺序：空库 `upgrade head` → `downgrade -1` → 再 `upgrade head` → `alembic check` 无模型漂移。PostgreSQL 上的部分唯一索引与 `JSON` 行为在未连接真实实例前记为风险，不得声明已验证。

## 10. 本期边界与后续决策

1. 通知渠道：令牌如何送达被邀请人（邮件/复制链接/重发）需产品确认；本期只提供 API 与一次性返回值，因此**本期无法端到端验收"外部人员受邀加入"**，只能验收已注册邮箱的加入闭环。
2. 未注册用户入驻：邀请即注册（设置密码/验证邮箱）与自助注册是否同时开放，属 `docs/08` 待确认决策 #2。
3. 所有者转让：需要明确转让后原 owner 角色与保护顺序，另立设计。被移除的成员可由管理员重新邀请，接受时复活原成员关系行（§6.2）。
4. 审计治理：保留周期、客户可导出的审计格式、数据库层触发器/RLS 保护待 PostgreSQL 基线确定。
5. `request_id` 关联：**已实现（维护轮 M3，2026-10-10）**。`app/platform/request_context.py` 提供中间件（生成或沿用 `X-Request-ID`、校验长度与字符集、响应头回填）、`contextvars` 上下文、日志过滤器与统一日志配置；`audit_events.request_id` 列由迁移 `e1f4c7a29d63` 加入（可空，不给默认值）。审计写入自动从上下文取 ID，显式传值优先；无请求上下文（Worker、派发器、脚本）写 `NULL` 而不编造。见 `docs/06 §5.26`。
6. 平台管理视图（FR-042）：平台管理员跨租户运营访问的授权模型必须独立设计，不通过放宽本期矩阵实现。
7. 复核角色接入（FR-023）：实现复核端点时复用 §3 矩阵行与 `require_roles`，不新增判定机制。
