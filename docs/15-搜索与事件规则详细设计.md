## 1. 目标与范围

两块能力：

1. **租户内检索**：让客户能用一个查询词找回"哪份文档提到过这个号码/这段文字/这个客户名"，覆盖文件名、解析原文与已提取字段值。
2. **事件规则**：让租户管理员把已经存在的领域事件（结果已确认、任务失败等）变成可配置的动作，并留下可追溯的运行记录与失败重试。

本期不实现：跨租户运营搜索、语义/向量检索、审批流与多人会签、外部通知渠道投递（邮件/IM 网关，见 `docs/08` R-011）、Webhook 与版本化开放 API（阶段 F）、检索结果排序打分与高亮分词。

## 2. 现状缺口（证据）

- 领域事件已经落库（`domain_events` 带 `published_at`、`publish_attempts`），但**没有任何消费者**：`grep` 全仓只有写入路径，`published_at` 从未被读取或推进。事件到此为止，FR-040 的"触发"没有落点。
- 没有检索入口。`docs/14` 的 `q` 只做文件名精确匹配，字段值与原文只能靠翻列表；`document_texts.text` 与 `extraction_results.values` 无法按关键词命中。
- `labels`、`retention_status` 等元数据无索引化副本，检索若直接对 JSON 列做 `LIKE` 会把方言差异（SQLite `JSON` 与 PostgreSQL `jsonb` 的文本化行为不同）写进业务查询。
- 没有"谁在什么时候按什么规则动了什么"的记录，自动化一旦改数据就无法回溯。

## 3. 上下文与聚合

新增 `search`（检索读模型，支撑域）与 `automation`（事件规则，支撑域）两个上下文。二者都只消费别的上下文的既成事实，不反向修改聚合。

| 聚合根 | 不变式 |
|---|---|
| `SearchEntry` | 一条索引条目只属于一个租户且只描述一种来源：`kind ∈ {filename, text, field}`；`(document_version_id, kind, field_name)` 唯一（`field_name` 对非字段类型为 `''`）；内容随源数据同事务重建，源删除即级联删除 |
| `EventRule` | 规则属于单租户；`status ∈ {active, paused}`；`event_type` 与 `action.type` 必须来自登记过的白名单；每次有效编辑 `version + 1`，历史 `RuleRun` 仍记录执行时的版本号；`condition` 只允许标量键值对，且键必须是该事件类型真实携带的载荷字段（`CONDITION_KEYS` 注册表），否则 422 |
| `RuleRun` | 一次事件 × 一条规则 × 该规则当时版本至多一条运行记录（`delivery_key` 唯一）；`status ∈ {applied, skipped, failed}`；失败重试不新增运行记录，只推进同一条的尝试次数；`detail` 入库前抹掉服务器绝对路径 |
| `NotificationRequest` | 通知意图与真实投递分离：只记录"该发给谁、因为哪条规则、关于哪个聚合"；无投递渠道时停在 `pending`，绝不假装已送达 |
| 规则动作 | 默认只允许安全动作：给文档加标签、登记待办通知。不允许自动确认结果、自动删除文档、自动改保留状态或调用外部系统 |

## 4. 数据模型

新增表（单个 Alembic revision）：

- `search_entries`：`id`、`tenant_id`（FK CASCADE，索引）、`document_id`（FK CASCADE，索引）、`document_version_id`（FK CASCADE，非空）、`kind`（String(16)）、`field_name`（String(120)，默认 `''`）、`content`（Text）、`updated_at`；唯一 `(document_version_id, kind, field_name)`，复合索引 `(tenant_id, kind)`。三类来源都挂在文件版本上，因此不需要部分索引。
- `event_rules`：`id`、`tenant_id`（FK CASCADE，索引）、`name`（≤80）、`event_type`（String(64)）、`condition`（JSON，标量映射）、`action_type`（String(32)）、`action_params`（JSON）、`status`（String(16)，默认 `active`）、`version`（Integer，默认 1）、`created_by`（FK SET NULL）、`created_at`/`updated_at`；同租户规则名唯一（规则只有 `active`/`paused`，没有退役态，因此用普通唯一约束而不是部分索引），复合索引 `(tenant_id, event_type, status)`。
- `rule_runs`：`id`、`tenant_id`（FK CASCADE，索引）、`rule_id`（FK CASCADE，索引）、`rule_version`、`event_id`（FK `domain_events.id` CASCADE，索引）、`event_type`、`status`、`detail`（String(500)，可空）、`attempt_count`（Integer，默认 0）、`delivery_key`（String(160)，非空且唯一）、`created_at`/`finished_at`。
- `notification_requests`：`id`、`tenant_id`（FK CASCADE，索引）、`recipient_user_id`（FK SET NULL，可空）、`rule_id`（FK SET NULL，可空）、`subject`（String(120)）、`body`（String(500)）、`status`（String(16)，默认 `pending`）、`object_type`/`object_id`、`created_at`、`delivered_at`（可空）。

检索实现取舍：`content` 用 `LIKE` 命中，查询词长度下限 2、上限 60，`%`、`_`、`\` 一律转义后再包 `LIKE`，避免用户输入变成模式匹配。SQLite 的 FTS5 与 PostgreSQL 的 `to_tsvector` 通过 `search` 上下文外的适配器替换（NFR-004），本表结构对两种后端都够用——它已经把"要搜什么"物化成行，换全文索引只是换命中方式。

## 5. API 契约

判定顺序沿用 DOC-DD-003 §5.1，前缀 `/api/v1/tenants/{tenant_id}`。

| 端点 | 角色 | 说明 |
|---|---|---|
| `GET /search?q=&kind=&doc_type=&limit=&offset=` | 任意 active 角色 | 命中条目列表（同一文档可有多条，按 `document_id`/`kind`/`field_name` 稳定排序）；`kind ∈ {all, filename, text, field}` 其他值 422；`q` 去除首尾空白后长度须 2–60，否则 422；响应含 `document_id`、`document_version_id`、`kind`、`field_name`、`doc_type`、`total` 与 `snippet`（命中处 ±40 字符，换行折成空格），不含存储路径与整篇原文 |
| `GET /automation/rules` | 任意 active 角色 | 规则列表（含 `version`、`status`、运行统计） |
| `POST /automation/rules` | `admin`/`owner` | 201； `{name, event_type, condition?, action}`；`event_type` 与 `action.type` 必须来自白名单，条件值只能是标量；动作参数按类型二次校验（标签同 `docs/14` 规则） |
| `PATCH /automation/rules/{rule_id}` | `admin`/`owner` | 任一业务字段变更即 `version + 1`；`status` 切换（active/paused）同样计版本；无实际变化 422、跨租户 404、重名 409 |
| `POST /automation/rules/{rule_id}/run` | `admin`/`owner` | 立即用该规则消费当前待投递事件，返回 `{applied, skipped, failed}` 计数 |
| `POST /automation/dispatch` | `admin`/`owner` | 只消费本租户待投递事件（`published_at IS NULL`，单批 ≤ `min(limit,100)`），逐条评估全部 active 规则；返回 `{consumed, applied, skipped, failed, published}` 计数，条目级明细在 `/automation/runs`；同时写 `automation.dispatched` 审计 |
| `GET /automation/runs?rule_id=&status=&limit=&offset=` | 任意 active 角色 | 运行日志倒序分页 |
| `GET /automation/notifications?status=&limit=&offset=` | `admin`/`owner` | 待办通知登记（无投递渠道时全部为 `pending`） |

白名单：可订阅事件 `job.succeeded`、`job.partial`、`job.failed`、`result.confirmed`、`result.rejected`、`result.revised`；可执行动作 `tag_document`（参数 `label`）、`create_notification`（参数 `subject`、`body`）。

## 6. 关键流程

1. **索引重建**：`review.record_machine_result` 与 `review.revise` 在写结果/文本的同一事务内调用 `search.service.reindex_version(...)`，按 `(document_version_id, kind, field_name)` upsert；机器重跑只更新内容不新增行；结果被删除时随外键级联清理。
2. **检索**：`search_entries` 上带租户条件查询，按 `(document_id, kind, field_name)` 稳定排序后返回命中条目（同一文档可以有多条命中，不做预先聚合），并为每条生成上下文片段。比较方式固定为 `lower(content) LIKE lower(转义后的 %词%)`：英文靠 `lower()` 达成大小写不敏感，中文在 SQLite 与 PostgreSQL 的 `lower()` 都是恒等映射，因此同样成立；小写只用于比较，库内 `content` 原值不改。
3. **事件消费**：`automation.dispatch` 取 `published_at IS NULL` 的事件（按 `occurred_at` 升序，单批上限 100），对每条事件找出租户内 `status='active'` 且 `event_type` 相同、`condition` 全等的规则；为每个 (事件, 规则) 组合以 `delivery_key = "{event_id}:{rule_id}:{rule_version}"` 插入 `rule_runs`，插入运行记录同样走保存点，`IntegrityError` 即视为已被并发消费者写走（两个 dispatch 同时跑不会各记一条）；已 `applied`/`skipped` 的组合直接跳过，动作成功 → `applied`，动作在保存点（`db.begin_nested()`）里执行，抛领域错误（`AccessError`/`ValueError`）时保存点回滚，不会留下「运行记录失败但前几份文档已经改过」的中间态；随后记 `failed` + `detail`（先抹掉绝对路径再截断 500）并累加同一条记录的尝试数。整批 dispatch 在"没有任何匹配规则处于 `failed`"时推进 `published_at`；按单条规则手动试跑（`/rules/{id}/run`）只处理该规则订阅的事件类型且**不推进** `published_at`，否则跑一条规则会把同租户其他事件永久标成已投递（无规则匹配也算投递完成，否则队列会被无关事件堵死），失败事件留在队列里由下次 dispatch 继续；已被消费的历史事件不回放。动作级以上的异常（数据库故障）不做吞掉处理，直接上抛由调用方重试整批。
4. **动作执行**：`tag_document` 走 `documents.service.add_label`（只追加单个标签、同租户、审计走 `document.metadata_updated` 并带 `rule_id`）；人工用 `PATCH /documents/{id}` 全量替换 `labels` 时会连带覆盖规则加上的标签，这是「整表单替换」语义的既有代价；`create_notification` 只写 `notification_requests`。两者都不绕过角色判定，也不引入"系统用户"越权通道：动作以事件所属租户内的规则作者身份登记审计，并在 `metadata` 里带 `rule_id`，便于回溯是谁的配置改的数据。

## 7. 安全与兼容约束

- 检索与规则的所有查询强制 `tenant_id` 条件；跨租户 ID 一律 404；`search_entries` 通过外键与租户列双重约束。
- 查询词按不可信输入处理：转义 `LIKE` 通配符、限长、不拼进原生 SQL；命中片段只取该文档自有内容，绝不跨租户拼接。
- 索引内容与通知正文都是**不可信外部内容**：通知列表接口只返回纯文本，审计与 `rule_runs.detail` 不得包含文档正文、服务器绝对路径、令牌。
- 规则只能由 `admin`/`owner` 创建与修改，`member`/`reviewer` 只读；规则动作集合固定，不提供任意脚本或 HTTP 回调（阶段 F 的 Webhook 才有出口，且需签名与密钥轮换）。
- 规则版本不可回退执行：历史 `RuleRun` 记录 `rule_version`，配置改了不会改写既有日志。
- 兼容：不改既有端点形状；`domain_events` 复用已有的 `published_at`/`publish_attempts` 列，不新增迁移字段。
- `published_at` 由此被赋予「已被自动化消费」的含义（`docs/13` 的原义是「已对外投递」）：阶段 F 的 Webhook 消费者必须另建投递状态列，不能复用这一列，否则历史事件对其不可见（登记为 `docs/08` R-014）。
- 规则与运行记录都没有删除端点：`rule_runs` 对 `rule_id`/`event_id` 用 CASCADE，`notification_requests.rule_id` 用 SET NULL（待办比规则更该留下）。两条路径当前都不可达，差异保留给将来的保留策略讨论。

## 10. 已知取舍

- `LIKE` 检索在数据量增长后会退化成顺序扫描：本期以"租户 + kind"复合索引和结果上限兜住，真实分词/全文索引待有容量数据后接入（`docs/08` R-010 的容量假设未确认）。
- 索引是**读模型**：与源数据同事务写入，不做异步补偿，因此处理路径多几次写放大；换来的是不会出现"搜不到刚改完的值"。
- 通知只有登记没有投递：没有确认的投递渠道前，宁可让待办堆在库里，也不把"以为发出去了"当成已完成（`docs/08` R-011）。
- 规则不自动在事件产生时执行，而由 dispatch 批处理触发：单进程内没有可靠的消费者，把触发点显式化比假装"实时"更容易排障；接入持久化队列后 dispatch 可原样搬到 Worker。
