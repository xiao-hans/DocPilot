## 1. 目标与范围

让平台运营能回答三个问题：服务是否可用、每个租户占了多少、哪些处理在失败。交付三件东西：

1. **健康与就绪探针**：进程存活与"能否服务真实请求"（数据库可达 + 迁移已到 head）分开。
2. **租户用量**：单个租户自视图（文档、文件版本、字节、任务与结果状态、待投递事件、规则数）。
3. **平台用量**：平台管理员的跨租户聚合榜，用于容量判断与失败集中发现。

本期明确**不做**：开放 API 密钥体系、配额强制、计费、自动扩缩容。Webhook 出站投递原也在"不做"之列，理由当时写在案：**没有批准的外部出口与密钥管理流程，把"签名 + 重试 + 密钥轮换"写成代码会在无对端验证的情况下上线一个真实的外呼通道**。阶段 G14（2026-10-04）用另一种方式收口这个判断——机制交付但**默认关闭**：没有 `WEBHOOK_MASTER_KEY` 就不允许建端点（409）、投递进程直接拒绝启动，出站目标默认只允许 https 且解析到回环/内网即拒（`docs/21 §5`）。"写完也无法验证送达到"这半句由假传输层的验签用例回答：签名覆盖的正是实际发出的那串字节，篡改一个字节就验不过。**该处理已由负责人 2026-10-04 认可（答复：保留，默认关闭即可，见 `docs/19 §5`）**。仍然在案的运维前置条件不变：部署侧密钥流程（谁生成、存哪儿、怎么轮换）与是否放行内网目标仍未定，联网部署在定下来之前不该设置这个主密钥。

## 3. 上下文与不变式

新增 `operations`（运营读模型，通用域）。它不拥有聚合，只从各上下文的表里读计数。

| 视图 | 不变式 |
|---|---|
| 租户用量 | 数值只来自该租户的行；结果状态与保留状态的出现次数等于库内实际值；不返回文档正文、文件名之外的内容与任何存储路径 |
| 平台用量 | 平台管理员身份**不授予**任何客户数据读取权（`docs/03 §5`）：本视图只输出计数与租户标识，不含文件名、正文、字段值、邮箱 |
| 就绪探针 | 只有数据库可达且 `alembic_version` 等于脚本目录的 head 才算 ready；head 比对失败时返回具体差值而不是 500 |
| 失败摘要 | 只统计终态为 `failed`/`partial` 的任务与 `status='failed'` 的运行记录，按最近窗口计数；不返回错误文本 |
| 租户失败明细（G10） | 本租户的失败任务与失败规则运行，**允许**出现该租户自己的任务号与错误原文；绝不出现别的租户的行。可见角色与 `/usage` 自视图一致 |
| 平台失败分布（G10） | 跨租户只输出**错误代号与计数**（哪一类错误、影响了几个租户、最后出现时间），不含错误原文、文件名、正文、邮箱，也不含任务号。要看原文必须回到租户端点，那里由成员关系与角色矩阵把关 |

## 4. 数据来源与口径

不新建表。口径全部由现有表派生，避免"运营数字与业务表不一致"这种第二真相：

- 文档与版本：`documents`、`document_versions`（`size_bytes` 求和为存储字节）。
- 任务：`processing_jobs.status` + `attempt_count`。
- 结果：`extraction_results.state`、`result_revisions`（人工修订量）。
- 自动化：`domain_events`（`published_at IS NULL` 为待投递）、`event_rules`（active 数）、`rule_runs.status`。
- 检索：`search_entries` 行数。
- 保留治理：`documents.retention_status` 分布。

窗口参数 `days`（1–365，默认 30）只作用于"最近失败"和"最近新建"两类计数，避免全表扫描随数据量漂移。

## 5. API 契约

| 端点 | 角色 | 说明 |
|---|---|---|
| `GET /healthz` | 无认证 | 进程存活；恒定 200，响应 `{status: "ok"}`，不查数据库 |
| `GET /readyz` | 无认证 | 就绪；`{status: "ready"|"unavailable", database: bool, migration: {current, head, in_sync}}`，未就绪时 503。响应不含连接串与文件名 |
| `GET /api/v1/tenants/{tenant_id}/usage?days=` | 任意 active 角色 | 本租户用量快照 |
| `GET /api/v1/platform/usage?days=&limit=&offset=` | 平台管理员 | 跨租户聚合，按 `documents` 数倒序；`limit` ≤ 100；无租户上下文要求（平台身份不等于租户身份） |
| `GET /api/v1/tenants/{tenant_id}/usage/failures?days=&limit=&offset=` | 任意 active 角色（G10） | 本租户失败明细：任务号、状态、尝试次数、最后一次尝试的错误原文、ISO 时间，外加错误代号与中文标签 |
| `GET /api/v1/platform/usage/failures?days=` | 平台管理员（G10） | 跨租户失败分布：只有代号、任务数、受影响租户数、最后出现时间；`truncated` 与 `scan_cap` 如实说明是否看全 |

`/api/v1/platform/*` 的判定独立于 `require_roles`：后者解析的是租户成员关系，平台管理员没有成员关系，必须先看会话用户的 `is_platform_admin`，再落审计。

## 6. 关键流程与约束

1. **就绪检查**：`SELECT 1` + 读取 `alembic_version` 与脚本目录 head 比对。任何异常都吞成 `unavailable` 并带上分类布尔值，探针本身不得因为数据库故障抛 500——那会让编排器把"探针挂了"误读成"服务挂了"。
2. **平台视图审计**：`audit_events.tenant_id` 是非空外键（阶段 B 既定约束），平台管理员没有成员关系，因此不存在「属于平台的审计行」。实现改为：平台每列出 N 个租户，就为这 N 个租户各写一条 `platform.usage_viewed`（`actor_user_id` 为平台账号，`metadata` 只含 `scope`/`window_days`/`rows`）。这样租户管理员在自己的审计流里能看见「平台读过我的聚合」，比把记录挂在某条无关租户上更可核查，也不需要在审计表上开一个非租户行。
3. **不越权**：平台视图不接收任何文档/任务 ID 参数；任何按 ID 的客户数据读取仍走租户端点与角色矩阵。
4. **错误代号怎么来（G10）**：`classify_failure` 是启发式——按已知处理链路的措辞给出稳定代号（超时 / 队列不可用 / 提取引擎不可用 / 文档无法读取 / 未提取到结果），规则**先命中先得**，所以更具体的词排在泛化词前面；认不出的只给 `unclassified-<sha8>` 与文本长度，**不回显原文**。这意味着代号是"便于聚合的近似分类"，不是新的权威事实：权威永远是租户明细里的原文。
   平台分布有扫描上限（默认 5000 行，按 `finished_at` 倒序），撞顶时 `truncated=true` 并连同 `scan_cap` 一起返回——宁可报"看不全"，也不给一个看起来完整的分布。审计动作 `platform.usage_failures_viewed` 已在 `app/services/audit.py` 的登记表里登记，未登记的动作为拒绝写入（沿用既有约束）。
4. 兼容：新增端点，既有行为不变。

## 9. 已知取舍

- 运营数字全部实时聚合而非物化：租户量级下可接受，量级上来后需要定时汇总表（那时必须定义刷新与滞后 SLA，避免"看起来实时其实是昨天"）。
- 平台视图不带失败明细：明细按租户走 `/jobs?status=failed`，跨租户下钻等于绕过角色矩阵。
- Webhook 不在本期：没有对端与密钥流程的出站通道，写完也无法验证"送达到"，不如留白并显式记为未实现。


## 8. 管理界面（G12，2026-10-04）

四个只读端点此前一直只有 API，没有界面。G12 补上 `OperationsPanel.vue`（工作区顶栏"运营"），布局就是这条边界的两层演示：

| 区块 | 数据来源 | 能看到什么 |
|---|---|---|
| 平台用量 | `/api/v1/platform/usage` | 租户数、文档数、存储字节、任务状态计数、窗口内失败数、待投递事件、规则失败数；另有快照退役观察期读数两条：`job_rebuild_incomplete_total`（审计表累计条数，跨重启可核对，`docs/20 §6.1` 的删列门禁看这条）与 `job_rebuild_incomplete`（本进程计数，重启归零）|
| 失败分布 | `/api/v1/platform/usage/failures` | 错误代号 + 中文标签 + 次数 + 受影响租户数 + 最近出现时间；撞扫描上限时显示"分布不完整" |
| 本工作空间用量 | `/api/v1/tenants/{id}/usage` | 文档/版本/字节/任务/结果状态/人工修订/活跃规则/待投递事件/检索条目 |
| 本工作空间失败明细 | `/api/v1/tenants/{id}/usage/failures` | 任务号、状态、尝试次数、错误代号**与原文** |

设计上的三条约束：

1. 平台区块**没有**"点开看某租户失败原因"的入口。不是漏了，是后端在那个面上就不给原文；界面如果给个展开箭头再去请求租户端点，等于用 UI 绕过角色矩阵。
2. "运营"入口只对平台身份显示，但**隐藏入口不是权限控制**：面板用 `platformAdmin` 决定是否发起平台请求，真正的把关仍是后端 `require_platform_admin`。非平台身份直接请求仍是 403。
3. 数字一律现取现算，界面不做二次汇总（避免又一个真相源）；窗口选择只有 7/30/90 三档，与后端的 `days` 参数同语义。

验收是浏览器实测，不是接口自测：Playwright 12 条用例在**一次性本地进程**与 **Compose 依赖栈**两种形态下各 12/12 通过，其中新增两条专门盯这个面板——一条断言平台区块只出计数且不含文件名、切窗口后仍无错误；一条真上传一份扩展名合法但内容损坏的 PDF，让任务在链路里失败，再断言它在"本工作空间失败明细"里出现且原文非空。
