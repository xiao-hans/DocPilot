一致性判定：任务终态与 `extraction_results` 必须同源——上表“有终态但没有规范化结果”为 0 才算通过。

队列深度随时间变化（每秒采样，抽稀展示）：

| 秒 | 已终态 | 待派发 | 最老等待(秒) | 消费者 |
|---|---|---|---|---|
| 0.1 | 0 | 100 | 8.102433 | 8 |
| 1.2 | 24 | 71 | 3.585941 | 8 |
| 2.2 | 72 | 23 | 0.873369 | 8 |
| 3.3 | 100 | 0 | — | 8 |

读这两组数字时必须带着两条口径说明，否则会把测量读成结论：

- 时间线里的「最老等待」取自 `queue_backlog()`，它按派发行**最后更新时间**算年龄；派发器投递成功会刷新这一列，所以它量的是「最久没有任何动作」，不是「最久的排队时间」——随后掉到亚秒级正是这个原因。真正的排队等待与调度延迟以上表两行为准（`job_dispatches.created_at / publish_confirmed_at → job_attempts.started_at`）。这个区别对 `/readyz` 的判据没有影响（它要的就是「有没有卡住不动」），但把它当排队指标用会低估积压。
- Worker 冷启动单独列了一行（5.2 秒）：脚本先等消费者到位再造任务，所以上表的「调度延迟」不含进程导入应用的时间；「排队等待」那一行则包含任务创建循环，两者相差一个数量级，引用时必须说清是哪一个。真实部署里冷启动成本发生在扩容时，不该混进调度指标，也不该被忘掉。

## C. 大对象、分页与导出（TC-PERF-003）

大对象 18.4 MB（上传上限配置 `MAX_UPLOAD_MB=32`）。RSS 变化按操作前后差值测量，负值表示期间发生回收。

| 操作 | 耗时 (秒) | RSS 变化 |
|---|---|---|
| 写入对象（流式 `put`） | 0.03 | 0.2 MB |
| 解析前的临时落盘（`local_path`，1 MB 分块） | 0.0 | 0.0 MB（临时文件 18.4 MB 在磁盘，不驻留内存） |
| 分块流式读（1 MB） | 0.01 | 0.0 MB / 读了 18.4 MB |
| 整对象读（`read_bytes`） | 0.01 | 18.4 MB / 读了 18.4 MB |

深翻页（该租户 1011 份文档，`limit=50`）：首页 18.7 ms、中间 15.3 ms、尾页 16.2 ms。

宽任务导出（1000 份文档、单任务）：上传+规范化结果 31.77 秒、写入侧 RSS 变化 6.8 MB；读导出行并重建任务快照，RSS 变化 -0.5 MB；XLSX 0.34 秒 / 1.0 MB（32681 字节）；CSV 0.01 秒 / 0.2 MB。

- 代码事实（不依赖本轮数字）：`read_bytes` 一次性返回整个对象，而解析链路用的 `local_path` 按 1 MB 分块落盘。因此**面向用户的预览/下载接口必须走流式读**，否则单个大对象就能把进程内存吃满。
- 本轮实测：整对象读使 RSS 增加 18.4 MB（对象 18.4 MB），与上面的代码事实一致。
- 观测进程结束时 RSS 为 107.7 MB。
