## 1. 性能阈值（G-DEC-02）

### 1.1 现在能测到的与测不到的

| 维度 | 本轮实测（mock 提取器、同机 8 Worker、PostgreSQL） | 能否作为生产阈值依据 |
|---|---|---|
| 读路径时延 | 100 租户 / 1000 文档下 P95 3.9–12.8 ms，1800 次查询 0 失败 | 部分可以：数据规模只有 1000 文档，比目标小 3 个数量级 |
| 深翻页 | 单租户 1011 份文档，首页 18.7 ms / 尾页 16.2 ms，OFFSET 未见退化 | 同上，只覆盖到千级 |
| 队列调度 | 发布确认→开始执行 P50 831 ms；Worker 冷启动 20.8 秒 | 可以：与提取器无关，是链路自身开销 |
| 处理耗时 | mock 单次执行 P50 0.102 秒 | **完全不可以**：真实 OCR/LLM 会慢 2–3 个数量级 |
| 大对象内存 | 整对象读 RSS +18.4 MB（对象 18.4 MB，线性）；流式分块读 +0.0 MB | 可以：这是代码形状决定的，与机器无关 |
| 吞吐 | 1825.7 任务/分钟（100 任务、8 Worker、mock） | 不可以：分子是空任务 |

### 1.2 建议值

**建议 A（推荐）：把阈值拆成"链路阈值"和"处理阈值"两类，本轮只锁定链路阈值。**

| 类别 | 指标 | 建议阈值 | 依据 |
|---|---|---|---|
| 链路 | 租户内列表/检索接口 P95（≤10 万文档量级） | ≤ 200 ms | 本轮 1000 文档下 P95 12.8 ms；按 OFFSET 与索引扫描的增长留出 15 倍余量，待 10 万级复测收紧 |
| 链路 | 调度延迟（发布确认→开始执行）P95 | ≤ 2 s | 本轮 P95 985 ms，同机 8 Worker，无外部依赖 |
| 链路 | 队列积压可发现时延 | `/readyz` 在积压且无消费者时 ≤ 1 个探测周期内报 503 | 已在 G5 实现并自动化（`docs/06 §5.14`） |
| 链路 | 单请求进程内存增量 | 与对象大小无关（流式） | 已实测：整对象读线性增长，流式读不增长 → 阈值应写成"禁止在请求路径整对象读" |
| 处理 | 单任务端到端 P95、吞吐上限、持续时间、文档构成 | **暂不设定** | 唯一能测的 mock 数字没有参考价值；需要接真实提取器的一轮压测 |

这样切的理由：链路阈值今天就有证据，写进验收标准能立刻约束实现（例如"导出/预览不得整对象读"）；处理阈值一旦按 mock 数字写下，就会变成一句永远无法证伪也无法兑现的假承诺。

**建议 B（更保守）**：本轮完全不写数字，只写"阈值待真实提取器压测后评审"。代价是链路侧已经能约束实现的几条也一起丢掉。

### 1.3 需要谁定

链路阈值：技术负责人批准即可。处理阈值：需要业务方给出真实文档构成（扫描件占比、页数分布）与可接受等待时间，否则无法设计负载模型。

## 2. 数据保留与彻底删除（G-DEC-03）

现状：`Document.retention_status` 已有 `active` / `purge_scheduled` / `purged` 三态与租户管理面角色限制（`app/contexts/documents/service.py:17,20`），但**没有任何自动清除**：对象、派生文本、规范化结果、检索索引、审计事件都只增不减。

### 2.1 建议按数据类别分别定保留期（推荐值）

| 数据类别 | 建议保留期 | 删除范围 | 依据与影响 |
|---|---|---|---|
| 原始对象 + `document_versions` 行 | 租户可配置，平台默认**不设自动删除**，只做"标记 + 人工批准清除" | 对象、版本行、`document_texts`、`extraction_results`、`search_entries` | 文档是租户资产；自动删错不可逆。先给能力，不给自动化 |
| 人工修订历史 `result_revisions` | 与所属结果同生命周期 | 随结果删除 | 它是复核证据，单独保留会破坏"只追加链"的可解释性 |
| 审计事件 `audit_events` | 建议 **≥ 365 天**，之后按租户归档而非物理删除 | 归档导出后清理 | 审计是越权与合规调查的唯一证据链；`docs/11` 把它设计成只追加，物理删除等于销毁证据 |
| 事件规则运行日志 `rule_runs` / 通知登记 | 建议 **90 天** | 直接清除 | 排障价值随时间衰减最快，量增长也最快 |
| 任务快照 `processing_jobs.snapshot` | 见 §2.3 | — | 它不是保留策略问题，是双真相问题 |
| 孤儿对象（写失败补偿残留） | 立即清除，但**只清本次运行创建的前缀** | 按前缀删除 | 补偿已按任务前缀回收；跨租户批量清理需要批准 |

### 2.2 建议的落地顺序（推荐）

1. 先做**只报告的**保留期符合性视图：每租户列出"超过建议保留期的对象数 / 字节数 / 最老一条"，让业务方看到体量再决定删不删。
2. 再做**单次授权**的清除命令：必须带租户、带 dry-run、带"删除前后计数与摘要"输出，且默认拒绝（沿用 `assert_disposable_database` 那种命名守卫思路，把"要删什么"写死在参数里而不是脚本里）。
3. 最后才谈定时任务。当前没有任何批准，跳过 1、2 直接上定时删除是不可接受的。

### 2.3 与快照退役的关系

`processing_jobs.snapshot` 目前仍被 `JobRepository.get()` 用来重建 `Job`（`docs/17 §6`），所以"删快照列"不是保留策略而是迁移工作：先让 `Job` 构造脱离快照 → 备份 → 单独一个变更删列。建议把它从 G-DEC-03 里拆出来，作为独立收尾项（用户已列在待办第 3 项）。

### 2.4 需要谁定

保留期限与"是否允许自动删除"必须由业务/合规给出书面确认；技术上建议先交付 1、2 两步，不交付 3。

## 3. RPO / RTO（G-DEC-04）

### 3.1 已有测量输入（G7 对象卷演练，本机单节点冷副本）

| 测量 | 值 | 说明 |
|---|---|---|
| 卷级冷副本制作 | 1.0–1.3 秒 | 源容器 `docker pause` 期间复制卷；副本体量很小（本轮桶内 5 个对象） |
| 恢复实例就绪（能读出**摘要正确**的内容） | 20.8–26.9 秒 | 只 head 桶会早于真正可读约 20 秒，所以这个数必须是"读得出正确内容"的口径 |
| 端到端可核对 | 21.8–28.0 秒 | 副本 + 启动 + 就绪 |
| 演练可靠性 | 11 次里 1 次在"重建副本复跑"阶段失败（那次未留下失败签名，根因未知） | 见 §3.3，这条直接决定 RPO/RTO 能不能写 |

PostgreSQL 侧（G1）：`pg_dump -Fc` + 恢复到隔离库的演练已通过，耗时随数据量变化，本轮数据量下为秒级。

### 3.2 建议值

**建议（推荐）：本轮不写 RPO/RTO 数字，只写"测量方法与当前下界"。**

- RPO 下界：冷副本方式只能保证"上次成功副本时点"之前的数据不丢；由于副本制作本身不是每次成功（§3.3），当前**无法给出有证据的 RPO**。
- RTO 下界：单节点、同机恢复的实测下界约 22–28 秒（对象）+ 数据库恢复时间。这个数字**不包含**跨机传输、真实体量（1 TB 级）与生产网络，因此只能作为方法验证，不能作为承诺。

若一定要给数字，建议写成"目标 RPO ≤ 24 小时、RTO ≤ 4 小时（**待验证**，需要增量备份与跨机恢复演练）"，并在 `docs/07 NFR-003` 明确标注"未验证目标"，避免被下游引用为承诺。

### 3.3 阻塞项：冷副本不是每次都恢复得回来

G7 演练在 11 次运行里出现 1 次"重建副本后读不出内容"（同一次运行的前一份副本是正常的）。演练本身抓到了它——这正是第 8 步存在的意义——但它说明：

- `pause` + 文件系统级复制得到的卷副本，在 SeaweedFS 上**不保证**每次都是可读一致状态；
- 因此"对象数据已有可恢复备份"这句话目前**不能签**；能签的是"我们有能力发现某次备份不可恢复"。

建议的下一步（择一，需要批准）：

1. **改为逻辑级备份**：按 S3 API 逐对象复制到隔离桶，恢复时逐对象写回。慢，但每个对象都有摘要可核对，失败可定位到键。
2. **改用 SeaweedFS 原生复制/同步**（`volume.replicate` 或 `remote.sync`），把"副本一致性"交给存储层，演练只核对结果。
3. **保留冷副本但强制校验**：每次备份后立刻起隔离实例做全量摘要核对，核对不过就判定这次备份失败并重试——把"不可靠的副本"变成"可靠的过程"。

推荐 3 作为短期（改动小、立刻能把 RPO 写出来），1 作为中期兜底。

### 3.4 需要谁定

RPO/RTO 取值与备份周期是运维 + 业务共同决定；技术侧需要先选定 §3.3 的方案，否则任何数字都没有依据。
