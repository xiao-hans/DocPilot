## 1. 为什么必须留这份方案

阶段 D 起机器值与修订值都写 `extraction_results`，G4 又把 `/result`、`/excel`、`/export` 全部切到规范化结果，但 `processing_jobs.snapshot` 仍然活着，因为 `JobRepository.get()` 还用**整份快照**重建内存里的 `Job`：字段定义、文件清单、进度、告警、错误。后果是 R-013 说的双真相没有真正闭合——写路径有两个家，读路径还剩一个只认快照的重建入口。

留着它还有两个更实际的代价：每次状态变化都要重抄一份 JSON（写放大，且大任务的 `result` 会在快照里再存一遍）；任何"按字段查任务"的诉求都只能靠 JSON 展开，PostgreSQL 与 SQLite 的行为还不一致（`docs/08` R-016 的残留项之一）。

**结论：快照必须退役，但删列是破坏性动作，必须先有对账证明规范化源能完整重建，再谈删除。**

## 2. 快照里现在有什么，规范化源缺什么

`JobRepository.get()` 读的键，逐个给出目标归属（`→` 右侧为本方案落地后的唯一来源）：

| 快照键 | 现在的规范化源 | 缺口与处置 |
|---|---|---|
| `fields` | 有 `template_version_id` 时，冻结字段在 `template_versions.fields` | 内联字段（不引用模板版本创建的任务）没有家。→ 新增 `processing_jobs.field_definitions`（JSON，创建时写入后不可变）。规则：`template_version_id` 非空就只信模板版本，为空才读这一列；两处都有且不一致即视为脏数据，对账脚本必须报出来 |
| `files[]` | `document_versions`（按 `job_id` 关联）提供 `original_filename` / `storage_key` / `checksum` / `media_type` / `size_bytes` | `FileInfo` 的 `page_count`、`chars`、`ocr_applied`、逐文件 `error` 无处可存。→ 给 `document_versions` 增加这四列（它们本来就是"这一版解析出来的结果"）。`path` 是遗留进程内入口专用的绝对路径，G3 之后一律为空，**不迁移直接删**（`docs/09 §11`） |
| `progress` | 无 | 状态列 `status` 推不出 `progress`（`processing` 之下还有多个阶段）。→ 新增 `processing_jobs.progress` 列，与 `status` 同一事务写入，二者不可分开更新 |
| `result` | `extraction_results`（G4 起为 `/result`、`/excel`、`/export` 的权威源） | 无缺口。快照里的 `result` 副本直接消失 |
| `warnings[]` | 无 | 告警属于"某一次尝试的解析产物"。→ 新增 `job_attempts.warnings`（JSON） |
| `error` | `job_attempts.error`（最近一次尝试） | 无缺口 |
| `excel_path` | 无 | **不建列**。G4 起 `/excel` 每次按需构建，不再复用缓存文件；留着它只会重新引入"修订之后仍下载旧内容"那一类 bug |

`Job` dataclass 里 `excel_path` 字段随之删除；`FileInfo.path` 保留给纯内存场景（无租户入口已退役，用例里的沙箱进程内执行仍需要），但不再进快照。

## 3. 迁移顺序（每个修订都可单独回滚）

1. ✅ **R1 扩容（可空，不动读路径）**（2026-10-04 已合入）：`processing_jobs.field_definitions`、`processing_jobs.progress`、`document_versions.page_count/text_chars/ocr_applied/parse_error`、`job_attempts.warnings`。全部可空——可空意味着"还没回填"，不需要默认值猜测。
2. ✅ **R2 双写**（2026-10-04 已合入）：创建与处理链路在写快照的同一事务里写这些新列（写旧列的能力此时保留）。G1 的方言门禁要求这一轮在 PostgreSQL 与 SQLite 上各全量通过。
3. ✅ **R3 回填**（2026-10-04 已合入，阶段 G20）：`scripts/snapshot_backfill.py` + 判定逻辑 `app/contexts/processing/retirement.py`。幂等（已有非空值即跳过）、只写不删、可中断重跑，另有 `--dry-run` 只报计数不落库。
4. ✅ **R4 对账**（2026-10-04 已合入，阶段 G20）：`scripts/snapshot_reconciliation.py` 逐键比较（`fields`/`progress`/四个逐文件列/`warnings`/`error`），三类非零情形：**漂移**、**仅存在于快照**、**关联不可判定**；任一非零即退出码 1。真实开发数据上的报告见 `docs/09 §30`。
5. ✅ **R5 切读**（2026-10-04 已合入，阶段 G21）：`JobRepository.get()` 只从规范化源重建（字段←模板版本或 `field_definitions`、逐文件←`document_versions`、进度←`progress` 列、告警与错误←当次尝试行、结果←`extraction_results`），快照列仍在写但没有任何代码读它；`Job.excel_path` 与快照里的 `result`/`excel_path` 键一并删除。回归按要求跑满：两方言各 352 项、`-m s3`/`-m broker`、两种浏览器端到端形态各 12/12（`docs/06 §5.21`）。
6. **R6 删列**：`ALTER TABLE processing_jobs DROP COLUMN snapshot`。**执行条件见 §6**。

顺序上刻意把"切读"(R5) 与"删列"(R6) 分成两个修订：R5 出问题可以立刻把读路径改回快照（一行代码），R6 出问题只能从备份恢复库。

## 4. 历史数据的硬边界

阶段 C 之前的任务没有 `document_versions` 行，也没有 `extraction_results` 行。对这类行，新列回填不出来，规范化源也重建不出 `Job`。处置规则，按优先级：

1. 开发库：这些行属于演示数据，可在 R6 之前单独清理（清理动作等同 §6 的备份与审批要求）。
2. 任何有真实数据的部署：**不允许**为了删列而丢弃无法重建的行。对账脚本必须把这类行单列为"仅存在于快照"，只要计数非零，R6 就不得执行。

这条是本方案最重要的约束：双真相的收尾不能变成数据丢失。

**R4 落地时补上的一条（2026-10-04，阶段 G20）**：逐文件事实的关联键是 `storage_key`——快照 `files[]` 本来就带着它（`JobRepository._snapshot` 写入），而它在版本行上是唯一列，所以"一次上传两个同名文件"是可判定的。只有**没有** `storage_key` 的历史行才退回按清洗后的文件名关联，那时同名多行才是真的没有答案：这类行判为**关联不可判定**，既不猜也不判通过，与"仅存在于快照"一样阻塞 R6。（本条最初的版本写成了"快照里没有 `storage_key`"，那是把 `Job.to_dict()` 的展示形状当成了 `_snapshot()` 的存储形状；核对源码后已更正，见 `docs/09 §30`。）

## 5. 验证与回归

- 每个修订都要过 `scripts/migration_gate.py`（空库 `upgrade head → downgrade -1 → upgrade head` + `alembic check` 无漂移），PostgreSQL 与 SQLite 各一次。
- R4 的对账脚本先在真实开发数据上跑出报告；期望终态是"漂移 0 行、仅快照 0 行"。**已执行（2026-10-04，G20）**：本机开发库（SQLite，`d5e2b74c0a19`）1 条任务，回填前报 5 条漂移（`fields`/`progress` 未回填 + 三个逐文件列 NULL 对不上快照）、仅快照 0、不可判定 0，退出码 1；`snapshot_backfill.py` 跑完再对账为 `CLEAN`、退出码 0；另用注入 `page_count+1` 证明判据真会失败（退出码回到 1），随后按快照值复原并复测 `CLEAN`。
- 端到端：`E2E_COMPOSE=1` 那条链路必须全绿——它是唯一会真正走"上传→队列→Worker 执行→复核修订→导出"完整生命周期并断言读路径的自动化证据（G8 就是靠它抓到派发租约竞态的）。
- 用例覆盖：内联字段任务与模板版本任务各一条重建断言；`progress` 与 `status` 同事务；逐文件解析列（`page_count` 等）在解析失败的部分成功场景下的取值；`warnings` 在旧尝试上的归属。**R1+R2 这四项由 `tests/test_snapshot_retirement_r1r2.py`（TC-DATA-007，七条）覆盖**；"用规范化源重建 `Job`" 的断言本身要等 R5 才有对象，那一步用例另立。

## 6. 删除列的门禁（R6）

R6 是不可逆的破坏性动作，同时满足以下四条才允许执行，缺一不可：

### 6.1 四条门禁清单

1. R5 已合入并在目标环境运行过至少一个完整工作日，期间审计动作 `job.rebuild_incomplete` 的**新增条数为 0**（`GET /api/v1/platform/usage` 的 `job_rebuild_incomplete_total`）（G21 换成计数，G27 再换成**持久**判据：读路径遇到不可重建的行会抛 `IncompleteJobFacts`、写一条 `job.rebuild_incomplete` 审计事件并计入进程内计数，不静默回落快照。§6.1 看的是审计表里的条数——进程内计数活不过重启，用它做删列门禁等于把证据放在最容易丢的地方）。
2. `scripts/snapshot_reconciliation.py` 在**每一个**将被影响的数据库上报告"漂移 0、仅快照 0"。
3. 已按 `scripts/backup_restore_drill.sh` 做过一次带数据的成功恢复演练，且对象卷按 `scripts/object_store_backup_drill.py` 演练过——注意 R-018 当前的结论（`docs/17` G-DEC-11）：冷副本不保证每次可恢复，所以删除前**另存一份纯逻辑导出**（`pg_dump --column` 级别的 `processing_jobs` 快照转储，落地到版本控制之外的独立存储）作为兜底，不能只依赖卷副本。**工具见 `scripts/snapshot_logical_export.py`（维护轮 M10–M13）**：逐行导出 `snapshot` 与 R1 规范化列（`field_definitions`、`progress`）写成自包含的 `snapshot.jsonl` + `manifest.json`（逐行摘要与整文件摘要），`--verify` 可事后校验，`--replay` 可写进空的一次性库再读回，`--include-parents` 连依赖行一起导出使导出**自足**，`--rebuild-check` 在 replay 之后调 `JobRepository._rebuild()` 证明**任务详情可重建**；`--rebuild-content` 再往前一步比 `result` 的**取值**，并按复核状态分档（未复核逐键相等，已复核只验键集与非空——复核后的当前值与快照的机器值本来就应当不同，要求相等会把正确行为判红）。与 `scripts/snapshot_reconciliation.py` 的分工：后者比**规范化列 vs 快照**（R5 迁移有没有丢数据），前者比**重建产物 vs 快照**（这份导出能不能还原出取值正确的任务）。`pg_dump` 没有"按列"这个粒度（要么整库要么整表），所以做法是逐行序列化，效果等价而更小，且 SQLite 与 PostgreSQL 共用同一份代码。脚本拒绝写入被 git 跟踪的目录。
   **两条实测结论**：① 只导 `snapshot` 列**不构成可独立恢复的备份**——`processing_jobs.tenant_id` 引用 `tenants`，空库无父行时插入被 `ForeignKeyViolation` 拒绝（决定性读数取自非超级用户，关不掉外键的情形）；② 只导 `snapshot` 列**也重建不出任务**——R5 切读后 `_rebuild()` 的 `fields` 与 `progress` 取自 R1 规范化列，实测报"缺 fields、progress"。所以导出同时带这三列，依赖行按四层顺序装（任务行自己也是被引用者）。这不是本门禁的缺口：门禁要保的是"这一列的内容在卷副本坏了时还能读出来"，而"这份导出能把任务读回来"是更强的问题，工具现在两个都覆盖了。
4. 负责人书面确认（本文件的状态从"待评审"改为"已批准"，并记入 `docs/08`）。

## 9. R5 落地前必须一并搬迁的东西（阶段 G20 发现，G21 已全部处理）

R3/R4 写出来之后才看清：`get()` 对快照的依赖不止 §2 列的那四处，而且**这条读路径今天就是坏的**。R5 若按"纯搬迁"来做会漏掉下面五条，其中第 3、4 条会改变行为。

1. **`Job.result` 仍由快照喂**。阶段 G4 把 `/result`、`/excel`、`/export` 都切到了 `extraction_results`，但 `get()` 里还有 `result=snap.get("result")`——这是最后一个只认快照的读入口。R5 必须二选一：改成从 `extraction_results` 重建，或删掉这个字段、让所有消费者走 G4 的读取函数。留着不动的话，R6 删列会让 `Job.result` 静默变成 `None`，而没有任何用例会立刻红。
2. **`Job.excel_path` 要一起删**。§2 已决定不为它建列（G4 起 `/excel` 每次按需构建），但 dataclass 字段和 `snap.get("excel_path")` 都还在。
3. **`files[].path` 会随换源消失**。快照里 `storage_key` 与 `path` 都有（`_snapshot` 写的全集），而 §2 已决定 `path` 不迁移、直接删——版本行上没有这一列。所以 R5 从 `document_versions` 重建时，`storage_key` 是同一批值换个来源（版本行的唯一列，值相同），`path` 则必然变成空串。今天还依赖 `path` 读本地文件的进程内路径必须在那之前清干净；`FileInfo.path` 本身按 §2 保留给纯内存场景，只是不再由持久化任务提供。
4. **`document_versions.job_id` 是 `SET NULL`**。任务行被清理时版本行留着、指针置空，反过来一条"版本行已经不指向它"的任务在 R5 之后会重建出零个文件——这类行必须由 R4 报成"仅存在于快照"，而不是被静默重建为空任务。
5. **§6.1 需要一个能失败的判据**。"R5 运行一个完整工作日、期间没有回退读路径的需要"是主观说法，没人能证明。改成可度量的：`get()` 在规范化源不完整时**明确失败并留下持久痕迹**（抛 `IncompleteJobFacts` + 写 `job.rebuild_incomplete` 审计事件，不静默回落快照），观察期内该审计事件新增 0 条才算满足 §6.1。计数必须是审计表里的条数而不是进程内变量——G21 用过进程内计数，它在一次重启后就不知道该数什么了，而删列是几周后的决定。宁可让一条重建不出来的任务在界面上报错，也不要让它带着空字段被当成正常任务展示——那正是 R-013 双真相的原始症状。
