## 1. 为什么必须留这份方案

阶段 D 起机器值与修订值都写 `extraction_results`，G4 又把 `/result`、`/excel`、`/export` 全部切到规范化结果，但 `processing_jobs.snapshot` 仍然活着，因为 `JobRepository.get()` 还用**整份快照**重建内存里的 `Job`：字段定义、文件清单、进度、告警、错误。后果是 R-013 说的双真相没有真正闭合——写路径有两个家，读路径还剩一个只认快照的重建入口。

留着它还有两个更实际的代价：每次状态变化都要重抄一份 JSON（写放大，且大任务的 `result` 会在快照里再存一遍）；任何"按字段查任务"的诉求都只能靠 JSON 展开，PostgreSQL 与 SQLite 的行为还不一致（`docs/08` R-016 的残留项之一）。

**结论：快照必须退役，但删列是破坏性动作，必须先有对账证明规范化源能完整重建，再谈删除。**

## 2. 快照里现在有什么，规范化源缺什么

`JobRepository.get()` 读的键，逐个给出目标归属（`→` 右侧为本方案落地后的唯一来源）：

| 快照键 | 现在的规范化源 | 缺口与处置 |
|---|---|---|
| `fields` | 有 `template_version_id` 时，冻结字段在 `template_versions.fields` | 内联字段（不引用模板版本创建的任务）没有家。→ 新增 `processing_jobs.field_definitions`（JSON，创建时写入后不可变）。规则：`template_version_id` 非空就只信模板版本，为空才读这一列；两处都有且不一致即视为脏数据，对账脚本必须报出来 |
| `files[]` | `document_versions`（按 `job_id` 关联）提供 `original_filename` / `storage_key` / `checksum` / `media_type` / `size_bytes` | `FileInfo` 的 `page_count`、`chars`、`ocr_applied`、逐文件 `error` 无处可存。→ 给 `document_versions` 增加这四列（它们本来就是"这一版解析出来的结果"）。`path` 是遗留进程内入口专用的绝对路径，G3 之后一律为空，**不迁移直接删**（`docs/09 §11`） |
| `progress` | 无 | 状态列 `status` 推不出 `progress`（`processing` 之下还有多个阶段）。→ 新增 `processing_jobs.progress` 列，与 `status` 同一事务写入，二者不可分开更新 |
| `result` | `extraction_results`（G4 起为 `/result`、`/excel`、`/export` 的权威源） | 无缺口。快照里的 `result` 副本直接消失 |
| `warnings[]` | 无 | 告警属于"某一次尝试的解析产物"。→ 新增 `job_attempts.warnings`（JSON） |
| `error` | `job_attempts.error`（最近一次尝试） | 无缺口 |
| `excel_path` | 无 | **不建列**。G4 起 `/excel` 每次按需构建，不再复用缓存文件；留着它只会重新引入"修订之后仍下载旧内容"那一类 bug |

`Job` dataclass 里 `excel_path` 字段随之删除；`FileInfo.path` 保留给纯内存场景（无租户入口已退役，用例里的沙箱进程内执行仍需要），但不再进快照。

## 3. 迁移顺序（每个修订都可单独回滚）

1. **R1 扩容（可空，不动读路径）**：`processing_jobs.field_definitions`、`processing_jobs.progress`、`document_versions.page_count/text_chars/ocr_applied/parse_error`、`job_attempts.warnings`。全部可空——可空意味着"还没回填"，不需要默认值猜测。
2. **R2 双写**：创建与处理链路在写快照的同一事务里写这些新列（写旧列的能力此时保留）。G1 的方言门禁要求这一轮在 PostgreSQL 与 SQLite 上各全量通过。
3. **R3 回填**：`scripts/snapshot_backfill.py` 从既有快照把历史行填进新列；幂等（已有非空值即跳过）、只写不删，可中断重跑——与 `scripts/storage_backfill_to_object_store.py` 同一套纪律。
4. **R4 对账**：`scripts/snapshot_reconciliation.py` 逐任务用规范化源重建 `Job`，与快照做**逐键比较**（不只是行数），报出漂移并返回非零退出码。这一步是删除的前置证据，也是唯一能证明"删了不丢信息"的东西。
5. **R5 切读**：`JobRepository.get()` 改为只从规范化源重建，快照列保留但不再被任何代码读取。切完必须跑：基础套件（两方言）+ 浏览器端到端两种形态 + 运营视图回归。
6. **R6 删列**：`ALTER TABLE processing_jobs DROP COLUMN snapshot`。**执行条件见 §6**。

顺序上刻意把"切读"(R5) 与"删列"(R6) 分成两个修订：R5 出问题可以立刻把读路径改回快照（一行代码），R6 出问题只能从备份恢复库。

## 4. 历史数据的硬边界

阶段 C 之前的任务没有 `document_versions` 行，也没有 `extraction_results` 行。对这类行，新列回填不出来，规范化源也重建不出 `Job`。处置规则，按优先级：

1. 开发库：这些行属于演示数据，可在 R6 之前单独清理（清理动作等同 §6 的备份与审批要求）。
2. 任何有真实数据的部署：**不允许**为了删列而丢弃无法重建的行。对账脚本必须把这类行单列为"仅存在于快照"，只要计数非零，R6 就不得执行。

这条是本方案最重要的约束：双真相的收尾不能变成数据丢失。

## 5. 验证与回归

- 每个修订都要过 `scripts/migration_gate.py`（空库 `upgrade head → downgrade -1 → upgrade head` + `alembic check` 无漂移），PostgreSQL 与 SQLite 各一次。
- R4 的对账脚本先在真实开发数据上跑出报告；期望终态是"漂移 0 行、仅快照 0 行"。
- 端到端：`E2E_COMPOSE=1` 那条链路必须全绿——它是唯一会真正走"上传→队列→Worker 执行→复核修订→导出"完整生命周期并断言读路径的自动化证据（G8 就是靠它抓到派发租约竞态的）。
- 用例覆盖：内联字段任务与模板版本任务各一条重建断言；`progress` 与 `status` 同事务；逐文件解析列（`page_count` 等）在解析失败的部分成功场景下的取值；`warnings` 在旧尝试上的归属。

## 6. 删除列的门禁（R6）

R6 是不可逆的破坏性动作，同时满足以下四条才允许执行，缺一不可：

1. R5 已合入并在目标环境运行过至少一个完整工作日，期间没有回退读路径的需要。
2. `scripts/snapshot_reconciliation.py` 在**每一个**将被影响的数据库上报告"漂移 0、仅快照 0"。
3. 已按 `scripts/backup_restore_drill.sh` 做过一次带数据的成功恢复演练，且对象卷按 `scripts/object_store_backup_drill.py` 演练过——注意 R-018 当前的结论（`docs/17` G-DEC-11）：冷副本不保证每次可恢复，所以删除前**另存一份纯逻辑导出**（`pg_dump --column` 级别的 `processing_jobs` 快照转储，落地到版本控制之外的独立存储）作为兜底，不能只依赖卷副本。
4. 负责人书面确认（本文件的状态从"待评审"改为"已批准"，并记入 `docs/08`）。

## 7. 本方案不解决的事

- 数据保留与彻底删除政策（G-DEC-03，`docs/19`）：删列与删用户数据是两回事，前者是本文件，后者仍待产品决策。
- 通知投递、Webhook 出站、配额强制（FR-040/041/042）：与本列无关。
- 把 `field_definitions` 进一步规范化成 `job_field_definitions` 关系表：当前形态够用，等到需要"按字段跨任务查询"时再评估，不提前建表。

## 8. 需要负责人拍板的三个问题

1. 阶段 C 之前的历史演示数据：允许清理，还是必须保留（保留则 R6 在该环境永不执行）？
2. 部署形态：是否已存在任何"真实客户数据"的库？决定 §4 走哪条分支。
3. R5 与 R6 是否合并到同一个发布窗口：默认建议**不合并**，中间至少隔一次带回归的观察期。
