## 1. 问题

`NFR-004` 把"搜索后端"列为应可替换的四类之一，而现状是：

- 查询：`app/contexts/search/service.py::search()` 直接调 `repository.search_entries()`，后者拼 `lower(content) LIKE pattern`。
- 写入：`service.py::reindex_version()` 直接 `db.add(SearchEntry(...))` / `entry.content = ...` / `db.delete(entry)`。
- 仓储：`app/contexts/search/repository.py` 里是四个模块级函数，直接 `select(SearchEntry)`。

后果：换成全文索引（PostgreSQL `tsvector`、外部搜索引擎）要改 service 与 repository 两层，且没有一处可注入的接口，因此也**无法在不改产品代码的前提下测"换后端"这件事**。

## 2. 取舍

| 方案 | 判断 |
|---|---|
| A. 抽 `SearchBackend` 契约，保留现有 SQL 实现为默认，加工厂与契约测试 | **采用**。行为不变、可回退、能立刻给"可替换"一个可执行判据 |
| B. 直接上 PostgreSQL `tsvector` | 不采用。真实分词与全文索引需要容量数据支撑（`docs/15 §10` 已记 `docs/08` R-010 容量假设未确认），且会改变查询语义（当前 `LIKE` 是子串匹配，`tsvector` 是词元匹配），属产品行为变更 |
| C. 只加注释说明"这里是替换点" | 不采用。这正是现状——M2 已证明注释不构成判据 |
| D. 引入外部搜索引擎（Elasticsearch 等） | 不采用。本地验证阶段引入新依赖，且与"不做线上部署"的边界冲突 |

## 3. 契约

新增 `app/contexts/search/backend.py`：

```python
class SearchBackend(ABC):
    """检索后端的可替换契约：重建索引与查询各一组。

    两侧必须成对替换：只换查询而保留写侧，会让索引行与查询语义错位——
    例如换成词元匹配的查询、索引仍按原文整段存，结果永远是零命中。
    """

    @abstractmethod
    def reindex(
        self, db: Session, *, tenant_id: str, document_id: str,
        document_version_id: str, filename: str, text: str,
        values: dict[str, Any], now: datetime,
    ) -> None:
        """把一个文件版本的索引重建为给定来源；同来源覆盖、缺失来源清除。"""

    @abstractmethod
    def query(
        self, db: Session, *, tenant_id: str, pattern: str, kind: str | None,
        doc_type: str | None, limit: int, offset: int,
    ) -> tuple[int, list[tuple[SearchEntry, str | None]]]:
        """按已转义的模式查询，返回 (总数, [(条目, 文档类型)])。"""


class SqlSearchBackend(SearchBackend):
    """默认实现：`search_entries` 表 + `lower(content) LIKE`。行为与抽取前逐字一致。"""
```

**边界划在"模式"而不是"查询词"**：契约接收的是**已转义**的 `pattern`，转义（`_like_pattern`）与限长校验留在 service。理由是转义是**查询语义**的一部分——换成词元匹配的后端时，转义规则完全不同（`%` 不再是通配符）。把它放进契约会让每个后端各写一份转义，而 service 就失去了"查询词合法性"这一层的唯一权威。

## 4. 工厂与配置

`app/contexts/search/__init__.py` 加：

```python
def get_search_backend() -> SearchBackend:
    """按 `SEARCH_BACKEND` 选实现；默认 `sql`。未知值显式抛错，不静默退化。"""
```

`app/platform/config.py` 加 `SEARCH_BACKEND = os.getenv("SEARCH_BACKEND", "sql").strip().lower()`。**只有 `sql` 一个合法值**，未知值抛 `RuntimeError`——与 `STORAGE_BACKEND`、`EXTRACTOR_MODE` 同一套纪律：配置错了要显式失败，不能悄悄用默认值跑。

## 5. 依赖方向（`docs/adr/0003` 的硬规则）

- `backend.py` 依赖 `domain.py`（`SearchEntry`）与 `repository.py`（默认实现转发），**不依赖 service**。
- `service.py` 依赖 `backend` 的**契约**，不再直接依赖 `repository` 的查询函数（写入路径的 `entries_for_version` 仍走 repository，因为它是"取现有索引行"的读，不是后端语义）。
- `api.py` 不变。
- 反向依赖（backend → service）不存在，因此无环。

## 6. 验收

| 判据 | 反向（怎么证明它不是恒过） |
|---|---|
| 默认配置下行为逐字不变：现有 `tests/test_search.py` 5 条全绿 | 把工厂改成返回空实现 → 现有用例红 |
| 工厂返回 `SqlSearchBackend`；未知 `SEARCH_BACKEND` 抛 `RuntimeError` | 去掉未知值分支 → 契约用例红 |
| 经工厂替换成假后端后，**HTTP `/search` 走的是假实现**（不是只在构造函数层生效） | 把 service 改回直连 repository → 契约用例红（M2 的教训：换工厂对构造时绑定无效） |
| 假后端能拿到**已转义**的模式（`%` 被转义成 `\%`） | 把转义挪进 backend → 断言红 |
| 写入侧同样可替换：`reindex_version` 经契约调用 | 只换查询侧 → 写侧契约用例红 |

## 7. 不做的事

- 不改查询语义（仍是子串匹配）、不加 `tsvector`、不引外部依赖。
- 不改 `search_entries` 表结构、不加迁移。
- 不动 `docs/15` 已定的转义与限长规则（`q` 去空白后 2–60 字符、`%_\` 转义、`snippet` ±40 字符）。
- 不解决"`LIKE` 退化为顺序扫描"这个性能问题——那是 `docs/15 §10` 与 `docs/08` R-010 记的容量问题，需要容量数据支撑后再定。

## 8. 风险

| 风险 | 处理 |
|---|---|
| 抽契约时把 `LIKE` 语义漏进 service，导致新后端只能假装自己是 SQL | 契约只传 `pattern`，不传 `LIKE` 专用的 `escape`；`escape="\\"` 留在 `SqlSearchBackend` 内部 |
| 两侧只换一半 | 契约把 `reindex` 与 `query` 放在同一个 ABC 里，且有"只换查询侧 → 红"的反向验证 |
| 多一层间接让调用方找不到实现 | `backend.py` 的类 docstring 直接写明"默认实现转发到 `repository.py` 的四个函数" |
