## 1. 为什么先评审而不是先动手

"方向变了"最容易被读成"现在就开始改"。而这个转向动的是四条主线的重心：现在是"租户上传文档 → 平台提取 → 人工复核 → 导出"，转向后重心是"对外提供模型/推理能力"。这两者的计量对象、限额对象、认证对象、计费对象都不同。

SWD 对 Tier 1 的要求是逐阶段确认：需求 → 设计 → 测试计划 → 实现。本文件覆盖"需求"这一阶段的产出，即**说清要变成什么、有哪些走法、代价各是什么**，并把不能由工程侧决定的问题挑出来。

## 2. 现状盘点（可复用的部分，全部实测）

| 已有资产 | 位置 | 对 AaaS 的可复用性 |
|---|---|---|
| 模型调用配置 | `app/config.py`：`AI_BASE_URL`、`AI_API_KEY`、`AI_MODEL`、`AI_TIMEOUT`、`AI_MAX_RETRIES`、`AI_TEMPERATURE` | **可直接复用**。已是"OpenAI 兼容接口"形态，换供应商只改配置 |
| 提取契约 | `app/services/extraction/base.py`：`ExtractorBase.extract(text, fields, metadata) -> ExtractResult` | **可复用**。它就是"输入文本 + 字段定义 → 结构化结果"的接口，正是对外推理 API 的形状 |
| 两个实现 | `mock.py`（离线基线）、`llm.py`（`httpx` 直调兼容接口） | **可复用**。`mock` 让对外能力可以在无密钥环境里被端到端验证 |
| 字段 schema 与类型强转 | `FieldDefinition` + `coerce_value` / `apply_type_coercion` | **可复用**。对外 API 的"输出形状由调用方给定"这条正是靠它 |
| 多租户隔离 | 三层强制（路径依赖、显式 `tenant_id`、复合外键/部分唯一索引） | **可复用**。对外服务同样要"一个 key 只能看自己的东西" |
| 审计与关联 ID | `audit_events` + `request_id`（`X-Request-ID` 贯穿响应头/日志/审计） | **可复用**。对外调用更需要它 |
| 任务与租约骨架 | `processing_jobs` + 派发行 + 执行租约（条件更新单胜） | **取决于范围**：只做推理 API 则不需要；做多步智能体则可复用 |
| 复核工作流 | `extraction_results` 的 `state`（machine/revised/confirmed/rejected）+ 修订链 | **取决于范围**：人工复核是"文档工作流"的产物，纯推理服务没有这一环 |
| 配额 | `tenant_quotas` 两轴：`max_documents`、`max_storage_bytes` | **需要改**。这两个轴量的是文档与存储，不是模型消耗 |
| 用量视图 | 文档数、版本数、存储字节 | **需要扩**。对外服务的量是调用与 token |

## 3. 两个应由业主决定的问题

工程侧不替业主定这两个，因为它们决定架构走向，而不只是参数。

### 3.1 对外暴露的是什么

| 方案 | 含义 | 保留什么、丢什么 |
|---|---|---|
| **A. 推理 API** | 输入文本或图片 + 字段定义，返回结构化结果。一次调用一个结果，无状态 | 保留提取契约、类型强转、多租户、审计；**不需要**任务/租约/复核那套骨架。最小可行，也最容易对外说明 |
| **B. 托管智能体** | 多步、可调用工具、可长时间运行 | 可复用任务/租约/派发/重试（这些本就是为"长时间、可恢复"设计的）；但要新增步骤编排、工具注册与权限、单次会话的成本上限 |
| **C. 两者都做** | A 作为 B 的原子能力 | 先落 A 再落 B，B 复用 A 的契约。风险是范围一次铺太大 |

工程侧的倾向是 **A → 再评估 B**：A 的契约已经存在（`ExtractorBase`），改动面小且可本机验证；B 需要先把"一个智能体一次能花多少钱"这类上限定下来，否则配额无从设计。

### 3.2 计费量是否要换

`docs/19 §7` 刚定的口径是"按文档数 + 存储字节"。对外提供推理能力后，常见的计费量是 **token / 调用次数 / 算力秒**。

| 方案 | 影响 |
|---|---|
| **保持文档数 + 存储字节** | 无需新埋点。但对外服务里"一次调用"不产生文档，计费会漏掉主要成本 |
| **改为 token 或调用次数** | 需要新增计量记录（每次调用的量、租户、时间），并新增配额轴。**`docs/19 §7` 的那条口径会作废**，需要重新批准 |
| **两套并行**（文档工作流按文档、对外服务按调用） | 计费模型复杂，但两类业务各自合理。需要一张"业务线 → 计量口径"的映射表 |

**这一条不确认，配额与计费就无法设计**——因为"上限"要挂在一个量上。

## 4. 影响面（无论选哪个方案都要处理的）

| 面 | 现状 | AaaS 下的缺口 |
|---|---|---|
| 认证 | 会话 Cookie + CSRF，面向浏览器；邀请令牌是一次性的 | 对外服务需要**长期凭据**（API key 或 OAuth client），且要能吊销、能轮换、能限权。现有令牌机制不覆盖 |
| 限流 | 配额是资源上限（文档数、字节数），不是速率 | 对外服务需要**速率限制**与并发上限，否则单个 key 能打满模型配额 |
| 计量 | 用量视图统计文档/版本/字节 | 需要**按调用的计量记录**，且要与审计同源（`request_id` 贯穿） |
| 配额判定时机 | 现有纪律是"在任何写入之前判定，被拒不留残迹" | 对外调用要在**调用模型之前**判定额度，否则成本已经发生 |
| 隐私边界 | NFR-002：文件、OCR 文本、提取结果按敏感信息处理，默认不得用于训练外部模型 | 语义变化：**我们是提供方**，客户数据流向我们。需要重述"我们的模型会不会拿客户数据训练"，这是对客户的承诺，不是内部约定 |
| 错误契约 | 现有 API 有稳定错误形状与 `request_id` | 对外 API 的错误契约要冻结并版本化，否则改一次就断一批客户 |
| 成本上限 | 单次任务成本未设阈值（`docs/19 §1` 的阈值只管本机基线） | 需要"单次调用/单租户的消耗上限"，与配额同一套判定纪律 |

## 5. 推荐的推进顺序（待你确认后逐阶段走）

1. **确认 §3 的两个问题**（暴露范围、计费量）。这两条不定，后面的设计会来回改。
2. **需求阶段产出**：写 `docs/02`/`docs/03` 里 AaaS 对应的 FR/NFR 编号（现在没有），含验收口径。
3. **设计阶段产出**：对外 API 契约（含版本策略）、认证与限流、计量与配额、隐私重述。此阶段出取舍表，不动代码。
4. **测试计划阶段产出**：对外契约的负向用例（无凭据、越权、超限、超速、模型失败）。
5. 实现。仍按"本机可验证"的边界推进，不引入部署形态。

## 6. 明确不做的事

- 不在本文件里定接口形状、表结构或配额数值。
- 不改现有文档工作流的行为：SaaS 形态的现有能力在转向期间保持可用，不因为要转 AaaS 就先拆掉。
- 不引入新的外部依赖（模型供应商由配置决定，不写死）。
- 不把"方向已定"读成"可以开始改结构"。

## 7. 风险

| 风险 | 处理 |
|---|---|
| 两条业务线的计量口径混在一起，导致计费说不清 | §3.2 确认前不设计计费表；若走两套并行，需要一张明确的映射表 |
| 把"对外提供推理"做成"把内部提取器直接暴露" | 内部契约面向"一次任务的字段提取"，对外契约要面向"调用方的稳定接口"。两者形状相近但承诺不同，需要独立的版本策略 |
| 配额判定放在调用之后 | 沿用现有纪律：判定在任何模型调用之前，被拒不留残迹、不产生成本 |
| 隐私承诺被含糊处理 | §4 的隐私重述是**对客户的承诺**，需要业主确认措辞后再写入对外文档 |
