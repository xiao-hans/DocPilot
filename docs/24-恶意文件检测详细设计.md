# 恶意文件检测详细设计（FR-010 补齐）

DOC-DD-024。维护轮 M30。口径来源：`docs/19 §7` 负责人答复（2026-10-17）两项——处置为**仅标记，不隔离不阻断**；引擎为**可替换契约 + 本地 ClamAV 适配器，默认关闭**。

## 1. 问题

FR-010 的写侧校验与读侧内容签名核对（G16，`POST /documents/{id}/integrity/check`）已交付。剩下的缺口只有一处：上传的字节从头到尾没有被任何引擎检查过是否含恶意内容。缺口本身不是"没写代码"，而是**没有口径**——检出之后拒收、隔离还是标记，三种处置对业务的影响完全不同，只能由负责人定。口径在 2026-10-17 定下，本节据此落地。

## 2. 取舍

### 2.1 为什么处置只写库不留阻断点

口径是"仅标记"。这意味着检出后的代价只有多一条告警，不会挡上传。落地时它对应三条具体约束：

- 检出**不抛异常**、不改 HTTP 状态码、不删对象、不改 `documents.status`。
- 结论落在 `document_versions.malware_status` 与 `malware_signature` 两列上，与版本同生命周期。
- 检出与"没扫成"各写一条审计事件；`clean` 与未扫不写。

第三条是本设计里唯一有争议的选择，理由见 §4.2。

### 2.2 为什么默认关闭

`MALWARE_SCAN_BACKEND` 为空或 `none` 时整条能力关闭，工厂返回 `None`，上传路径连分支都不进。这与 `docs/21` 的 Webhook 主密钥为空即禁用投递是同一姿态：**宁可"这件事没做"，也不要有一个看起来在跑、实际什么都没查的检查点**。默认开启还多一层问题——扫描器依赖本机 clamd，在没有 clamd 的机器上默认开启会让每次上传都记一条 `error`，噪声把真正的故障埋掉。

### 2.3 为什么结论要三档而不是两档

`clean` / `infected` / `error` 三档，`NULL` 表示从未扫过。`error` 单独存在是有意的：把"引擎连不上"混进 `clean` 会让一次引擎故障看起来像一次干净结果，**那是最坏的一种谎报**；把它混进 `infected` 则会把每一次引擎抖动变成一堆误报告警。同理，`NULL` 与 `clean` 在读取侧应可区分——历史版本没扫过，用默认值填 `clean` 等于伪造一次扫描结论，所以两列都可空且无服务端默认值。

## 3. 契约

`app/adapters/malware/base.py`：

```python
STATUS_CLEAN = "clean"
STATUS_INFECTED = "infected"
STATUS_ERROR = "error"

@dataclass(frozen=True)
class ScanResult:
    status: str
    signature: str | None = None   # 只在 infected 时有值
    reason: str | None = None      # 只在 error 时有值

class MalwareScanner(ABC):
    @property
    @abstractmethod
    def name(self) -> str: ...

    @abstractmethod
    def scan(self, data: bytes) -> ScanResult:
        """实现不得抛异常：扫不成要返回 error，不要用异常打断调用方。"""
```

**契约收的是字节，不是路径也不是存储句柄**。理由：换成基于路径的引擎（如 `clamscan --file`）时，调用方会不得不把对象落盘再传路径，而这个适配决定不该由契约强迫；反之换成流式引擎时，字节是最小共同输入。存储细节留在调用方，契约不替它决定。

`scan()` 不得抛异常这条写进契约而不是只在实现里兜底：调用方是上传路径，它应能假设"调这个函数不会炸"，否则每处调用都要包一层 try。

## 4. 实现

### 4.1 ClamAV 适配器

`app/adapters/malware/clamav.py` 走 clamd 的 `INSTREAM`：`zINSTREAM\0` 开头，随后 0 个或多个"4 字节大端长度 + 数据"块，以长度 0 的块结束；回复形如 `stream: OK\0` 或 `stream: Win.Test.EICAR_HDB-1 FOUND\0`。

传输层抽成 `ClamdTransport`（`exchange(request) -> bytes`），与 `docs/21` 的 Webhook `Transport` 同一姿态：协议编解码留在适配器里（可被断言），套接字动作可被替换（可在没有 ClamAV 的机器上做决定性验证）。

`parse_reply` 的判定顺序有讲究：**先看 `FOUND` 再看 `OK`**。判定用 `endswith` 而不是子串匹配——签名名里可能含 `OK`，用 `"OK" in text` 会把检出读成干净。反过来若把 `OK` 分支放前面，`stream: X FOUND` 不含 `OK` 时不受影响，但畸形回复会。宁可漏一个不可能的边界，也不要把可疑读成干净。

### 4.2 落库与审计

`app/contexts/documents/malware.py` 三个函数：

| 函数 | 职责 |
|---|---|
| `scan_into(scanner, data, version)` | 扫一次，把结论写进版本行；扫描器为 `None` 直接返回 `None`。不抛异常 |
| `audit_events_for(versions, *, tenant_id, actor_id)` | 按已写入的结论生成 `AuditEvent` 对象（未写库，供并入上传事务） |
| `summarize(versions)` | 按结论计数，未扫过的计入 `unscanned` |

**为什么 `clean` 不记审计**：干净是绝大多数，逐条入库会把审计面淹成噪声，真正的检出反而难找。审计的读者是"事后查有没有出事"的人，不是"统计扫了多少次"的人——后者由 `malware_status` 列本身回答，一次 `GROUP BY` 就够。代价是"某次上传扫过且干净"这件事只能从列上读、不能从审计流上读；这是有意的取舍。

**为什么扫描器异常也记 `error` 而不冒泡**：检测是旁路组件，它自己的 bug 不该让一次正常上传变成 500。`scan_into` 里 `except Exception` 兜一层，把异常类型记进日志，结论记 `error`。

### 4.3 上传路径的接入点

`app/contexts/processing/api.py` 的 `create_job` 里，`storage.put` 之后、事务提交之前：

```python
malware.scan_into(scanner, content, document_version)
```

三个位置选择各有理由：

- **扫内存字节而不是回读存储**：刚写完就回读只会多一次 I/O，还引入"读到的与写下的不是同一份"的可能。
- **在 `storage.put` 之后**：对象已经在，检出时它确实存在于系统里，审计里记的 `object_id` 指向的版本行有对应实体。
- **在事务提交之前**：结论与版本行同一个事务落库。分成两个事务会出现"版本在、结论缺"的中间态。

`scanner = malware.get_scanner()` 在文件循环外取一次：能力关闭时它是 `None`，循环里连分支都不进。

### 4.4 迁移

`migrations/versions/a8c41f2b6e07_malware_scan_columns.py`（`down_revision='e1f4c7a29d63'`）：`document_versions` 加 `malware_status String(20) NULL` 与 `malware_signature String(200) NULL`，两列都无服务端默认值（理由见 §2.3）。

### 4.5 配置

`app/platform/config.py`：

| 键 | 默认 | 说明 |
|---|---|---|
| `MALWARE_SCAN_BACKEND` | `none` | `none` 关闭；`clamav` 走本机 clamd。未知值在工厂里抛 `RuntimeError` |
| `CLAMAV_HOST` | `127.0.0.1` | |
| `CLAMAV_PORT` | `3310` | 钳制到 1–65535 |
| `CLAMAV_TIMEOUT_SECONDS` | `10` | 钳制到 1–300 |

工厂 `build_scanner(name=None)` 与 `get_scanner()` 每次调用都读配置——与 `get_search_backend()` 同理，换配置不需要重建进程内状态。

## 5. 依赖方向

- `app/adapters/malware/*` 只依赖自身与 `app/platform/config`，不依赖任何 context。
- `app/contexts/documents/malware.py` 依赖 `app/adapters/malware`（契约与工厂）、`app/models/document`、`app/shared/audit`。
- `app/contexts/processing/api.py` 依赖 `app.contexts.documents.malware`——这是**跨上下文依赖**，记入债务：`processing` 的写路径要知道 `documents` 的检测口径。更干净的做法是让 `processing` 只发"版本已创建"事件、由订阅方触发检测，但当前没有事件总线（outbox 是写出去给外部的），为这一处引一条内部总线不划算。已在 `docs/12 §7` 的归属表里标注。
- `documents/service.py` 的 `list_documents` 把 `malware_status` 带进版本条目——读侧不需要知道检测是怎么做的，只需要这个字段。

## 6. 验收

`tests/test_malware.py` 22 条。四个面各有一条"退化了会怎样"的对照：

| 判据 | 反向（怎么证明它不是恒过） |
|---|---|
| 关闭时不扫、不写列、不写审计 | 注入"扫描器为 None 时仍写 `clean`" → `test_upload_keeps_null_when_capability_is_off` 红 |
| `error` 与 `clean` 分开 | 把传输失败的返回值改成 `STATUS_CLEAN` → `test_transport_failure_is_error_not_clean` 红（已实测） |
| 检出只标记不阻断 | 在 `infected` 分支加 `raise` → `test_upload_marks_infected_but_does_not_block` 红（已实测） |
| 上传路径真的调了扫描 | 删掉 `scan_into` 调用 → `test_upload_records_clean_when_scanner_is_on` 红（已实测） |
| 判定不用子串匹配 | 改成 `if "OK" in text: return clean` → `test_found_is_checked_before_ok` 红（已实测） |

第一条的反向验证在 M30 的注入里**没成立过**：第一次注入的形态是 `endswith("OK")` 分支，而用例的回复以 `FOUND` 结尾，那个分支永远走不到，`rc=0`。这说明注入无效，不是判据无效。改用子串匹配才是真实的退化形态。

## 7. 不做的事

- 不做隔离、不做拒收、不删对象、不改 `documents.status`——口径就是仅标记。
- 不做定期全量重扫、不做签名库更新——那是运维动作，不是应用行为。
- 不做多引擎编排、不做信誉查询。
- 不改上传与处理路径的失败语义。
- 不把检测结果写进 `extraction_results` 或 `search_entries`——它属于版本，不属于提取结果。

## 8. 风险

| 风险 | 处理 |
|---|---|
| 默认关闭 → 部署后没人开，以为有检测实际没有 | `MALWARE_SCAN_BACKEND` 只在显式设置时生效。库里 `malware_status` 全为 `NULL` 就是"没开"的直接证据（`SELECT malware_status, count(*) FROM document_versions GROUP BY 1`）。运维视图已展示这个分布（维护轮 M31，`app/contexts/operations/service.py` 的 `tenant_usage()` 返回 `malware`，界面在"本工作空间用量"里逐状态给计数）；"未扫描"应单独一格，不应折进"干净"，否则会把"能力没开"显示成"全部通过" |
| 检出只标记 → 恶意文件仍在库里、仍可下载 | 口径即如此。真正的处置（隔离/删）需要另一次批准，且要定"谁有权判误报" |
| clamd 不可达 → 每次上传多一次连接超时（默认 10 秒） | 超时钳到 1–300 秒；结论记 `error` 而不是失败。运维视图里 `error` 计数升高即可定位 |
| 大文件扫描耗时 | 走内存字节、不分块落盘；`INSTREAM` 按 8 KB 分块发送。真正的瓶颈是 clamd 的吞吐，属容量问题，`docs/08` 记 |
| `processing` → `documents` 的跨上下文依赖 | 已在 `docs/12 §7` 标注为债务。引入内部事件总线是更大的改动，当前不做 |
| 审计只记检出与失败 → "扫了多少次"查不到 | 由 `malware_status` 列 `GROUP BY` 回答。若将来需要时间序列，那是运维报表的事，不该塞进审计流 |
