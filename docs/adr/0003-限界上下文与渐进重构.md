# ADR-0003：以 DDD 限界上下文约束模块边界，渐进重构目录

- 状态：已接受，待阶段 C 验证
- 日期：2026-10-02
- 相关：`docs/12-领域驱动设计与限界上下文.md`、`docs/04-概要设计说明.md`、ADR-0001、ADR-0002

## 背景

阶段 B 之前，`Membership.role` 与 `is_platform_admin` 已经入库却没有任何代码使用它们，授权判定散落在数据访问层，最终在评审时暴露出一个 P0：匿名历史接口 `GET /api/jobs/{id}` 借 `JobManager.get_job(tenant_id=None)` 的内部回退读到了其他租户的任务并可下载 Excel。根因不是缺字段，而是"谁能改这个数据"没有归属：任务读取同时服务传输层与 worker，租户边界在两个调用者之间被隐式共享。

阶段 C–F 会新增模板、任务尝试、复核、检索与集成五类对象。若不先决定边界与归属，每个阶段都会重演同类缺陷。

## 决策

1. 采用 DDD 战略设计划分上下文（身份与授权、文档资产、模板配置、处理编排、提取与复核、检索、集成与运营），以 `docs/12` 为基线，含统一语言与上下文映射。
2. 一个事务只修改一个聚合；跨聚合一律持 ID 不持对象。不变式（例如"每空间至少一名 active owner"、"已发布模板版本不可改"）写在聚合所在层，而不是端点里。
3. 代码布局渐进重构：新上下文使用 `app/contexts/<ctx>/{domain,repository,service,api}.py` 骨架；存量代码只在触及它的阶段内搬移，不开独立重构分支。
4. 两条硬性规则由评审保证：仓储查询必须显式携带 `tenant_id`，无租户上下文的方法只能命名 `*_internal` 且仅供 worker；授权判定只写在 API 层依赖声明处。
5. 阶段 C 引入事务性 outbox 表记录领域事件，先落库不接消息中间件。

## 备选方案

| 方案 | 取舍 |
|---|---|
| 保持现状分层（`api/services/models`）不加边界约定 | 短期改动最小，但阶段 C 一次加 3 个聚合、5 类端点，"规则写在哪儿"会持续摇摆；阶段 B 的 P0 正是这种摇摆的后果 |
| 立即把全部代码重排为 `app/contexts/**` | 边界一次到位，但要一次改动 168 项测试覆盖的全部路径；重构与功能同时变更时，回归失败无法定位原因 |
| 拆微服务（模板服务、处理服务独立部署） | 与团队规模和负载未知冲突（`docs/04 §5`），网络边界还会让"同事务写快照与文档版本"这类保证变弱 |

## 影响

**正面**

- 越权类缺陷有单一收敛点：仓储签名与 API 依赖声明，评审可按条核对。
- 阶段 C–F 的新对象有明确归属，模板版本与任务引用关系不需要临时发明位置。
- 渐进搬移让每次迁移都有回归测试兜底，不出现"重构期"盲区。

**负面与风险**

- 边界靠约定维持，没有编译期强制；跨上下文传 ORM 对象的违规只能靠评审与后续静态检查发现。
- 目录会出现两套布局并存期（`app/services/*` 与 `app/contexts/*`），新人定位成本上升；由 `docs/12 §7` 的归属表缓解。
- 快照双写期延长，规范化表与 JSON 快照存在短期不一致风险；由"同事务写入 + 不回填"限制爆炸半径。

**验证动作**

1. 阶段 C 实现时，模板与处理上下文按新骨架落位，并由越权负向用例验证仓储 `tenant_id` 规则。
2. 阶段 D 收拢身份上下文后，阶段 B 的 168 项测试必须仍全部通过（不修改断言）。
3. 每次阶段结束在 `docs/09` 记录边界违例发现数，若连续两个阶段为 0，可考虑加入静态检查（如导入白名单测试）替代人工评审。
