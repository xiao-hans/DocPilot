# ADR-0004：任务队列采用 RabbitMQ + pika 自建薄层，而非 Celery

| 属性 | 内容 |
|---|---|
| 状态 | 已采用（2026-10-03，阶段 G2）；取代 `docs/17 §3` 中"队列建议采用 Celery + RabbitMQ"的初步建议 |
| 日期 | 2026-10-03 |
| 关联需求 | FR-020/021/022/024/025、NFR-003/004/009 |
| 依据 | `docs/17 §3/§4`、`docs/04 §6`、`docs/06 §5.7` |

## 背景

`docs/17 §4` 要求的可靠性语义是**数据库权威**的：任务在同一个 PostgreSQL 事务里落库并登记派发意图；派发器以可重试方式发布持久消息并等待 publisher confirm；Worker 通过条件更新领取带随机令牌的执行租约，周期续租，租约过期后由恢复器重新排队或终结；结果与终态必须同事务写入，旧执行者不得覆盖新尝试。

原设计建议用 Celery + RabbitMQ 承载消息。落地前发现两点具体障碍：

1. Celery 默认的 prefork 执行池在 Windows 上不受支持，而本项目的开发、测试与迁移验证入口都固定在 Windows 侧的 `.venv`（见 `docs/09 §5`）。走 Celery 就必须把 Worker 搬进 WSL 的第二个 Linux 环境，并在跨 OS 挂载目录上重装 PyMuPDF、RapidOCR 等重依赖。
2. Celery 自带一套任务状态机（重试、acks_late、可见性超时、result backend），它与 `docs/17 §4` 要求的租约/尝试/回收模型**语义重叠且互相竞争**。原设计已明确"不使用 Celery result backend 作为业务结果库"，也就是说 Celery 的大部分状态能力会被刻意绕开，只留下 broker 连接管理。

## 决策

- 队列继续使用 RabbitMQ（持久队列、持久消息、publisher confirm、手动消费确认）。
- 消息层改为 `pika` 自建薄层，实现集中在三个模块：
  - `app/contexts/processing/broker.py`：连接与通道管理、发布确认、prefetch 与手动 ack、跨线程安全的停止（`stop()` 通过 `add_callback_threadsafe` 投递回连接的 IO 线程）。
  - `app/contexts/processing/dispatcher.py`：把 `job_dispatches` 中 `ready` 记录发布出去，只有拿到确认才推进为 `published`；失败留在 `ready` 重放。
  - `app/worker.py`：独立进程 `python -m app.worker`，领取租约 → 周期续租 → 复用现有处理链路执行 → 结果与租约同事务收口 → 手动 ack。
- 业务状态的权威仍然是 `processing_jobs`、`job_attempts` 与新增的 `job_dispatches`；消息只携带 `dispatch_id/job_id/tenant_id/attempt_no/queue`，不含文件正文、令牌或绝对路径。
- 队列模式是显式运维选择：`BROKER_URL` 为空时任务仍由 API 进程内执行（现有开发与 273 项用例基线），非空时 API 不再进程内执行，改由 `python -m app.dispatcher` + Worker 承载。

## 备选方案

- **Celery + RabbitMQ**：省掉连接重试与 ack 细节，但要引入第二套任务状态机、拆分开发环境到 WSL，并与我们已有的尝试/回收表建立映射层。否决。
- **`aio-pika` 异步客户端**：与 FastAPI 的 asyncio 循环更贴合，但 Worker 是独立进程、执行链路（PyMuPDF/OCR/pandas）是同步 CPU 密集代码，异步只增加回调复杂度。否决。
- **数据库轮询，不引入 broker**：最少的移动部件，但无法满足"派发与执行移出 API 进程 + 多 Worker 水平扩展"的阶段目标。否决。

## 影响

**正面**

- 只依赖 `pika` 一个运行库（`requirements.txt` 已固定 `pika>=1.3,<2.0`），Windows 与 Linux 同一份 venv 可跑 API、派发器与 Worker。
- 并发判据只有一处：数据库条件更新。重复投递、双派发器、被接管的旧 Worker 都表现为"条件更新没命中"，不需要额外的分布式锁。
- 故障分支可以直接在测试里注入（记录型假传输、手工把租约置为过期、关闭连接模拟中断），不依赖真实 broker 即可覆盖 TC-REC-009/010/011 的判定逻辑。

**负面与风险**

- 连接与通道的重连、心跳、退避策略由我们自己负责；漏写一个分支就可能出现"Worker 假死"。当前以 `app/dispatcher.py` 与 `app/worker.py` 主循环的轮次级异常兜底 + 用例验证。
- 没有 Celery 的现成指标与生态（队列长度、任务耗时分布），可观测性需要在 G6 前自行补齐（`docs/08` R-009/R-010 相关）。
- 队列模式与进程内模式并存意味着部署配错会静默降回单进程执行；已在启动入口显式拒绝（未设置 `BROKER_URL` 时 `app.dispatcher`/`app.worker` 直接退出并说明原因）。

**验证动作**

- `tests/test_queue_dispatch.py`（11 项，记录型传输）：同事务登记派发、确认后才推进、发布失败留在 `ready`、超窗回退重投、租约唯一领取、过期租约被接管且旧执行者无法写结果、重复投递只留一次尝试、损坏消息直接确认、超时回收生成新派发行。
- `tests/test_queue_broker.py`（3 项，标记 `broker`，需本机 RabbitMQ）：真实发布确认与队列可见、重复投递只执行一次、连接中断后持久消息仍可被消费执行。未设置 `BROKER_URL` 时整组跳过并记为覆盖缺口，不作为通过。
- 全量用例在 PostgreSQL 与 SQLite 双方言复跑，迁移门禁 `scripts/migration_gate.py` 覆盖 `job_dispatches` 的空库与往返。
